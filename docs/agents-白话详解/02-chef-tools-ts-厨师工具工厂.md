# 02 · chef/tools.ts 源码白话详解（厨师工具工厂）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`tools.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agents/chef/src/tools.ts`
- 编译产物：`packages/agents/chef/dist/tools.js`

### 2、文件存在的核心原因

**因为** AI 模型不会"查冰箱"——它只会**调用工具**；而宿主注入的能力（Provider 实现）是程序函数，模型够不着，中间必须有一道"翻译 + 包装"工序：把每个注入的能力包装成一个 AI 可调用的工具（名字、说明、参数表齐全），并且**有几个能力才造几个工具**——没注入的能力绝不造假工具。**所以**必须有一个"工具工厂"，统一完成"检查能力 → 包装工具 → 交付工具列表"。

文件头注释原话："根据宿主实际注入的能力动态生成工具，没有实现的能力不会暴露给模型。"

**如果没有这个文件，程序会出现的问题：**

- Agent 要么一个工具都没有（配了能力也用不上），要么被迫注册全部工具（没配的能力一调就崩，模型还误以为能力存在）；
- 每个工具的包装代码散落各处，返回格式、异常兜底各自为政（好在有 agent-sdk 的 defineDomainTool 流水线，本文件只需要专注"造不造、造什么参数表"）。

### 3、文件的整体定位

这个文件**专门负责"按能力清单生成厨师域的工具列表"**，是 01 文档那套"能力合同"与 AI 之间的"发工具窗口"。全文件只有 1 个导出函数，但它是厨师 Agent"能不能干活、能干什么"的实际决定者。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- `@meimaohouse/agent-sdk`：`defineDomainTool`（把本领包装成标准工具的流水线，见 agent-sdk 02 文档）+ `DomainTool` 类型；
- `zod`：给有参数的工具写参数校验器；
- `./capabilities.js`：`ChefCapabilities` 类型（检查能力、转发调用的依据）。

**谁来调用它（下游）：**

- `index.ts`：`createChefAgent` 第一步就调 `createChefTools(options.capabilities)`，把产出的工具列表交给 defineSubAgent。

**一句话：能力注入的终点、AI 双手的起点——这个文件是两者的焊接点。**

## 模块2：文件内核心函数超详细说明

### 核心函数：`createChefTools(capabilities)`（工具车间）

1. **函数名称**：`createChefTools`，入参 `capabilities: ChefCapabilities = {}`（不传 = 空面板），返回 `DomainTool[]`（工具数组）。
2. **函数设计的根本原因**：**因为**"注入了什么能力就有什么工具"是一条必须强制执行的纪律，**而**工具注册动作（起名、写说明、定参数表、接转发）每个工具都要一遍，**所以**封装成一个工厂：进面板、出工具列表——纪律写一遍、四个工具都守。**不封装的弊端**：工具注册散在 index.ts 里，"没能力不注册"的 if 判断会被复制粘贴、迟早漏一处。
3. **函数语法写法的原因**：
   - **因为**绝大多数调用场景是"面板可能整个没传"（`createChefAgent()` 空参调用，见 index.ts 默认导出），**所以**参数默认值 `= {}`——空面板也是合法面板（返回空数组，零工具）；
   - **因为**工具的注册与否取决于运行时传入的面板内容，**所以**函数体内用 if 逐个判断（而不是配置驱动的一次性映射——**四个工具的参数表差异很大**（有的无参、有的带数组、有的带默认值），逐个 if 写直白代码反而最清晰、最好改）；
   - **因为**返回的是"一组工具"，**所以**类型是数组 `DomainTool[]`。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：`const tools: DomainTool[] = []`——先备一个空篮子；
   - 第 2 步：`if (capabilities.fridgeInventory)` → 先把能力实现存进局部变量 `provider`（**为什么要先存局部变量**：**因为** TS 的类型收窄——`capabilities.fridgeInventory` 在 if 里虽然知道非空，但闭包/回调里再引用时类型可能" Widening 回去"，存进 const 局部变量后类型收窄被固定，后续 `provider.read()` 编译器才敢放行；这是 TS 严格模式下的常见技巧）→ 用 `defineDomainTool` 注册 fridge_inventory 工具（无参数表 `z.object({})`，execute 直接转发 `provider.read()`）；
   - 第 3 步：`if (capabilities.groceryOrdering)` → 注册 order_groceries 工具——这个工具有**完整的参数表**：items 是商品数组（每件：name 非空 + quantity 正整数）、数组本身至少 1 件、note 可选；execute 解构出 items/note 组装成请求转发 `provider.placeOrder({ items, note })`；
   - 第 4 步：`if (capabilities.kitchenSafety)` → 注册 kitchen_safety_check 工具（无参数表，转发 `provider.inspect()`）；
   - 第 5 步：`if (capabilities.mealStats)` → 注册 meal_stats 工具——参数表只有一个 days：正整数、最多 365、**默认 7**（AI 没说查几天就默认查最近一周）；execute 解构 days 转发 `provider.read(days)`；
   - 第 6 步：`return tools`——篮子交出去。
5. **函数的触发条件**：`createChefAgent` 组装 Agent 时调用一次（每次创建厨师 Agent 都会走一遍——包括默认导出的空壳，空壳时四格全空、篮子空着返回）。
6. **函数的最终作用**：产出一个"与注入能力严格一致"的工具列表——配了几格就有几个工具，一格不多、一格不少。
7. **函数的使用场景**：仅被 index.ts 调用；未来宿主侧测试也可以直调它验证工具生成逻辑。
8. **函数的缺陷/注意事项**：四个 if 是"能力 → 工具"映射的**手工清单**——新增能力时必须记得来这里加 if 块（漏加 = 有能力没工具，Agent 永远说"暂无数据"），见模块6。

## 模块3：文件内每一个参数超详细说明

### 参数 1：`capabilities`（createChefTools 的入参——能力面板）

1. **名称 + 类型**：`capabilities`，`ChefCapabilities`（01 文档的四格面板），带默认值 `{}`。
2. **参数设计原因**：**因为**工厂的产出完全由面板决定，**所以**面板是唯一入参；**因为**"什么都不配"是合法且常见的形态（空壳 Agent），**所以**给默认值让空调用不报错。
3. **参数类型选择原因**：**因为**要用四格的可选性表达"配没配"，**所以**必须是 ChefCapabilities 接口类型（每格都是 Provider 可选字段）——换成宽松的 any 会丢掉全部类型保护。
4. **参数的传入来源**：createChefAgent 转发的 `options.capabilities`（宿主在装配时填）。
5. **参数的内部使用逻辑**：四个 if 分别读四格；格里有值就把值固定到局部 provider 变量供 execute 转发。
6. **参数的取值范围**：不传（空面板）或部分/全部四格有实现；**传 null 会在读格子时崩**（`capabilities.fridgeInventory` 对 null 取属性直接 TypeError）——调用方要么不传、要么传对象（TypeScript 类型层面也拦 null，双重保险）。
7. **参数的最终作用**：决定厨师 Agent 的"双手数量"。

### 参数 2：`tools`（函数内部的工作篮子）

1. **名称 + 类型**：`tools`，`DomainTool[]`，函数内局部变量，初始 `[]`。
2. **参数设计原因**：**因为**四个工具的产出要汇总成一个列表返回，**所以**需要收集容器。
3. **参数类型选择原因**：**因为**要显式标注"篮子里只放 DomainTool"（塞错东西编译报错），**所以**声明时带类型标注 `const tools: DomainTool[] = []`——不标注则推成 `never[]`/any[]，push 错误对象查不出来。
4. **参数的传入来源**：函数内部新建。
5. **参数的内部使用逻辑**：四个 if 命中时 push（cleaner 包的版本会一次 push 两个，见 05 文档）；最后整体 return。
6. **参数的取值范围**：0-4 个工具（厨师域四个能力，最多四个工具）。
7. **参数的最终作用**：工具列表的装配容器。

### 参数 3：`provider`（各 if 块内的能力实现局部变量）

1. **名称 + 类型**：`provider`，对应 Provider 接口类型（如 FridgeInventoryProvider），每个 if 块内一个。
2. **参数设计原因**：**因为** execute 回调是异步执行时才调用的（不是 if 里立刻调），**所以**必须把面板格子里的实现"接住"供回调使用。
3. **参数类型选择原因**：**因为** if 判断已经证明格子非空，**所以**存进 const 后类型收窄为具体 Provider 接口（非 undefined）——这是 TS 类型收窄的标准用法（见模块2第 2 步），不存变量直接在回调里用 `capabilities.fridgeInventory.read()` 会报"可能是 undefined"的编译错。
4. **参数的传入来源**：面板对应格子的值。
5. **参数的内部使用逻辑**：被 execute 回调闭包捕获（agent-sdk 03 文档讲过闭包"记住"外部变量的机制），每次工具被 AI 调用时通过它转发到真实实现。
6. **参数的取值范围**：对应接口的合法实现（类型层保证）。
7. **参数的最终作用**：工具与真实本领之间的"对接销钉"。

### 参数 4：`items`（order_groceries 工具的入参字段）

1. **名称 + 类型**：`items`，数组：每件元素是 `{ name: string, quantity: number }`，Zod 校验：数组 `.min(1)`（至少一件）、name `.min(1)`（非空）、quantity `.int().positive()`（正整数）。
2. **参数设计原因**：**因为**下单必须说清买什么买多少，**所以**参数表必须装下整张清单；**因为**模型填单可能手滑（空清单、空名字、零个/负数），**所以**每层都加校验。
3. **参数类型选择原因**：**因为**与 01 文档 GroceryItem 的形状对齐（name/quantity 两件套），**所以** Zod 校验器逐字段照抄接口形状——**接口定形状、Zod 定运行规则，两份必须一致**（Zod 里写的形状才能保证转发给 placeOrder 时类型吻合）。
4. **参数的传入来源**：AI 模型按任务意图填写（从"买两斤西红柿"类话语提炼）。
5. **参数的内部使用逻辑**：校验通过 → execute 解构 → 组装 `{ items, note }` → 转发 placeOrder。
6. **参数的取值范围**：1 到多件、每件 name 非空、quantity 正整数；空数组/空名/非正整数都会在校验层被拒（拒了之后由 defineDomainTool/框架按失败处理，AI 会收到失败信息重填）。
7. **参数的最终作用**：下单动作的核心数据。

### 参数 5：`note`（order_groceries 工具的入参字段）

1. **名称 + 类型**：`note`，字符串（string），可选（`.optional()`）。
2. **参数设计原因**：**因为**下单常有附加交代（放前台、要新鲜的），**所以**留备注格；**因为**不是每次都有，**所以**可选。
3. **参数类型选择原因**：自由文本 → string + optional。
4. **参数的传入来源**：AI 按人类要求填或省略。
5. **参数的内部使用逻辑**：与 items 一起组装进请求转发。
6. **参数的取值范围**：不填或任意字符串。
7. **参数的最终作用**：订单的附加说明。

### 参数 6：`days`（meal_stats 工具的入参字段）

1. **名称 + 类型**：`days`，数字（number），Zod 校验：`.int().positive().max(365).default(7)`。
2. **参数设计原因**：**因为**统计必须带范围，**所以**要有这个参数；**因为**人类问"最近吃得怎么样"通常默认指一周，**所以**默认 7——AI 没填也能给出合理结果（**default 的意义**：校验器自动补 7，AI 不需要每次都想"填几天"）。
3. **参数类型选择原因**：**因为**天数要参与聚合运算、要比较上限，**所以**必须 number；`.int().positive()` 拦掉"0.5 天""-3 天"这类无意义值；`.max(365)` 拦掉"查十年"——统计粒度太粗没意义还拖垮宿主（**365 是工程拍板的上限**，要改应连宿主实现一起评估）。
4. **参数的传入来源**：AI 填（不填自动 7）。
5. **参数的内部使用逻辑**：校验补全 → execute 解构 → 转发 `provider.read(days)`。
6. **参数的取值范围**：1-365 的整数，缺省 7。
7. **参数的最终作用**：饮食统计的时间窗。

### 参数 7：无参数工具的"空参数表"（fridge_inventory 与 kitchen_safety_check 的 inputSchema）

1. **名称 + 类型**：`z.object({})`——一个**空对象校验器**（不是"没有校验器"）。
2. **参数设计原因**：**因为**查库存、查安全是"只查不管"的动作，不需要 AI 提供任何参数；**但**框架注册工具必须有 inputSchema，**所以**给空对象校验器——语义是"AI 必须传一个空对象 `{}`"。
3. **参数类型选择原因**：**为什么用 `z.object({})` 而不是留空/传 undefined**：留空 = 框架不知道参数形状（可能报错或行为不明）；空对象校验器 = 明确告诉 AI"这个工具没有参数可填"——**防止模型自作聪明编参数**。
4. **参数的传入来源**：写死在工具定义里。
5. **参数的内部使用逻辑**：框架按它校验 AI 的调用（AI 传 `{}` 通过，传别的字段会被丢掉/拒绝）。
6. **参数的取值范围**：仅空对象。
7. **参数的最终作用**：把"无参工具"表达得清清楚楚。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、四个 if 守卫——整个文件存在的意义，为什么一个都不能少

**因为**"没注入能力就不注册工具"是工程红线（总览红线 4、README"没有注入的能力不会注册工具"），**所以**每个工具的注册都被 if 包住。**如果删掉某个 if**（比如无条件注册 order_groceries）：

- 没配生鲜平台的宿主那里，AI 会看到"能下单"的工具并真去调用 → execute 里 provider 是 undefined → `provider.placeOrder` 直接 TypeError → 虽然会被 defineDomainTool 兜底成失败 JSON，但**模型已经相信"我有下单能力"**，之后还会反复尝试——浪费推理、误导用户；
- 更糟的是 index.ts 的 configured 播报与工具列表将不再一致（说明书说"无"，工具列表却有四个）——**壳与手的口径分裂**。

### 2、`const provider = capabilities.fridgeInventory` 这一步"多余的赋值"——为什么不是多此一举

**因为** execute 是**回调**：if 判断发生在注册时刻，而 provider.read() 发生在"未来某次 AI 调用"时刻，两处的类型收窄状态不同——if 里的类型收窄"不会跟着闭包走"，**所以**必须把已收窄的值存进 const（const 的类型固定不变），回调里用 const 才编译通过。**这是 TypeScript 严格模式的硬要求**：不存变量，`provider.read()` 处报"可能为 undefined"，**编译都过不去**。

### 3、execute 的解构转发（`({ items, note }) => provider.placeOrder({ items, note })`）——为什么不是原样透传 input

**因为** AI 填的参数经过校验后形状是"平的"（items/note 平铺），而 placeOrder 合同要求一个 `GroceryOrderRequest` 对象；**所以**要在 execute 里**重新组装**一次（解构 + 重组），保证转发给宿主的实参严格符合 01 文档的合同——**类型层不检查"Zod 输出是否等于接口入参"**，这一步组装就是人肉保证的一致性（写错字段名这里编译期就能查出来，因为对象字面量会被对照接口检查）。

### 4、days 的 `.default(7)`——为什么默认值放在校验器里而不是 execute 里

**因为** Zod 的 default 在**校验阶段**就补值：补完之后 execute 拿到的 days 一定有值，解构 `({ days })` 类型上就是"必有 number"——**如果**把默认逻辑写在 execute 里（`days ?? 7`），类型系统不知道你兜过底，多一层防御还多一处逻辑；放校验器里 = "数据进门前就整规了"，下游永远干净。

### 5、meal_stats 与 order_groceries 的参数表差异——为什么要各自手写而不是套模板

**因为**四个工具的"参数需求"本质不同：两个只读（无参）、一个带数组清单（多层校验）、一个带单个数字（带默认值和上限）；**而**模板化/配置化会让"特例"塞进配置里变得难读——**直白的四段 if + 各自的 Zod 定义，是可读性和可改性最好的写法**（KISS 原则）。代价是新增能力要手写新块（可接受——新增能力本来就伴随新参数表的设计）。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 编译期：tsc 检查四个工具定义与 Provider 接口/Zod 校验器的类型吻合性；
2. 装配期：createChefAgent 调用本函数 → 四个 if 逐格检查 → 命中的格注册工具 → 返回工具列表（0-4 个）；
3. 工具列表交给 defineSubAgent → 挂到每次新建的厨师 Agent 工作间上；
4. 运行期：AI 判断需要某本领 → 调对应工具 → 参数过 Zod → defineDomainTool 流水线 try/catch 包着执行 execute → execute 闭包里经 provider 转发到宿主真实实现 → 结果按标准 JSON 回给 AI。

### 2、文件在整个工程中不可替代的作用

**它是"能力注入"与"AI 可用"之间的转换器**：注入面板说了算、工具列表不撒谎——工程"没有的能力不注册、不假装"的原则在这里变成了一行行 if。

### 3、运行依赖的环境与前置条件

- 依赖 agent-sdk（defineDomainTool）、zod、本包 capabilities 的类型；
- 前置条件：调用方传入的面板内容决定产出——**空面板完全合法**（返回空数组）；
- 无网络/数据库依赖——它自己不碰真实世界，转发而已。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **"if 守卫 + defineDomainTool 注册"的工具工厂模式**：cleaner 包同款、新领域 Agent 照抄——**只有参数表需要重新设计**；
- **"provider 局部变量固定类型收窄"技巧**：一切"if 判断后进回调"的场景通用；
- **Zod default/max/int/positive 组合**：一切"带范围默认值"的数字参数通用。

### ⚠️ 易错点

1. **新增能力忘了加 if 块**：有能力没工具，AI 永远"暂无数据"——新能力四步联动（总览红线 7）；
2. **Zod 形状与 capabilities 接口形状改了一边忘另一边**：转发组装处编译报错（这是好事——编译器在提醒你同步）；
3. **给无参工具的 inputSchema 传 undefined**：框架行为不明——坚持用 `z.object({})`；
4. **在 execute 里写业务逻辑**：execute 只做转发，业务在宿主 Provider 里——工厂里长业务 = 职责越界，测试和替换都变难。

### 🔍 调试关键点

- **AI 看不到某工具**：先查对应能力格是否有值——没有值就是不注册（设计如此，不是 bug）；
- **工具调用总失败"capability_error"**：看失败 JSON 里的 error 文案，多半是宿主 Provider 实现抛的（本文件只转发）；
- **参数校验失败**：对照工具参数表（本文模块3）逐项检查 AI 填的值——特别是 quantity 必须正整数、days 上限 365。
