# 03 · chef/index.ts 源码白话详解（厨师 Agent 组装）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`index.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agents/chef/src/index.ts`
- 编译产物：`packages/agents/chef/dist/index.js`（`package.json` 的 `main`/`exports` 就指向它——**本包的包入口**）

### 2、文件存在的核心原因

**因为**前面两个文件各备好了一半材料（capabilities.ts = 能力合同、tools.ts = 工具车间），但还没有一个地方**把材料装配成"一名有身份、有规矩、有双手的工人"**；而装配动作（填身份登记表、生成工具、写岗位说明书、调 defineSubAgent）正是使用方唯一需要面对的入口——**所以**必须有这个总装文件：对外暴露一个 `createChefAgent(options)` 工厂，宿主传什么能力就装配出什么样的厨师，什么都不传就是合法的空壳。

**如果没有这个文件，程序会出现的问题：**

- 使用方没有入口可用（总不能让应用自己拼 defineSubAgent 的登记表——那就把 SDK 的组装负担转嫁给了每个应用）；
- 厨师的身份（id=chef、领域、规矩）没有统一出处，管家花名册、任务路由、记忆命名空间全都失去依据；
- 包不成立（package.json 的入口指向空）。

### 3、文件的整体定位

这个文件**专门负责"厨师的出生"**：一张登记表（defineSubAgent 的 spec）+ 一个出生工厂（createChefAgent）+ 一个出厂默认品（空壳 chef）。它是三个文件里的"门面"，也是**新子 Agent 接入的最佳参考样例**（docs/SUBAGENT-DEV-GUIDE.md 的对接规范就是照这个结构讲的）。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- `@meimaohouse/agent-sdk`：`defineSubAgent`（组装线）、`SubAgent`（成品类型）、`Memory`/`ModelInstance`（选项类型）；
- `./capabilities.js`：`ChefCapabilities` 类型（选项里的能力面板）；
- `./tools.js`：`createChefTools`（工具车间）。

**谁来调用它（下游）：**

- `apps/butler-web/src/agents.ts`：`import chef from '@meimaohouse/chef-agent'`（**默认导出的空壳**）→ 放进 agents 数组交给管家注册；
- 想配真实能力的宿主：`createChefAgent({ capabilities, model, memory })`；
- 测试代码：可注入假能力/假模型。

**一句话：厨师的出生证明 + 户口本都在这里，应用只跟这一个文件打交道。**

## 模块2：文件内核心定义与核心函数超详细说明

### 核心定义 1：文件头的两组 `export *` 转发（对外完整交付）

1. **名称**：第 10-11 行：`export * from './capabilities.js'` 和 `export * from './tools.js'`。
2. **设计的根本原因**：**因为**外部（比如测试）可能需要直接引用厨房域的类型（ChefCapabilities）或直调工具工厂（createChefTools），**所以**包入口把两个内部文件的导出全部转发出去——外部只需要认包名，不用知道内部文件划分。
3. **语法写法的原因**：与 agent-sdk 06 文档同款——`export *` 全量转发 + **NodeNext 规范强制写 `.js` 后缀**（不写编译报错）。
4. **内部逻辑分步讲解**：加载本文件时依次转发两份导出集合。
5. **触发条件**：任何 `import ... from '@meimaohouse/chef-agent'`。
6. **最终作用**：包的完整 API 面暴露齐全（类型 + 工厂 + 转发来的合同/车间）。
7. **使用场景**：宿主引用类型、测试直调车间。
8. **缺陷/注意事项**：转发是全量的——capabilities/tools 里不该暴露的东西别加 export（同 agent-sdk 06 文档的注意事项）。

### 核心定义 2：`ChefAgentOptions`（出生工厂的选项单）

1. **名称**：`ChefAgentOptions`，接口，3 个可选字段：`capabilities?`、`model?`、`memory?`。
2. **设计的根本原因**：**因为** createChefAgent 需要一个"装配选项"的形状：配什么能力、用什么大脑、要不要记性——三项都可选（都有合理默认：不配能力=空壳、不给模型=全局配置兜底、不给记忆=没有记忆工具），**所以**定义这张选项单。
3. **语法写法的原因**：**因为**TypeScript 接口 + 全可选字段（`?`）正好表达"都可以不填"，**所以**这样写——`createChefAgent()` 空参合法的类型基础就在这。
4. **内部逻辑分步讲解**：capabilities 面板（01 文档）；model 模型实例（agent-sdk 04 文档的注入通道）；memory 记忆实现（agent-sdk 03 文档的接口）。
5. **触发条件**：不运行；createChefAgent 的入参类型。
6. **最终作用**：宿主装配厨师的全部可调项收敛为一个对象。
7. **使用场景**：README 示例、apps 装配、测试注入。
8. **缺陷/注意事项**：三个选项的默认行为各不同（空壳/全局模型/无记忆）——使用者要清楚"不填 ≠ 没影响"，见模块3各字段的"不填会怎样"。

### 核心函数：`createChefAgent(options)`（出生工厂）

1. **函数名称**：`createChefAgent`，入参 `options: ChefAgentOptions = {}`，返回 `SubAgent`（agent-sdk 05 文档的成品规格）。
2. **函数设计的根本原因**：**因为**"造工具 → 数能力 → 填登记表 → 交 defineSubAgent"是一条固定的出生流程，**而**每个宿主只该关心"我传了什么"而不是"内部怎么组装"，**所以**封装成工厂——这是领域包对 SDK 组装线的"二次封装"：SDK 的 defineSubAgent 管"怎么组装"，本函数管"厨师是什么"。
3. **函数语法写法的原因**：
   - **因为**整个装配是同步的（defineSubAgent 懒加载设计——不创建模型不实例化 Agent，见 agent-sdk 05 文档），**所以**本函数也是同步的；
   - **因为**空参调用是主流（默认导出就这么用），**所以**参数默认值 `= {}`；
   - **因为**返回值要能直接交给管家注册表，**所以**类型精确为 `SubAgent`。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：`const tools = createChefTools(options.capabilities)`——先按面板发工具（02 文档：配几格发几个，空面板发零个）；
   - 第 2 步：`const configured = [ capabilities?.fridgeInventory ? '冰箱库存' : '', ..., ].filter(Boolean)`——**能力现状播报**：四格逐个检查，配了的格子写出人话名字（"冰箱库存"），没配的写空串，最后 `filter(Boolean)` 把空串全部筛掉——**为什么这么写**：用"空串占位 + 最后过滤"代替"动态 push"，四个能力一行看全（对照表式写法），加新能力时照着加一行即可，不会漏；`capabilities?.` 的问号是可选链——options.capabilities 本身可选（没传面板时不会崩，整个表达式变 undefined → 三元走 '' 分支）；
   - 第 3 步：`return defineSubAgent({...})`——填登记表（下面第 4 步拆）；
   - 第 4 步（登记表逐项）：`id: 'chef'`（全工程身份，**写死**——厨师的 id 不该由调用方决定，否则管家路由会乱）；`name: '厨师'`；`domain: '厨房域'`；`description`（能力自述：掌管什么 + 四类典型任务——**管家派活就靠这段**）；`systemPrompt`（岗位说明书模板字符串：工作范围四条 + **当前可用能力插值** `${configured.length > 0 ? configured.join('、') : '无'}` + 行为准则四条——详见模块4第 2 条）；`tools`（第 1 步的产出）；`model: options.model`（不传则 undefined → defineSubAgent 内部 getModel 兜底）；`memory: options.memory`（不传 = 无记忆工具、说明书无记忆条款）。
5. **函数的触发条件**：应用装配阶段（web 应用导入默认导出时已执行一次；配能力的宿主在创建时执行）。
6. **函数的最终作用**：产出一个身份明确、工具与能力严格一致、岗位说明书自带"能力现状播报"的厨师 Agent。
7. **函数的使用场景**：默认导出（空壳）、宿主配能力、测试注入。
8. **函数的缺陷/注意事项**：每次调用都产出**新的** SubAgent 实例——同一应用重复调用会产生多个 chef（管家注册表 id 撞车），**一个进程一份**（默认导出已经保证了主流场景的正确性）。

### 核心定义 3：默认导出 `export const chef = createChefAgent()` + `export default chef`（出厂空壳）

1. **名称**：`chef`（常量）+ 默认导出。
2. **设计的根本原因**：**因为**"开箱即用"必须是零配置的——应用 `import chef from '@meimaohouse/chef-agent'` 一行就能把厨师挂进管家（apps/butler-web/src/agents.ts 就是这么干的），**而**零配置意味着零能力（没有真实本领可注入），**所以**默认导出必须是空壳：能对话、能如实回答"厨房能力未配置"（status=unavailable + error_code=capability_not_configured），**绝不内置模拟数据**（README 核心原则 4 + 注释"默认导出空壳 Agent，供应用层直接装配"）。
3. **语法写法的原因**：**因为**模块的默认导出语法（`export default`）让 import 方可以不写花括号直接起名，**所以**既导出常量又默认导出——`import chef from ...`（用空壳）和 `import { createChefAgent } from ...`（配能力）两条路都顺。
4. **内部逻辑分步讲解**：模块加载时执行 `createChefAgent()`（空参）→ 空面板 → 零工具 → configured 为空 → 说明书里"当前可用能力：无" → 空壳成品。
5. **触发条件**：任何 import 本包的动作（模块顶层立即执行——**这是本包唯一的"加载即运行"代码**）。
6. **最终作用**：零配置可用的厨师空壳，也是"不做假成功"的活样例。
7. **使用场景**：apps/butler-web 的 agents.ts（实际在用）、demo。
8. **缺陷/注意事项**：**它永远没有能力**——想在 Web 应用里配真实能力，不能 import 默认导出，要用 createChefAgent({ capabilities }) 自建再交给管家（apps 的 agents.ts 装配点要改成工厂调用）。

## 模块3：文件内每一个参数超详细说明

### 参数 1：`options`（createChefAgent 的入参）

1. **名称 + 类型**：`options`，`ChefAgentOptions`（三格可选），默认 `{}`。
2. **参数设计原因**：**因为**装配需要的全部可调项（能力/模型/记忆）必须有个统一入口，**所以**打包成 options；默认值让 `createChefAgent()` 直呼合法。
3. **参数类型选择原因**：接口类型 + 默认值的组合（语义见核心定义 2）。
4. **参数的传入来源**：宿主装配代码；默认导出路径传的是 `{}`。
5. **参数的内部使用逻辑**：capabilities 进工具工厂；model/memory 原样透传给登记表（SDK 决定默认行为）。
6. **参数的取值范围**：不传或三格任意组合（capabilities 为面板对象、model 为 ModelInstance、memory 为 Memory 实现）。
7. **参数的最终作用**：厨师"出生配置"的唯一入口。

### 参数 2：`options.capabilities`（能力面板）

1. **名称 + 类型**：`capabilities`，`ChefCapabilities`，可选。
2. **参数设计原因**：**因为**真实本领只能由宿主注入，**所以**面板是能力的唯一通道；不填 = 空壳。
3. **参数类型选择原因**：01 文档的面板类型（四格 Provider）。
4. **参数的传入来源**：宿主实现四类 Provider 后填入。
5. **参数的内部使用逻辑**：两处消费——① createChefTools（决定工具列表）；② configured 播报（决定说明书里的能力清单）——**两处必须永远一致**（都读同一格，天然一致）。
6. **参数的取值范围**：不填或四格任意组合。
7. **参数的最终作用**：厨师"会什么"的总开关。

### 参数 3：`options.model`（模型实例）

1. **名称 + 类型**：`model`，`ModelInstance`，可选。
2. **参数设计原因**：**因为**个别场景要给厨师单独换脑（便宜小模型/测试假脑），**所以**留这个格。
3. **参数类型选择原因**：agent-sdk 的 ModelInstance（框架认的模型类型）。
4. **参数的传入来源**：宿主/测试。
5. **参数的内部使用逻辑**：透传给登记表的 model 字段 → defineSubAgent 里 `spec.model ?? getModel()` 兜底（**不填的后果**：不是报错，而是走全局配置——入口没 configureModel 时才会在"开工作间"时报 ModelNotConfiguredError）。
6. **参数的取值范围**：不填或合法模型实例。
7. **参数的最终作用**：厨师的大脑个性化通道。

### 参数 4：`options.memory`（记忆实现）

1. **名称 + 类型**：`memory`，`Memory`，可选。
2. **参数设计原因**：**因为**厨师需要记跨任务的账（库存快照、主人饮食偏好），**所以**留记忆格；**生产环境**按 docs/DATABASE.md 的说法注入 SQLite 版（createSqliteMemory）。
3. **参数类型选择原因**：agent-sdk 的 Memory 接口（只认标准不认牌子）。
4. **参数的传入来源**：宿主（createMemory/createSqliteMemory 的产物）。
5. **参数的内部使用逻辑**：透传给登记表 → SDK 内部：有 memory 则追加 4 个记忆工具 + 说明书加记忆条款（agent-sdk 05 文档核心函数 1 第 2 步、核心函数 5 条件条款）。
6. **参数的取值范围**：不填或 Memory 实现。
7. **参数的最终作用**：厨师的"记性"开关。

### 参数 5：`tools`（函数内局部变量——工具列表）

1. **名称 + 类型**：`tools`，`DomainTool[]`（createChefTools 的返回）。
2. **参数设计原因**：**因为**登记表的 tools 字段要用，**所以**先接住车间产出。
3. **参数类型选择原因**：车间返回类型的自然承接。
4. **参数的传入来源**：createChefTools(options.capabilities)。
5. **参数的内部使用逻辑**：唯一消费点——登记表 `tools` 字段。
6. **参数的取值范围**：0-4 个工具。
7. **参数的最终作用**：厨师的双手清单。

### 参数 6：`configured`（函数内局部变量——能力现状播报数组）

1. **名称 + 类型**：`configured`，字符串数组（`string[]`），元素是"冰箱库存/食材采购/厨房安全/饮食统计"中人话名字的子集。
2. **参数设计原因**：**因为**岗位说明书必须告诉模型"你此刻真的会什么"——**模型的行为完全依赖这份播报**（说"无"它就老实回 unavailable），**所以**要有这个数组把面板翻译成人话。
3. **参数类型选择原因**：**因为**要 `filter(Boolean)` 过滤和 `join('、')` 拼接，**所以**用字符串数组。
4. **参数的传入来源**：函数内从 options.capabilities 四格现算。
5. **参数的内部使用逻辑**：唯一消费点——systemPrompt 的插值 `${configured.length > 0 ? configured.join('、') : '无'}`。
6. **参数的取值范围**：0-4 个人话名字（空数组时插值成"无"）。
7. **参数的最终作用**：模型自我认知的校准器——**它是"壳与手口径一致"的可见面**。

### 参数 7：登记表 spec 的固定字段（id/name/domain/description/systemPrompt）

1. **名称 + 类型**：全部字符串（写死在工厂里）。
2. **参数设计原因**：
   - `id: 'chef'`：全工程身份（任务编号/domain/记忆命名空间/管家工具名的根），**写死是刻意的**——id 属于"产品的身份证"，不该让调用方改；
   - `name: '厨师'` / `domain: '厨房域'`：人设与门牌（SDK 的说明书和工具描述要用）；
   - `description`：给管家的派活广告（"掌管厨房域：冰箱库存与食材新鲜度、食材采购、厨房安全检查、剩菜处理、饮食数据统计与饮食控制建议"——范围 + 意图清单式写法）；
   - `systemPrompt`：岗位说明书（工作范围 + 能力播报 + 行为准则）。
3. **参数类型选择原因**：都是自然语言文本 → string；id 额外受 SDK 正则校验（小写字母开头）。
4. **参数的传入来源**：本文件写死（这是领域包的"内容工作"，不是参数）。
5. **参数的内部使用逻辑**：整体交给 defineSubAgent 验表、组装（agent-sdk 05 文档）。
6. **参数的取值范围**：固定值；修改规则见模块6。
7. **参数的最终作用**：厨师身份、形象、规矩的全部内容来源。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、`configured` 的"占位 + 过滤"写法——为什么不用 if/push

**因为**四个能力的检查逻辑完全同构（"配了写名字，没配写空串"），**而**"一行一格"的对照式写法让四格状态一眼看全、加第五格就是加一行；**所以**用数组字面量先放占位空串、末尾 `filter(Boolean)` 统一筛掉空串（空串在 JS 里是假值，Boolean 过滤正好）。**如果**换成 if/push：五行判断 + 五行 push，代码翻倍且对照感消失——两种写法功能等价，选可读性好的。

### 2、systemPrompt 里的能力插值——为什么说明书要"动态"而不是写死

**因为**同一个包在不同宿主手里能力不同（有的配了冰箱、有的全空），**而**模型只会照说明书办事：说明书说"你有冰箱库存能力"，实际没配，模型就会硬答或瞎调——**所以**说明书里的能力清单必须由代码在装配时算出来插进去：配了写名字、没配写"无"。**这是"壳知道现状"机制的本体**，与工具列表（同源数据）永远一致。

### 3、systemPrompt 行为准则四条——为什么一条都不能少

- "只能根据已注册工具返回的真实数据作答，禁止编造库存、订单、传感器状态或饮食记录"——**不做假成功的模型层执行令**；
- "所需能力没有对应工具时返回 status=unavailable 并设 error_code=capability_not_configured"——与 agent-sdk 协议的 5 状态对齐，且错误码给机器读（管家能自动化处理）；
- "需要人类拍板的返回 status=needs_human"——大额采购、上门服务这类事的正确出路；
- "需要其他领域协作时写入 suggestions，由管家转派"——平级不互聊架构的协作通道。

**删任何一条的后果**：第一条没了 → 模型可能编库存（最严重的事故）；第二条没了 → 模型可能用别的方式表达"没能力"（协议外的自由发挥，管家没法可靠处理）；第三条没了 → 该问人的事被擅自执行；第四条没了 → 跨域协作断路。**这四条是 chef/cleaner/未来所有子 Agent 的公共纪律**，与 docs/SUBAGENT-DEV-GUIDE.md 的规范同源。

### 4、`model: options.model` 原样透传（不传 undefined）——为什么不在工厂里兜底 getModel

**因为** getModel 在未配置时会**抛错**——如果工厂里强行取模型，"只想先声明一个空壳"的调用（默认导出！）都会炸，**而**默认导出在模块加载时就要执行；**所以**工厂层只透传，把"要不要解析模型"推迟到 SDK 内部（defineSubAgent 的懒加载：开工作间才 getModel）——**这就是默认导出能安全存在的全部原因**。

### 5、`export const chef = createChefAgent()` 写在模块顶层——为什么敢在加载时就执行

**因为**整条出生流程是纯同步、无副作用的（不连网、不建模型实例——工具工厂只 if 判断、defineSubAgent 只验表存闭包），**所以**加载即执行安全。**如果**装配里有异步动作（比如早期设计若在工厂里 getModel），默认导出就得改成 async 函数，apps 那边一行 import 变成 await 调用——SDK 的懒加载设计让"一行 import"得以保持。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 应用 import 本包 → Node 加载 dist/index.js → 转发行执行（capabilities/tools 导出并集）→ 顶层执行 `createChefAgent()`：
   - createChefTools(空面板) → 零工具；
   - configured 算出空数组 → 说明书插值"当前可用能力：无"；
   - defineSubAgent 验表（id 过正则等）→ 返回空壳成品 → 赋给 chef 并默认导出；
2. 应用把 chef 交给管家 → 管家调 `toButlerTool()` → 注册为 `subagent_chef` 工具；
3. 运行期：管家派活 → 信封进来 → SDK 开新工作间（此刻才取模型/挂工具/拼说明书）→ 厨师按 intent 干活：
   - 有工具的本领 → 调工具拿真实数据；
   - 没工具的本领 → 按准则回 unavailable + capability_not_configured；
4. 结果信封回管家 → 转述人类。
5. **配了能力的宿主**：不走默认导出，改用 `createChefAgent({ capabilities: {...}, memory: ... })`，流程同上但工具齐全、播报写实。

### 2、文件在整个工程中不可替代的作用

**它是厨师的出生地与包门面**：身份固定、能力现状如实播报、空壳开箱即用、真实能力按需注入——"壳 + 注入"模式的完整示范，也是所有未来子 Agent 的抄写模板。

### 3、运行依赖的环境与前置条件

- 依赖 agent-sdk（编译期 + 运行期）与 zod（工具车间内部）；
- 前置条件：作为 Agent 使用时入口需已 configureModel（或 options.model 注入）——但**模块加载本身零前置**（空壳出生不需要模型）；
- 编译前置：agent-sdk 与 zod 已安装。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **整个文件就是"新子 Agent 模板"**：新领域照抄结构，替换 id/name/domain/description/systemPrompt 文案与能力面板——流程一行不用改；
- **configured 播报 + 说明书插值**：一切"能力可变"的 Agent 都该有这份"自我认知校准"。

### ⚠️ 易错点

1. **以为默认导出会自动带上注入的能力**：默认导出永远空壳——配能力必须用工厂自建并交给管家；
2. **改 id 但没同步管家侧**：路由、历史数据、记忆键全断（总览红线 1）；
3. **configured 名字与 capabilities 格子错位**（加能力忘了加播报行）：模型"知道"的工具集与说明书播报不一致，行为困惑——两处读同一格所以结构上不会错位，**但手工维护的播报行会漏**，加能力时四步联动；
4. **在工厂里塞异步/副作用**：会破坏"加载即执行"的默认导出安全性。

### 🔍 调试关键点

- **厨师什么任务都回 unavailable**：查是不是在用默认导出空壳（无能力）——正确现象，配能力走工厂；
- **管家从不派活给厨师**：查 description 是否被改得含糊（agent-sdk 05 文档模块6）；
- **模型行为与工具集不符**：查 systemPrompt 的播报与实际工具列表是否一致（应一致，不一致说明有人手工改了模板字符串）。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| `id: 'chef'` | 🚫 不能改 | 全链路身份（总览红线 1） |
| 行为准则四条 | 🚫 不能删改 | 与协议/规范/工程原则三方对齐（见模块4第 3 条） |
