# agents-白话详解 · 总览与阅读指南（chef + cleaner 两个子 Agent 包）

> 本文件夹是 `packages/agents/chef/src` 和 `packages/agents/cleaner/src` 两个目录下共 6 个源文件的零基础白话详解。
> 每个源文件一份独立文档，与《agent-sdk-白话详解》配套阅读（那边讲"零件箱"，这边讲"用零件造出来的两个工人"）。

---

## 一、先搞懂这两个包在整个工程里扮演什么角色

**因为**整个工程是"一个总协调管家 + 一群平级领域子 Agent"的架构（见 agent-sdk 总览的第二节），**所以**管家之外必须有真正干活的"工人"。这两个包就是最先造出来的两名工人：

```
人类 👤
   │
   ▼
大管家（butler-core）
   │            │
   ▼            ▼
厨师 Agent      清洁工 Agent        ← 就是这两个包
(chef)          (cleaner)
 厨房域          清洁域
```

- **厨师（chef，包名 `@meimaohouse/chef-agent`）**：管厨房域——冰箱库存、食材采购、厨房安全、饮食统计。
- **清洁工（cleaner，包名 `@meimaohouse/cleaner-agent`）**：管清洁域——房间清洁、扫地机器人、洗衣、上门服务预约。

**它们的共同出身**：两个包都是拿 `agent-sdk` 的零件（`defineSubAgent`、`defineDomainTool`）组装出来的，组装方式一模一样——**所以这两个包互为镜像**，读懂一个，另一个就是换了个领域内容而已。它们也是工程给"以后新增子 Agent"提供的标准样板。

## 二、必须先懂的核心设计：「壳 + 能力注入」

**因为**框架方（写这两个包的人）不知道你家冰箱是什么牌子、你家用的哪个生鲜平台、清洁机器人是谁家的——真实世界五花八门，**所以**这两个包被刻意做成"**空壳**"：

1. **壳（壳的部分）**：Agent 的身份（id/名字/领域）、能力自述（description）、岗位规矩（systemPrompt）——这些是框架方能确定的，直接写死在包里；
2. **能力（注入的部分）**：真实本领（真连冰箱传感器、真连生鲜平台）只在**接口文件里定标准**（"你必须会 read()"），**真实现由宿主（使用框架的应用）在创建 Agent 时注入**；
3. **没注入就没工具**：工具工厂（tools.ts）逐个检查能力在不在，在才注册对应工具——**没有的能力绝不假装有**；
4. **壳知道现状**：index.ts 会把"当前配置了哪些能力"用大白话写进岗位说明书（"当前可用能力：无"），Agent 被问到没配置的能力时，必须老老实实回 `unavailable`（状态未配置），不许编。

**这就是工程 README 里"不做假成功"原则在子 Agent 层的完整落地**：空壳默认导出（`export const chef = createChefAgent()`）就是零能力空壳——能正常对话、能如实说"这个我干不了"。

## 四、上下游关系（谁依赖谁、谁在用它们）

```
它们依赖（上游）：
  @meimaohouse/agent-sdk（defineSubAgent、defineDomainTool、Memory/ModelInstance/SubAgent 类型）
  zod（工具入参校验器）

谁在用它们（下游）：
  apps/butler-web/src/agents.ts：
    import chef from '@meimaohouse/chef-agent'      ← 注意：import 的是"默认导出的空壳"
    import cleaner from '@meimaohouse/cleaner-agent'
    export const agents: SubAgent[] = [chef, cleaner]  ← 交给管家注册
  docs/DATABASE.md 也记载：工厂支持 memory 选项注入 SQLite 记忆；
    能力未配置时任务返回 unavailable 并落库留痕。
```

**想配真实能力时的正规姿势**（README 原样示例）：不 import 默认导出，而是调工厂并传能力——`createChefAgent({ capabilities: { fridgeInventory: 我的冰箱实现, ... } })`。

## 五、开始前必须懂的大白话概念（本文件夹新增的部分）

其余概念（Agent、模型、工具、信封、Zod、SDK 等）见 agent-sdk 总览第四节，这里只补这两个包特有的：

1. **能力接口（Provider 接口）**：一份"宿主必须会什么"的清单。比如 `FridgeInventoryProvider` 只有一条：必须会 `read()`，一查就给出冰箱库存。宿主照单实现，就能被塞进 Agent 当"本领"。
2. **能力注入（capabilities 选项）**：创建 Agent 时把真实实现当参数传进去的动作——相当于"上岗前发工具"。
3. **工具工厂（createXxxTools）**：一个"按需发工具"的车间——检查宿主发了哪些本领，发一个就包装一个 AI 工具，没发的不造。
4. **空壳 Agent（默认导出）**：不带任何真实本领的 Agent 成品——能接任务、能如实说"干不了"，绝不编数据。它是演示和兜底两用的出厂形态。
5. **能力现状播报（configured 数组）**：组装 Agent 时把"哪些能力已配置"翻译成人话（如"冰箱库存、食材采购"）写进岗位说明书，让 Agent 自己知道"我此刻会什么、不会什么"。

## 六、全局修改红线与易错点（改这两个包前必看）

> ⚠️ **高亮警告区**：各文件的细项在各自文档的模块6，这里是从 6 个文件提炼的全局红线。

1. **两个包的 `id`（chef / cleaner）不能改**：它们是任务信封的 domain 值、任务编号第一段、记忆命名空间、管家工具名（`subagent_chef`）——改一个字，历史任务记录、记忆数据、管家提示词全部对不上号。
2. **systemPrompt 里的行为准则不能删改**（"禁止编造数据 / unavailable 时设 error_code=capability_not_configured / needs_human / suggestions 转派"）：这四条是与 agent-sdk 协议、工程"不做假成功"原则、docs/SUBAGENT-DEV-GUIDE.md 开发规范三方对齐的约定，改了 = 全链路口径乱。
3. **能力接口的函数签名不能改**（如 `read()`、`placeOrder(request)`）：工具工厂按这些签名转发调用，改签名 = 工具工厂和宿主实现两头都得跟着改，且是静默的运行时错误风险。
4. **"没注入能力就不注册工具"的 if 结构不能改成"注册一个报错版工具"**：那会让管家模型误以为能力存在而频繁派活，Agent 只能反复回 unavailable——派活准确率和上下文预算都被浪费。
5. **默认导出（`export default createXxxAgent()`）不能改成"带示例能力的默认导出"**：默认导出必须保持空壳——往里塞模拟实现就违反"仓库不内置模拟数据"的工程红线（README 核心设计原则第 4 条）。
6. **改任何文件后要重新编译对应包**（包目录下 `npm run build`）：应用引用的是 `dist` 产物，忘编译 = "改了没生效"的灵异现象。
7. **新加能力时的完整链路**：capabilities.ts 加接口 + 数据结构 → tools.ts 加 if 块注册工具 → index.ts 的 configured 数组加一行展示名 → systemPrompt 的工作范围按需补充——四处只改一处会出现"有工具但 Agent 不知道/知道但没有工具"的错位。

## 七、本文件夹文档的通用结构
