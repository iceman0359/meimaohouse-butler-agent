# 01 · chef/capabilities.ts 源码白话详解（厨房域能力接口）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`capabilities.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agents/chef/src/capabilities.ts`
- 编译产物：`packages/agents/chef/dist/capabilities.js`（经 index.ts 的 `export *` 转发，外部从包名导入）
- **特殊身份**：这是一个**纯类型文件**——全部内容都是 TypeScript 的 interface（接口）和 type（类型别名），**编译后不产生任何可执行代码**，只给编译器和写代码的人看。

### 2、文件存在的核心原因

**因为**厨师 Agent 需要四类真实本领——查冰箱库存、下采购订单、查厨房安全、读饮食统计——而框架方不知道这些本领的真实来源（你家冰箱什么牌子？用的哪个生鲜平台？），**所以**必须有一份"标准合同"：把每类本领**数据长什么样**（比如库存单必须有什么字段）和**宿主必须会什么动作**（比如必须会 read()）全部写成类型契约。

文件头注释原话："这里只定义宿主需要实现的能力，不包含任何模拟数据或平台实现。真实实现可以由传感器、摄像头、生鲜平台、饮食记录系统或测试替身注入。"

**如果没有这个文件，程序会出现的问题：**

- 宿主注入真实能力时没有标准可依，各写各的，工具工厂拿到的东西形状对不上，一调用就崩；
- 数据结构没有契约，AI 拿到的库存单/订单回执字段五花八门，没法稳定理解；
- "能力可插拔"无从谈起——没有接口，就没法"只认标准不认牌子"。

### 3、文件的整体定位

这个文件**专门负责"厨房域的类型契约"**：一半是**数据结构**（8 个：库存单、食材项、订单请求、订单回执、安全等级/条目/报告、饮食统计），一半是**能力标准**（4 个 Provider 接口）+ **能力汇总包**（ChefCapabilities）。它不干活、不连网、不存数据——它是"图纸"。

### 4、文件的依赖关系

**它需要调用谁（上游）：** 谁都不依赖——零 import，纯自包含的类型定义（这是刻意的：类型契约层越干净，越不容易被实现细节污染）。

**谁来调用它（下游）：**

- `tools.ts`：工具工厂按 `ChefCapabilities` 检查能力、按数据结构类型转发调用（第 3 行 `import type { ChefCapabilities }`）；
- `index.ts`：组装 Agent 时（通过 `export * from './capabilities.js'` 转发 + ChefAgentOptions.capabilities 的类型）；
- **宿主应用**：实现 Provider 接口、构造数据结构时引用。

**一句话：它是厨师域的"字典 + 合同"，tools 和 index 都按它的词汇表说话。**

## 模块2：文件内核心定义逐个超详细说明

> 本文件没有函数，15 个核心定义（8 个数据结构 + 4 个能力接口 + 1 个能力包 + 1 个类型别名 + 1 个联合状态）逐个拆解。数据结构按"组合关系"分组讲。

### 核心定义 1：`FridgeItem`（一种食材的档案）

1. **名称**：`FridgeItem`，接口。
2. **设计的根本原因**：**因为**冰箱里不是"一堆东西"，而是"每样东西各有名字、数量、单位、保质期"，AI 要回答"鸡蛋还有几个、快过期吗"，就得拿到**逐样**的结构化档案，**所以**定义"一种食材"的标准形状。
3. **语法写法的原因**：**因为** TypeScript 的 interface 用 `字段名: 类型` 声明形状、用 `?` 标可选，**所以** name/quantity/unit 必填（没名字没数量的食材记录毫无意义），expiresInDays/note 可选（有的食材没必要记保质期、备注是锦上添花）。
4. **内部逻辑分步讲解**（5 个字段含义见模块3）：name 是什么、quantity 有多少、unit 用什么单位计（个/盒/克）、expiresInDays 还能放几天、note 补充说明。
5. **触发条件**：不运行；作为 `FridgeInventory.items` 数组的元素类型被引用。
6. **最终作用**：让"冰箱里的一种食材"在全工程有一个统一说法。
7. **使用场景**：宿主实现 `FridgeInventoryProvider.read()` 时构造；AI 读工具返回的 JSON 时按它理解。
8. **缺陷/注意事项**：quantity 是纯数字——单位靠 unit 字段配套（"0.5"+"kg"），**宿主别把单位偷偷写进 quantity**（如 "500g" 当字符串塞进来是类型错误）。

### 核心定义 2：`FridgeInventory`（一整份冰箱库存单）

1. **名称**：`FridgeInventory`，接口。
2. **设计的根本原因**：**因为**"查库存"的答案必须包含**两样东西**：清单内容 + **什么时候查的**——没有查证时间，AI 分不清这是刚查的还是昨天的旧数据（食材是最讲究时效的东西），**所以**库存单 = 时间戳 + 食材数组。
3. **语法写法的原因**：`checkedAt: string`（ISO 时间字符串——见 agent-sdk 01 文档"JSON 可序列化"约定，时间用字符串不用 Date）；`items: FridgeItem[]`（数组类型表示"零到多份食材"——空冰箱就是空数组，**不能因为没东西就不返回**）。
4. **内部逻辑分步讲解**：两个字段——checkedAt 记"快照时刻"，items 装"全部食材档案"。
5. **触发条件**：不运行；是 `FridgeInventoryProvider.read()` 的返回类型。
6. **最终作用**：工具 fridge_inventory 的返回数据形状，AI"看冰箱"的全部依据。
7. **使用场景**：宿主实现 read()；tools.ts 的 execute 转发；AI 解析库存数据。
8. **缺陷/注意事项**：它是**快照**不是实时流——两次 read 之间冰箱可能被拿东西，AI 引用时要以 checkedAt 为准。

### 核心定义 3：`GroceryItem`（要买的一种商品）

1. **名称**：`GroceryItem`，接口。
2. **设计的根本原因**：**因为**下单的最小单位是"商品名 + 数量"——**故意没有 unit**：生鲜平台通常按自己的售卖规格计（平台说"一份"就是一份），框架方定死单位反而跟平台打架，**所以**比 FridgeItem 精简（名字 + 数量足矣）。
3. **语法写法的原因**：两个字段都必填——没名字买不了，没数量平台没法发货。
4. **内部逻辑分步讲解**：name 商品名；quantity 数量。
5. **触发条件**：不运行；作为 GroceryOrderRequest.items 的元素类型。
6. **最终作用**：下单清单的标准条目。
7. **使用场景**：AI 填 order_groceries 工具入参时按它构造（tools.ts 的 Zod 校验器与它逐字段对应）。
8. **缺陷/注意事项**：数量单位含糊是刻意留白——宿主实现 placeOrder 时应把自己的计量约定写进返回的 message 里让用户可查。

### 核心定义 4：`GroceryOrderRequest`（一张采购订单请求）

1. **名称**：`GroceryOrderRequest`，接口。
2. **设计的根本原因**：**因为**下单动作需要"一次把要买的东西说全"（逐个下单又慢又贵运费），**所以**请求 = 商品数组 + 可选备注。
3. **语法写法的原因**：`items: GroceryItem[]` 必填（空单没有意义，**最小 1 件的限制不在这里卡，而在 tools.ts 的 Zod 校验器里 `.min(1)`**——类型层只管形状，"至少一件"这种规则归运行校验管，分工明确）；`note?` 可选。
4. **内部逻辑分步讲解**：items 要买的全部商品；note 给平台/商家的补充交代。
5. **触发条件**：不运行；是 `GroceryOrderProvider.placeOrder(request)` 的入参类型。
6. **最终作用**：下单动作的"原材料"。
7. **使用场景**：AI 调 order_groceries → tools.ts 校验 → placeOrder 收到。
8. **缺陷/注意事项**：没有"收货地址/支付方式"字段——这些属于宿主平台侧的账户配置，框架不碰（职责分离）。

### 核心定义 5：`GroceryOrder`（一张订单回执）

1. **名称**：`GroceryOrder`，接口。
2. **设计的根本原因**：**因为**下单后 AI 必须能向人类交代"单号、成没成、什么时候到"，**所以**回执必须带这三样 + 可选留言。**特别注意**：status 是三选一（submitted 已提交 / confirmed 已确认 / rejected 已拒绝）——**刻意没有"成功完成"**：生鲜下单的真实世界就是"提交了不等于确认了"，框架不粉饰。
3. **语法写法的原因**：status 用字面量联合类型 `'submitted' | 'confirmed' | 'rejected'`（**因为**这三种状态之外没有合法值，**所以**类型层面就锁死，比 string 安全）；orderId 必填（没单号的回执是废纸）；estimatedDelivery/message 可选。
4. **内部逻辑分步讲解**：orderId 平台单号；status 当前状态；estimatedDelivery 预计送达；message 平台留言（如"鸡蛋缺货已替换"）。
5. **触发条件**：不运行；是 placeOrder 的返回类型。
6. **最终作用**：AI 汇报"买菜下单"结果的数据依据。
7. **使用场景**：tools.ts 转发返回；AI 读后写进结果信封的 summary/detail。
8. **缺陷/注意事项**：status=rejected 时 AI 应该把 message 里的原因转述给人类——宿主实现时 rejected 务必填 message。

### 核心定义 6：`KitchenSafetyLevel`（安全等级类型别名）

1. **名称**：`KitchenSafetyLevel`，类型别名：`'ok' | 'warning' | 'critical'`。
2. **设计的根本原因**：**因为**安全检查的结论必须是分级的（正常/警告/危急），而且这个等级要被**单个区域**和**整体报告**两处共用，**所以**抽成一个独立类型——两处引用同一个定义，口径永远一致（改等级词表只动一处）。
3. **语法写法的原因**：**因为**三个等级是固定的离散值，**所以**用字面量联合类型（与 agent-sdk 的 TaskPriority 同款思路）；**为什么用 `type` 而不是 interface**：它是一个值集（不是对象形状），type 别名是表达值集的正规语法。
4. **内部逻辑分步讲解**：ok 正常；warning 有隐患要留意；critical 危急要立刻处理。
5. **触发条件**：不运行；被 KitchenSafetyItem.status 和 KitchenSafetyReport.overall 引用。
6. **最终作用**：安全结论的统一刻度。
7. **使用场景**：宿主构造巡检结果；AI 判断"要不要建议人类立刻处理"（critical 显然要）。
8. **缺陷/注意事项**：三个词的语义边界（warning 和 critical 的分界）由宿主的巡检系统决定，框架不管——AI 只认词不认深意。

### 核心定义 7：`KitchenSafetyItem`（一个区域的安全检查条目）

1. **名称**：`KitchenSafetyItem`，接口。
2. **设计的根本原因**：**因为**厨房安全不是一句话（"厨房安全"）能回答的——燃气一个结论、插座一个结论、刀具一个结论，**必须逐区域报告**才能让 AI 说清"哪里有问题"，**所以**定义"一个区域一条"的条目。
3. **语法写法的原因**：area/status 必填（哪个区域 + 什么等级，缺一不可）；note 可选（"燃气软管老化"这类说明）。
4. **内部逻辑分步讲解**：area 区域名；status 该区域等级；note 补充。
5. **触发条件**：不运行；作为 KitchenSafetyReport.items 的元素。
6. **最终作用**：逐区域安全结论的标准载体。
7. **使用场景**：宿主构造报告；AI 逐条转述。
8. **缺陷/注意事项**：area 是自由文本（没有枚举区域表）——宿主应保持区域命名稳定，否则 AI 的前后对比会混乱。

### 核心定义 8：`KitchenSafetyReport`（一整份安全巡检报告）

1. **名称**：`KitchenSafetyReport`，接口。
2. **设计的根本原因**：**因为**除了逐区域条目，还必须有**一个总评**（overall）——管家问"厨房安全吗"，人类要的是一句话结论，逐条念完不是回答；**所以**报告 = 快照时间 + 总评等级 + 区域条目数组。
3. **语法写法的原因**：`overall: KitchenSafetyLevel` 复用核心定义 6（总评和分项用同一套刻度）；checkedAt 与 FridgeInventory.checkedAt 同理（快照时间字符串）。
4. **内部逻辑分步讲解**：checkedAt 何时巡检；overall 总体结论；items 逐区域明细。
5. **触发条件**：不运行；是 `KitchenSafetyProvider.inspect()` 的返回类型。
6. **最终作用**：工具 kitchen_safety_check 的返回数据形状。
7. **使用场景**：宿主实现 inspect()；AI 汇报安全状况。
8. **缺陷/注意事项**：AI 可能被问"瓦斯关了吗"这类单点问题——报告是全量巡检数据，AI 要自己挑相关条目回答，不能整份照念。

### 核心定义 9：`MealStats`（一段时间的饮食统计）

1. **名称**：`MealStats`，接口。
2. **设计的根本原因**：**因为**"最近吃得怎么样"是一个统计问题（N 天内记了多少条、平均热量多少），不是单条记录，**所以**定义统计结果的形状；notes 数组留给"特别提示"（如"外食比例偏高"）。
3. **语法写法的原因**：days/records 必填（统计范围和样本数，是统计的身份证）；averageCaloriesPerDay 可选（**为什么可选**：记录太少或数据不全时算平均没有意义——**宁可不给，不许编**，这正是"不做假成功"在数据结构上的体现）；notes 可选。
4. **内部逻辑分步讲解**：days 统计多少天；records 其间记录条数；averageCaloriesPerDay 日均热量；notes 补充提示。
5. **触发条件**：不运行；是 `MealStatsProvider.read(days)` 的返回类型。
6. **最终作用**：工具 meal_stats 的返回数据形状。
7. **使用场景**：宿主实现 read(days)；AI 做饮食建议时引用。
8. **缺陷/注意事项**：records 为 0 时 AI 应说"暂无饮食记录"而不是硬凑统计——数据结构和系统提示词两层都在防这个。

### 核心定义 10：`FridgeInventoryProvider`（冰箱库存能力的合同）

1. **名称**：`FridgeInventoryProvider`，接口，只有 1 个方法：`read(): Promise<FridgeInventory>`。
2. **设计的根本原因**：**因为**"查库存"这个本领，宿主的实现可能是冰箱传感器、可能是摄像头识别、可能是手工录入系统——**不管底下是什么，对厨师 Agent 来说只需要"一查就出库存单"**，**所以**合同只写一条：必须会 read，读了必须（异步地）给一份 FridgeInventory。
3. **语法写法的原因**：**因为**真实读取要碰硬件/网络（等待），**所以**返回 Promise<FridgeInventory>（异步承诺——与 agent-sdk 的 Memory 接口同款异步设计：接口层声明 Promise，内存/测试实现只是"立刻完成的承诺"，成本为零）；**为什么只有一个方法**：接口最小化——宿主实现成本越低，接入越快。
4. **内部逻辑分步讲解**：一条签名——"read，无入参，异步返回库存单"。
5. **触发条件**：不运行；宿主实现它，tools.ts 检查到它存在才注册 fridge_inventory 工具。
6. **最终作用**：把"查冰箱"变成一个可注入的标准件。
7. **使用场景**：宿主写 `class MyFridge implements FridgeInventoryProvider`，创建 Agent 时传入。
8. **缺陷/注意事项**：read 可能抛异常（传感器掉线）——异常由 defineDomainTool 的兜底统一转成失败结果（agent-sdk 02 文档），宿主无需自己包 try/catch（但错误信息请写人话）。

### 核心定义 11：`GroceryOrderProvider`（采购下单能力的合同）

1. **名称**：`GroceryOrderProvider`，接口，1 个方法：`placeOrder(request: GroceryOrderRequest): Promise<GroceryOrder>`。
2. **设计的根本原因**：**因为**下单是有副作用的真动作（真花钱、真发货），**所以**合同必须把"进什么（订单请求）、出什么（订单回执）"都钉死，宿主平台五花八门（生鲜电商、社区团购），但接口不变。
3. **语法写法的原因**：入参 request 的类型就是核心定义 4、返回类型就是核心定义 5——**合同两端都指向同一份字典**，谁也不能私改形状。
4. **内部逻辑分步讲解**：一条签名——"placeOrder，收一张订单请求，异步给一张回执"。
5. **触发条件**：不运行；注入后由 order_groceries 工具的 execute 转发调用。
6. **最终作用**：把"买菜下单"变成可注入的标准件。
7. **使用场景**：宿主接入真实生鲜平台时实现。
8. **缺陷/注意事项**：**它是全文件唯一"花钱"的方法**——宿主实现务必做额度/确认控制（大额走 needs_human 是 Agent 层的纪律，但宿主侧也该有熔断，双保险）。

### 核心定义 12：`KitchenSafetyProvider`（厨房安全能力的合同）

1. **名称**：`KitchenSafetyProvider`，接口，1 个方法：`inspect(): Promise<KitchenSafetyReport>`。
2. **设计的根本原因**：**因为**安全检查依赖传感器/巡检系统（框架没有），**所以**合同化："会 inspect、给巡检报告"就够格。
3. **语法写法的原因**：无入参（巡检是"查当前"，不需要 AI 传参——查哪、怎么查是巡检系统自己的配置）；返回 Promise<报告>。
4. **内部逻辑分步讲解**：一条签名——"inspect，无入参，异步给整份报告"。
5. **触发条件**：不运行；注入后由 kitchen_safety_check 工具调用。
6. **最终作用**：把"查厨房安全"变成可注入的标准件。
7. **使用场景**：宿主接入燃气/烟感/摄像头巡检系统时实现。
8. **缺陷/注意事项**：安全是高优先级场景——宿主实现应保证 inspect 尽量快、失败时错误信息写清"传感器无响应"之类，便于 AI 转达"需要人工检查"。

### 核心定义 13：`MealStatsProvider`（饮食统计能力的合同）

1. **名称**：`MealStatsProvider`，接口，1 个方法：`read(days: number): Promise<MealStats>`。
2. **设计的根本原因**：**因为**统计天然带"范围"参数（最近 7 天还是 30 天？），**所以**这个合同与前三条不同——**带一个入参**：天数。宿主按天数出统计。
3. **语法写法的原因**：`days: number`（数字——**因为**要做数学运算：按天数聚合、算平均，字符串没法算）；返回 Promise<MealStats>。
4. **内部逻辑分步讲解**：一条签名——"read，收一个天数，异步给统计结果"。
5. **触发条件**：不运行；注入后由 meal_stats 工具调用（AI 传的天数先过 tools.ts 的 Zod 校验：正整数、最多 365、默认 7）。
6. **最终作用**：把"读饮食统计"变成可注入的标准件。
7. **使用场景**：宿主接入饮食记录系统时实现。
8. **缺陷/注意事项**：**365 上限在 tools.ts 校验层**，宿主实现不必重复校验（但校验了也无害）——两层防线各司其职。

### 核心定义 14：`ChefCapabilities`（能力汇总包——宿主的"注入面板"）

1. **名称**：`ChefCapabilities`，接口，4 个可选字段：fridgeInventory?、groceryOrdering?、kitchenSafety?、mealStats?。
2. **设计的根本原因**：**因为**宿主可能只配一部分能力（只接了冰箱、没接生鲜平台），**所以**需要一个"能力面板"：四格开关，配一格亮一格——**它就是 createChefAgent(options.capabilities) 的参数类型**（index.ts 第 27-31 行按它逐格检查）。
3. **语法写法的原因**：**因为**四项全部可选（`?`），**所以**宿主传 `{}`（什么都不配）也合法——这正是"空壳 Agent"的类型基础；每个字段的类型是对应 Provider 接口——**面板格子只认"有合同的实现"**。
4. **内部逻辑分步讲解**：四格各自对应一个能力接口，配了即注入。
5. **触发条件**：不运行；createChefAgent / createChefTools 的入参类型。
6. **最终作用**：宿主注入能力的一站式入口，也是"配了什么亮什么"机制的开关面板。
7. **使用场景**：README 示例 `createChefAgent({ capabilities: {...} })`、apps 的装配代码。
8. **缺陷/注意事项**：**新增第五种能力时**：接口加字段 → tools.ts 加 if 块 → index.ts configured 数组加行 → systemPrompt 工作范围核对——四处联动（见总览红线 7）。

## 模块3：文件内每一个参数超详细说明

> 按接口分组，每个字段一个条目。为避免重复啰嗦，"类型选择原因/来源"等共性在组内首次出现处讲透，后续同类字段讲各自的特殊点。

### 组 1：FridgeItem 的 5 个字段

**字段 1：`name`（食材名，string，必填）**——设计原因：没有名字的食材记录无法回答任何问题；类型原因：名字是自然语言标签；来源：宿主的识别/录入系统；内部使用：AI 直接引用（"鸡蛋还有 6 个"）；取值范围：任意非空字符串（惯例中文或通用食材名，保持宿主侧稳定）；最终作用：库存条目的主键式标识。**选 string 是因为 AI 要能直接读给人类听**——用编码/ID 会让 AI 多一道翻译还容易错。

**字段 2：`quantity`（数量，number，必填）**——设计原因："还有多少"是库存问答的核心；类型原因：**必须 number**——AI 可能要做算术（"6 个够吃几天"），字符串没法算，选错类型这里直接断功能；来源：传感器/识别/录入；内部使用：AI 引用与简单计算；取值范围：≥0 的数（负数是脏数据，宿主侧应拦）；最终作用：库存量的本体。

**字段 3：`unit`（计量单位，string，必填）**——设计原因：数字离开单位没有意义（"6"是个还是盒？）；类型原因：单位是文本标签所以 string；来源：宿主；内部使用：与 quantity 搭配出现（"6 个""500 克"）；取值范围：任意字符串（惯例：个/盒/瓶/克/千克）；最终作用：让数量可被人类正确理解。

**字段 4：`expiresInDays`（剩余保质天数，number，可选）**——设计原因："还能放几天"决定"要不要赶紧吃/买"，是厨房域高频问题；类型原因：天数参与比较（≤3 天算临期），必须 number；来源：保质期推算；内部使用：AI 据此给"先吃这个"建议；取值范围：≥0 整数（不填 = 不追踪该食材的保质期）；最终作用：新鲜度判断的数据支撑。**选"剩余天数"而不是"过期日期"**：天数可以直接比较、无需解析日期，对 AI 更友好。

**字段 5：`note`（备注，string，可选）**——设计原因：有非结构化信息要带（"已开封""放冷冻室了"）；类型原因：自由文本；来源：宿主；内部使用：AI 需要时转述；取值范围：任意字符串；最终作用：结构化字段装不下的补充。

### 组 2：FridgeInventory 的 2 个字段

**字段 6：`checkedAt`（查证时间，string，必填）**——设计原因：食材数据强时效，没有时间戳 AI 无法判断数据新旧，可能拿昨天的库存答今天的问题；类型原因：ISO 8601 字符串（JSON 可序列化约定，见 agent-sdk 01 文档模块4）；来源：宿主生成 `new Date().toISOString()`；内部使用：AI 转述时提"刚才查的/今天上午查的"；取值范围：合法 ISO 时间字符串；最终作用：库存数据的"新鲜度证明"。

**字段 7：`items`（食材数组，FridgeItem[]，必填）**——设计原因：库存的本体是一组食材档案；类型原因：数组——**空冰箱也必须是空数组**（有"查过、没东西"的明确表达），绝不允许宿主返回 null/undefined 表达"空"；来源：宿主组装；内部使用：AI 逐条理解；取值范围：FridgeItem 数组（可为空数组）；最终作用：库存问答的全部素材。

### 组 3：GroceryItem 的 2 个字段

**字段 8：`name`（商品名，string，必填）**——设计原因：平台按名字找商品；类型原因：商品名是文本；来源：**AI 从任务参数里填**（这是本文件唯一"AI 写"的字段之一，经 tools.ts 的 Zod 校验 min(1) 把关）；内部使用：传给 placeOrder；取值范围：非空字符串（太偏门的写法平台可能匹配不到——宿主应在回执 message 里说明）；最终作用：下单标的。

**字段 9：`quantity`（数量，number，必填）**——设计原因：平台要知道买多少；类型原因：数字可比可算；来源：AI 填，Zod 校验 `.int().positive()`（正整数——买 -2 个鸡蛋是笑话，0 个是空手）；内部使用：传给平台；取值范围：正整数；最终作用：购买量。

### 组 4：GroceryOrderRequest 的 2 个字段

**字段 10：`items`（商品清单，GroceryItem[]，必填）**——设计原因：一次下单说全；类型原因：数组（"至少一件"的硬约束在 tools.ts 的 `.min(1)`，类型层只管形状）；来源：AI 构造经校验；内部使用：整包传给 placeOrder；取值范围：至少在运行层保证 ≥1 件；最终作用：订单主体。

**字段 11：`note`（备注，string，可选）**——设计原因：给平台的补充交代（"鸡蛋要新鲜的""放前台"）；类型原因：自由文本；来源：AI 按人类要求填；内部使用：透传平台；取值范围：任意字符串；最终作用：订单的附加说明。

### 组 5：GroceryOrder 的 4 个字段

**字段 12：`orderId`（订单号，string，必填）**——设计原因：人类查单、后续追问"菜到哪了"全靠它；类型原因：平台单号是含字母数字的文本；来源：**平台生成**（宿主透传）；内部使用：AI 写进结果信封 detail 供后续引用；取值范围：平台合法单号；最终作用：订单的身份凭证。

**字段 13：`status`（订单状态，'submitted' | 'confirmed' | 'rejected'，必填）**——设计原因：AI 必须如实转述"提交了"还是"成了"还是"黄了"；类型原因：字面量联合锁死三值（没有"成功完成"——提交≠确认，框架不粉饰）；来源：平台；内部使用：AI 按 status 决定转述口径；取值范围：仅三值；最终作用：订单结局的诚实表达。

**字段 14：`estimatedDelivery`（预计送达，string，可选）**——设计原因："什么时候到"是下单后必被追问的；类型原因：时间用字符串（可含自然语言如"今天傍晚"——平台给什么转什么）；来源：平台；内部使用：AI 转述；取值范围：任意时间表述；最终作用：送达预期。

**字段 15：`message`（平台留言，string，可选）**——设计原因：缺货替换、取消原因等要传回；类型原因：自由文本；来源：平台；内部使用：AI 必读（尤其 rejected 时原因就在这）；取值范围：任意字符串；最终作用：平台与人类的沟通桥。

### 组 6：KitchenSafetyItem 的 3 个字段

**字段 16：`area`（区域名，string，必填）**——设计原因：安全结论必须落到具体区域（燃气区/电器区/水槽区）；类型原因：区域是文本标签；来源：巡检系统；内部使用：AI 挑相关区域回答单点问题；取值范围：任意字符串（宿主应保持命名稳定）；最终作用：安全条目的定位。

**字段 17：`status`（等级，KitchenSafetyLevel，必填）**——设计原因：每个区域要一个明确刻度；类型原因：复用三值联合（ok/warning/critical）；来源：巡检系统判定；内部使用：AI 判断轻重；取值范围：仅三值；最终作用：逐区域结论。

**字段 18：`note`（备注，string，可选）**——设计原因：隐患细节（"软管老化"）必须能说清；类型原因：自由文本；来源：巡检系统；内部使用：AI 转述给人类听；取值范围：任意字符串；最终作用：等级的解释。

### 组 7：KitchenSafetyReport 的 3 个字段

**字段 19：`checkedAt`（巡检时间，string，必填）**——设计原因：安全数据同样强时效；同组 2 字段 6 的类型/来源逻辑；最终作用：报告的快照时刻。

**字段 20：`overall`（总评，KitchenSafetyLevel，必填）**——设计原因：人类要一句话结论；类型原因：复用统一刻度；来源：宿主汇总各区域得出（通常取最差）；内部使用：AI 的第一句转述；取值范围：仅三值；最终作用：整体安全结论。

**字段 21：`items`（区域条目数组，KitchenSafetyItem[]，必填）**——设计原因：总评要有明细支撑；类型原因：数组（每个检查过的区域一条）；来源：巡检系统；内部使用：AI 挑重点转述；取值范围：数组（可为空——巡检系统坏了时应报异常而非空报告）；最终作用：明细清单。

### 组 8：MealStats 的 4 个字段

**字段 22：`days`（统计天数，number，必填）**——设计原因：统计范围是统计的身份证；类型原因：数字；来源：read 的入参回显；内部使用：AI 说明"最近 7 天…"；取值范围：正整数（≤365 在工具层卡）；最终作用：范围声明。

**字段 23：`records`（记录条数，number，必填）**——设计原因：样本量决定统计可信度；类型原因：数字；来源：宿主统计；内部使用：records=0 时 AI 说"暂无记录"；取值范围：≥0 整数；最终作用：可信度标尺。

**字段 24：`averageCaloriesPerDay`（日均热量，number，可选）**——设计原因：饮食控制建议的核心指标；类型原因：数字可比较可建议；来源：宿主计算；**为什么可选**：记录太少算不出来——**宁可缺省不许编数**；内部使用：AI 给建议时引用；取值范围：≥0 的数；最终作用：统计的价值核心。

**字段 25：`notes`（提示数组，string[]，可选）**——设计原因：统计之外的定性发现（"外食多"）值得带上；类型原因：多条提示用数组；来源：宿主分析；内部使用：AI 转述；取值范围：字符串数组；最终作用：统计的"人话注脚"。

### 组 9：四个 Provider 方法的入参（合同层的参数）

**参数 26：`request`（placeOrder 的入参，GroceryOrderRequest）**——见核心定义 4/11：整张订单请求原样转发，工具层校验在前。

**参数 27：`days`（read 的入参，number）**——设计原因：统计范围由 AI 按人类问题决定（"最近一个月"→30）；类型原因：数字可运算；来源：AI 填 → tools.ts Zod 校验（正整数、≤365、默认 7）→ 转发；内部使用：宿主按天数聚合；取值范围：1-365 的整数；最终作用：统计范围的唯一决定项。

### 组 10：ChefCapabilities 的 4 个字段（注入面板四格）

**字段 28：`fridgeInventory?`（FridgeInventoryProvider，可选）**——亮这格 = 注册 fridge_inventory 工具 + configured 显示"冰箱库存"。

## 模块4：文件关键逻辑 & 特殊代码说明

> 纯类型文件没有 if/循环/异常。需要讲清"为什么"的是三条结构性设计：

### 1、为什么全文件零 import（连 zod 都不引）

**因为**类型契约层是"最底层图纸"，它依赖的任何东西（哪怕是类型库）都会成为全链路的牵连点；**而**它需要的所有类型（string/number/数组/字面量联合）TS 原生就有，**所以**零依赖。**好处**：这份文件永远编译得过、永远可以被任何层引用（包括测试替身），"图纸"保持绝对干净。

### 2、为什么"请求"和"回执"成对出现（GroceryOrderRequest/GroceryOrder）

**因为**下单是"有来有往"的动作：AI 要知道"发什么"（请求形状）也要知道"会收回什么"（回执形状）才能决定怎么转述；**而**宿主要知道"收什么、还什么"才能实现。**成对定义 = 双方共用同一套词汇**，谁都不用猜。同样的成对思想也体现在 CleaningRequest/CleaningRun、ServiceRequest/ServiceBooking（cleaner 包，见 04 文档）。

### 3、为什么 status 字段全部用"字面量联合"而不是 string

**因为**状态是要被 AI 和程序**分支处理**的（rejected → 转述原因；critical → 建议人类处理），自由字符串会让"写错状态词"静默通过、下游全懵；**而**字面量联合让错误拼写直接编译报错 + AI 读到的值永远在预期集内。三处状态（订单三值、安全三值、以及 cleaner 包里的清洁/预约状态）全部遵循这一条。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 编译期：tsc 读取本文件，把 15 个类型并入类型系统（**无任何运行产物**）；

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **"数据结构 + Provider 合同 + 能力面板"三件套**：新增领域（园艺/宠物）照抄这个三件套骨架即可；
- **"请求/回执"成对类型**、"字面量联合状态"：一切"有来有往、状态有限"的场景通用。

### ⚠️ 易错点

1. **给可选字段强行赋值**：averageCaloriesPerDay 算不出来时返回 undefined/省略，**别塞 0**（0 是"算了且为零"，语义完全不同）；
2. **quantity 里掺单位**："500g" 是 string，类型直接报错——单位走 unit 字段；
3. **空数据返回 null**：items 永远返回数组（可空数组），null 会让 AI 误解为"没查到"而触发 unavailable 误报；
4. **rejected 回执不带 message**：AI 没法解释失败原因，转述变成"被拒绝了，原因不明"。

### 🔍 调试关键点

- **AI 说"暂无数据"但实际有数据**：查宿主 read 实现是否真的被注入（面板四格是否有值）；
- **工具调用报"参数校验失败"**：是 tools.ts 的 Zod 层拦的（如数量非正整数），不是本文件的锅——本文件只在编译期说话；
- **数据形状对不上**：对比工具返回的 JSON 与本文件接口逐字段核对。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| 四个 Provider 的方法签名 | 🚫 不能改 | tools.ts 按签名转发、宿主按签名实现，动一处断两头 |
| status 字面量联合的值 | 🚫 不能改 | AI 提示词、宿主实现、既有数据都按现值工作 |
| 字段名 | 🚫 不能改 | AI 理解数据、宿主构造数据都按字段名来 |
| averageCaloriesPerDay 的"可选"语义 | 🚫 不能改成必填 | 必填会逼宿主编数（没记录时填什么？）——违背不做假成功 |
| 新增字段（如 FridgeItem 加位置字段） | ✅ 可扩展 | 加可选字段向后兼容；加必填字段=破坏既有宿主，需全员同步 |
| 新增第五种能力 | ✅ 可扩展 | 按总览红线 7 的四处联动清单走 |
