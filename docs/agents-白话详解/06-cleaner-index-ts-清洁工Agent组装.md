# 06 · cleaner/index.ts 源码白话详解（清洁工 Agent 组装）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`index.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agents/cleaner/src/index.ts`
- 编译产物：`packages/agents/cleaner/dist/index.js`（`package.json` 的 `main`/`exports` 指向它——**本包的包入口**）

### 2、文件存在的核心原因

**因为**清洁域也备好了材料（capabilities.ts 合同 + tools.ts 车间），还缺一个**装配成"完整工人"并提供使用入口**的地方——与厨师的 index.ts 完全同构的需求（见 03 文档模块1第 2 条）。**而**清洁工的岗位说明书里有一条自己的特色纪律——**"涉及费用、上门时间或隐私区域时需要人类确认"**（清洁域独有：上门服务和进入卧室这类隐私区域，是厨师域没有的风险面），**所以**这个文件不只是镜像，还承载着清洁域专属的风险边界表达。

**如果没有这个文件，程序会出现的问题：** 同 03 文档——使用方没有入口、身份没有出处、包不成立。

### 3、文件的整体定位

这个文件**专门负责"清洁工的出生"**：`createCleanerAgent(options)` 工厂 + 出厂空壳默认导出。它与 chef/index.ts 构成一对镜像样板——**读通这两个文件，"如何接一个新子 Agent"就完全掌握了**（docs/SUBAGENT-DEV-GUIDE.md 的目录模板即以此为准）。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- `@meimaohouse/agent-sdk`：`defineSubAgent`、`SubAgent`、`Memory`/`ModelInstance` 类型；
- `./capabilities.js`：`CleanerCapabilities` 类型；
- `./tools.js`：`createCleanerTools`。

**谁来调用它（下游）：**

- `apps/butler-web/src/agents.ts`：`import cleaner from '@meimaohouse/cleaner-agent'`（默认导出空壳）→ 交给管家；
- 配真实能力的宿主：`createCleanerAgent({ capabilities, model, memory })`；
- 测试代码。

## 模块2：文件内核心定义与核心函数超详细说明

### 核心定义 1：文件头的两组 `export *` 转发

1. **名称**：第 10-11 行：`export * from './capabilities.js'` 和 `export * from './tools.js'`。
2. **设计的根本原因**：**因为**外部可能需要直接引用清洁域类型或直调工具工厂，**所以**包入口全量转发（机理与 03 文档核心定义 1 完全一致，含 NodeNext 强制 `.js` 后缀的语法理由）。
3. ~ 8. **（其余维度同 03 文档核心定义 1，此处不赘）**
   最终作用：包的完整 API 面暴露齐全；注意事项：内部文件不该暴露的别加 export。

### 核心定义 2：`CleanerAgentOptions`（出生工厂的选项单）

1. **名称**：`CleanerAgentOptions`，接口，3 个可选字段：`capabilities?`、`model?`、`memory?`。
2. **设计的根本原因**：**因为** createCleanerAgent 需要"配什么能力/用什么脑/要不要记性"的统一选项形状，三格全可选（各有合理默认）——与 ChefAgentOptions 完全同构（03 文档核心定义 2）。
3. **语法写法的原因**：全可选字段（`?`）——`createCleanerAgent()` 空参合法的类型基础。
4. **内部逻辑分步讲解**：capabilities → 清洁域三格面板；model → 模型实例；memory → 记忆实现。
5. **触发条件**：不运行；createCleanerAgent 的入参类型。
6. **最终作用**：装配清洁工的全部可调项收敛为一个对象。
7. **使用场景**：宿主装配、测试注入。
8. **缺陷/注意事项**：三格"不填 ≠ 没影响"（空壳/全局模型/无记忆），同 03 文档提醒。

### 核心函数：`createCleanerAgent(options)`（出生工厂）

1. **函数名称**：`createCleanerAgent`，入参 `options: CleanerAgentOptions = {}`，返回 `SubAgent`。
2. **函数设计的根本原因**：**因为**"发工具 → 数能力 → 填登记表 → 交 defineSubAgent"的出生流程要有一个领域专属的执行点——**而**清洁工的登记表内容（身份、说明书、风险纪律）是本包独有的"内容资产"，**所以**工厂存在；SDK 的 defineSubAgent 管"怎么组装"，本函数管"清洁工是什么"。
3. **函数语法写法的原因**：同步（defineSubAgent 懒加载）、参数默认值 `= {}`、返回类型精确为 SubAgent——三条理由与 03 文档核心函数第 3 条完全一致。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：`const tools = createCleanerTools(options.capabilities)`——按三格面板发工具（0-4 个，cleaning 格贡献 2 个，05 文档）；
   - 第 2 步：`const configured = [ capabilities?.cleaning ? '清洁执行' : '', capabilities?.scheduling ? '服务预约' : '', capabilities?.laundry ? '洗衣状态' : '', ].filter(Boolean)`——**三格播报**（chef 是四格，这里少一格）：配了写人话名字、没配空串、最后筛空——机理同 03 文档模块4第 1 条；
   - 第 3 步：`return defineSubAgent({...})`——填登记表；
   - 第 4 步（登记表逐项）：`id: 'cleaner'`（**写死**——全工程身份）；`name: '清洁工'`；`domain: '清洁域'`；`description`（"掌管清洁域：房间清洁、扫地机器人、洗衣与床品提醒、上门清洁和收纳服务预约。"——范围 + 意图清单式）；`systemPrompt`（模板字符串，见第 5 步）；`tools`（第 1 步产出）；`model: options.model`（透传，SDK 兜底）；`memory: options.memory`（透传）；
   - 第 5 步（systemPrompt 内容拆解）：
     - **工作范围四条**：房间与公共区域清洁 / 扫地机器人和其他清洁设备 / 洗衣与床品更换提醒 / 上门清洁、洗鞋和收纳服务预约——与 description 呼应、与工具集对应；
     - **能力播报插值**：`当前可用能力：${configured.length > 0 ? configured.join('、') : '无'}`——"壳知道现状"机制（03 文档模块4第 2 条同款）；
     - **行为准则四条**：① 只按工具真实数据作答、禁止编造设备状态/清洁完成结果/预约结果；② 缺工具回 `unavailable` + `error_code=capability_not_configured`；③ **涉及费用、上门时间或隐私区域时需要人类确认，返回 `needs_human`**（**清洁域特色条款**——厨师域对应条款是泛泛的"人类拍板"，这里点名了三类高风险场景）；④ 需要协作写 suggestions 由管家转派。
5. **函数的触发条件**：应用装配阶段（默认导出在模块加载时执行一次）。
6. **函数的最终作用**：产出身份明确、工具与能力一致、自带"能力现状播报 + 风险纪律"的清洁工 Agent。
7. **函数的使用场景**：默认导出（空壳）、宿主配能力、测试。
8. **函数的缺陷/注意事项**：每次调用产新实例——一个进程一份；同 03 文档提醒。

### 核心定义 3：默认导出 `export const cleaner = createCleanerAgent()` + `export default cleaner`（出厂空壳）

1. **名称**：`cleaner`（常量）+ 默认导出。
2. **设计的根本原因**：**因为**"开箱即用必须零配置"，应用一行 import 就能把清洁工挂进管家（apps/butler-web/src/agents.ts 实际用法）；**而**零配置 = 零真实能力，**所以**默认导出必须空壳（注释原话："默认导出空壳 Agent，供应用层直接装配"）。
3. **语法写法的原因**：常量导出 + 默认导出双通道——`import cleaner from ...`（用空壳）与 `import { createCleanerAgent } from ...`（配能力）两条路都顺。
4. **内部逻辑分步讲解**：模块加载即执行工厂（空参）→ 零工具 → 播报"无" → defineSubAgent 验表 → 空壳成品。
5. **触发条件**：任何 import 本包的动作（本包唯一的"加载即运行"代码）。
6. **最终作用**：零配置可用的清洁工空壳。
7. **使用场景**：apps/butler-web 的 agents.ts、demo。
8. **缺陷/注意事项**：它永远没有能力——配能力要用工厂自建（03 文档核心定义 3 第 8 条同款提醒）；**加载即执行的安全性依赖"装配全程同步无副作用"**（03 文档模块4第 5 条），改工厂时不可引入异步/副作用。

## 模块3：文件内每一个参数超详细说明

### 参数 1：`options`（createCleanerAgent 的入参）

1. **名称 + 类型**：`options`，`CleanerAgentOptions`，默认 `{}`。
2. **参数设计原因**：装配可调项的统一入口；默认值支撑空壳直呼。
3. **参数类型选择原因**：接口 + 默认值（同 03 文档参数 1）。
4. **参数的传入来源**：宿主装配；默认导出路径传 `{}`。
5. **参数的内部使用逻辑**：capabilities 进工具工厂与播报数组；model/memory 透传登记表。
6. **参数的取值范围**：不传或三格任意组合。
7. **参数的最终作用**：清洁工出生配置的唯一入口。

### 参数 2：`options.capabilities`（能力面板）

1. **名称 + 类型**：`capabilities`，`CleanerCapabilities`，可选。
2. **参数设计原因**：真实本领的唯一注入通道；不填 = 空壳。
3. **参数类型选择原因**：04 文档三格面板类型。
4. **参数的传入来源**：宿主实现三个 Provider 后填入。
5. **参数的内部使用逻辑**：两处消费（工具工厂 / configured 播报）读同一格——口径天然一致。
6. **参数的取值范围**：不填或三格任意组合。
7. **参数的最终作用**：清洁工"会什么"的总开关。

### 参数 3：`options.model`（模型实例）

1. **名称 + 类型**：`model`，`ModelInstance`，可选。
2. **参数设计原因**：单独换脑/测试注入的通道。
3. **参数类型选择原因**：agent-sdk 的 ModelInstance。
4. **参数的传入来源**：宿主/测试。
5. **参数的内部使用逻辑**：透传 → SDK 内 `spec.model ?? getModel()` 兜底（不填走全局配置；入口没配置时开工作间才报错——懒加载保护，见 03 文档模块4第 4 条）。
6. **参数的取值范围**：不填或合法模型实例。
7. **参数的最终作用**：清洁工的大脑个性化通道。

### 参数 4：`options.memory`（记忆实现）

1. **名称 + 类型**：`memory`，`Memory`，可选。
2. **参数设计原因**：清洁工要记跨任务的账（各区域清洁周期、人类对哪些区域敏感），生产环境注入 SQLite 版（docs/DATABASE.md）。
3. **参数类型选择原因**：agent-sdk 的 Memory 接口。
4. **参数的传入来源**：宿主。
5. **参数的内部使用逻辑**：透传 → SDK 决定是否追加记忆工具 + 说明书记忆条款。
6. **参数的取值范围**：不填或 Memory 实现。
7. **参数的最终作用**：清洁工的"记性"开关。

### 参数 5：`tools`（局部变量——工具列表）

1. **名称 + 类型**：`tools`，`DomainTool[]`。
2. **参数设计原因**：登记表 tools 字段的原料。
3. ~ 7. **类型承接车间返回；来源 createCleanerTools；消费点登记表；取值 0-4 个；作用：清洁工的双手清单。**

### 参数 6：`configured`（局部变量——能力现状播报数组）

1. **名称 + 类型**：`configured`，`string[]`，元素为"清洁执行/服务预约/洗衣状态"的子集。
2. **参数设计原因**：模型靠它知道"我此刻真的会什么"——自我认知校准器（03 文档参数 6 的机理）。
3. **参数类型选择原因**：要 filter/join 所以字符串数组。
4. **参数的传入来源**：函数内从三格现算。
5. **参数的内部使用逻辑**：唯一消费点——systemPrompt 插值（空数组插成"无"）。
6. **参数的取值范围**：0-3 个人话名字。
7. **参数的最终作用**："壳与手口径一致"的可见面。

### 参数 7：登记表 spec 的固定字段（id/name/domain/description/systemPrompt）

1. **名称 + 类型**：全字符串，写死。
2. **参数设计原因**：
   - `id: 'cleaner'`：全工程身份（任务编号/domain/记忆命名空间/`subagent_cleaner` 工具名的根），**写死**；
   - `name: '清洁工'` / `domain: '清洁域'`：人设与门牌；
   - `description`：管家的派活广告（范围 + 意图清单）；
   - `systemPrompt`：岗位说明书（工作范围 + 能力播报 + 四条行为准则，其中"费用/上门/隐私需人类确认"是清洁域特色）。
3. **参数类型选择原因**：自然语言文本 → string；id 受 SDK 正则校验。
4. **参数的传入来源**：本文件写死（领域包的"内容工作"）。
5. **参数的内部使用逻辑**：整体交 defineSubAgent 验表组装。
6. **参数的取值范围**：固定值（修改规则见模块6）。
7. **参数的最终作用**：清洁工身份、形象、规矩的内容来源。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、`configured` 的"占位 + 过滤"三格版——机理与 chef 四格版完全一致

一行一格看全三格状态、`filter(Boolean)` 统一筛空串（空串是假值）——同 03 文档模块4第 1 条，不赘。**注意**：cleaning 格只播报一个名字（"清洁执行"）但它实际出两个工具——**播报按"能力"计数，工具按"操作"计数，两个口径不需要相等**（05 文档模块2第 8 条）。

### 2、systemPrompt 的能力插值——为什么说明书必须动态

同 03 文档模块4第 2 条：模型照说明书办事，说明书与现实（工具列表）必须同源一致——否则模型对着"无"的说明书乱用工具，或对着"全能"的说明书空口编数据。

### 3、行为准则第三条的清洁域特色写法——为什么点名"费用、上门时间、隐私区域"

**因为**清洁域的风险面与厨房域不同：厨师域的"花钱"集中在下单，而清洁域是**三类外部侵入**——① 费用（上门服务要真付钱）；② 上门时间（有陌生人进家门，时间错了很尴尬）；③ 隐私区域（让人进卧室收纳=隐私暴露）。**这三类事一旦模型"自作主张"，代价远超一次错误回答**，**所以**说明书把 needs_human 的触发场景从泛泛的"需要人类拍板"细化成三个具体红线——模型照单执行，管家照单转述"这事需要你确认"。

### 4、`model: options.model` 透传 + 默认导出在顶层执行——为什么这对组合安全

同 03 文档模块4第 4/5 条：工厂里不 getModel（未配置会抛错会炸掉模块加载）→ 透传 undefined → SDK 懒加载推迟解析 → "加载即执行"的默认导出安全成立。

### 5、与 chef 包的镜像关系——为什么两个包要刻意保持同构

**因为**这两个包是工程给"未来子 Agent"的标准样板：结构越同构（同样的三文件、同样的工厂骨架、同样的播报写法、同样的准则四条骨架），新人照抄接新领域的出错率越低；**而**领域差异只应体现在"内容"（说明书文案、数据结构、工具参数表）而不是"结构"里。**这是"模板一致性"的刻意工程决策**——改动任一包的结构时，问一句"另一个包要不要跟着改"。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 应用 import 本包 → 加载 dist/index.js → 转发行执行 → 顶层 `createCleanerAgent()`：零工具 → 播报"无" → defineSubAgent 验表 → 空壳成品；
2. 应用把 cleaner 交给管家 → `toButlerTool()` → 注册为 `subagent_cleaner`；
3. 运行期：管家派活 → 信封进来 → SDK 开新工作间（此时才取模型/挂工具/拼说明书）→ 清洁工按 intent 干活：有工具调工具拿真实数据；缺工具按准则回 unavailable + capability_not_configured；涉及费用/上门/隐私 → needs_human 等确认；
4. 结果信封回管家 → 转述人类。
5. 配真实能力的宿主：用 `createCleanerAgent({ capabilities, memory })` 自建，流程同上但工具齐全。

### 2、文件在整个工程中不可替代的作用

**它是清洁工的出生地与包门面**——与 chef/index.ts 组成"子 Agent 接入模板"的双例证；清洁域的"费用/上门/隐私"风险纪律在此落地。

### 3、运行依赖的环境与前置条件

- 依赖 agent-sdk 与 zod；作为 Agent 使用时入口需已 configureModel（或注入 model）——但模块加载零前置；
- 编译前置：依赖已安装。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **整个文件 = 新子 Agent 模板第二例**（与 03 文档互为镜像）——新领域抄结构换内容；
- **"特色风险条款"写法**：把 needs_human 的触发场景按领域风险面具体化（费用/上门/隐私）——每个新领域都应做这道"风险面盘点"。

### ⚠️ 易错点

1. **以为默认导出会带注入的能力**：默认导出永远空壳——配能力走工厂；
2. **改 id 'cleaner'**：路由/历史数据/记忆键全断（总览红线 1）；
3. **播报行与能力格错位**（加能力忘加播报行）：模型认知与现实工具集分裂——加能力四步联动（总览红线 7）；
4. **删改行为准则**：特别是第三条"费用/上门/隐私"——删了模型可能擅自约上门服务（真实金钱与隐私风险）。

### 🔍 调试关键点

- **清洁工什么任务都回 unavailable**：在用默认导出空壳（正确现象），配能力走工厂；
- **AI 擅自调用 schedule_cleaning_service**：查 systemPrompt 第三条是否被删/改弱；
- **管家不派活给清洁工**：查 description 文案是否被改含糊；
- **模型认知与工具不符**：查播报插值与实际工具列表是否一致。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| `id: 'cleaner'` | 🚫 不能改 | 全链路身份 |
