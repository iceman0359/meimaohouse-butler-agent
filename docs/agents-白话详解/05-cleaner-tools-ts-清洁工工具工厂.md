# 05 · cleaner/tools.ts 源码白话详解（清洁工工具工厂）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`tools.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agents/cleaner/src/tools.ts`
- 编译产物：`packages/agents/cleaner/dist/tools.js`

### 2、文件存在的核心原因

**因为**清洁工 Agent 的本领（查清洁状态、开工清洁、约上门服务、查洗衣）都是宿主注入的程序实现，AI 模型够不着，**必须**有"翻译 + 包装"这道工序——与厨师包的工具工厂同理（见 02 文档模块1第 2 条）。**而**清洁域还多了一个独特需求：**一格能力要出两个工具**（清洁 Provider 既能查状态又能开工——查和做对模型来说是两个完全不同的操作，必须分开两个工具，模型才能"想查就查、想做才做"），**所以**需要一个能处理"一格多工具"的工厂。

文件头注释原话："根据宿主实际注入的能力动态生成工具。"

**如果没有这个文件，程序会出现的问题：** 同 02 文档——能力用不上或假工具横行；另外"查/做混在一个工具里"会让模型困惑（一个调用到底是在查还是在扫？）。

### 3、文件的整体定位

这个文件**专门负责"按能力清单生成清洁域的工具列表"**——结构与 chef 的 tools.ts 镜像，特色是 **cleaning 一格 if 块里 push 两个工具**（查状态的 cleaning_status + 干活的 start_cleaning），以及**三个"做动作"的工具全部带参数表**（清洁域的查洗衣虽然也是"查"，但与厨房"纯查"不同之处在于开工类动作多）。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- `@meimaohouse/agent-sdk`：`defineDomainTool` + `DomainTool` 类型；
- `zod`：参数校验器；
- `./capabilities.js`：`CleanerCapabilities` 类型。

**谁来调用它（下游）：**

- `index.ts`：`createCleanerAgent` 第一步调它。

**一句话：清洁域"能力 → AI 双手"的焊接点，且示范了"一格焊两只手"的写法。**

## 模块2：文件内核心函数超详细说明

### 核心函数：`createCleanerTools(capabilities)`（工具车间）

1. **函数名称**：`createCleanerTools`，入参 `capabilities: CleanerCapabilities = {}`，返回 `DomainTool[]`。
2. **函数设计的根本原因**：**因为**"没注入能力就不注册工具"的纪律必须有唯一执行点，**而**清洁域有 4 个工具要按 3 格能力分发（cleaning 格管 2 个），**所以**封装成工厂统一执行。**不封装的弊端**：与 chef 同理——注册逻辑散落、"没能力不注册"的判断迟早漏一处。
3. **函数语法写法的原因**：
   - **因为**空面板合法（空壳 Agent），**所以**参数默认值 `= {}`；
   - **因为**cleaning 格要出两个工具，**所以**那一格的 if 块里是**连续两次 tools.push(...)**（一次 push 一个）——这是本文件与 chef 版最大的语法结构差异（chef 每块 push 一个）；
   - **因为**与 chef 版保持同构便于对照维护，**所以**其余写法（provider 局部变量、defineDomainTool 包装）完全同款。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：`const tools: DomainTool[] = []`——备篮子；
   - 第 2 步：`if (capabilities.cleaning)` → 存 `provider`（类型收窄技巧，见 02 文档模块4第 2 条）→ **push 第一个工具 `cleaning_status`**：无参查询（`z.object({})`），execute 转发 `provider.getStatus()` → **push 第二个工具 `start_cleaning`**：带参数表（area 必填非空、mode 三选一可选、note 可选），execute 把**整个校验后的 input 原样转发** `provider.start(input)`——**为什么这里能原样转发而 chef 的下单要重新组装**：**因为** start_cleaning 的 Zod 参数表与 CleaningRequest 接口的形状**逐字段一致**（area/mode/note），校验后的对象天然就是合同要的形状（chef 的 items/note 平铺参数与请求对象结构不同才需要重组）；
   - 第 3 步：`if (capabilities.scheduling)` → 存 provider → push `schedule_cleaning_service`：参数表（service 必填非空、preferredTime 可选、note 可选），execute 原样转发 `provider.book(input)`（参数表与 ServiceRequest 逐字段一致，同上理由）；
   - 第 4 步：`if (capabilities.laundry)` → 存 provider → push `laundry_status`：无参查询，转发 `provider.getStatus()`；
   - 第 5 步：`return tools`。
5. **函数的触发条件**：createCleanerAgent 组装时调用一次。
6. **函数的最终作用**：产出与注入能力严格一致的工具列表（0-4 个工具，最多四工具）。
7. **函数的使用场景**：仅被 index.ts 调用。
8. **函数的缺陷/注意事项**：三段 if 是"能力 → 工具"的手工映射——新增能力要记得加块（与 chef 版同款注意）；**cleaning 格的"一格两工具"要当整体看待**（删状态工具留开工工具，模型就"只能瞎扫不能问"，反之"只能问不能扫"——半截能力比没能力更糟）。

## 模块3：文件内每一个参数超详细说明

### 参数 1：`capabilities`（能力面板）

1. **名称 + 类型**：`capabilities`，`CleanerCapabilities`（04 文档三格面板），默认 `{}`。
2. **参数设计原因**：**因为**工厂产出完全由面板决定，面板是唯一入参；默认值支撑空壳调用。
3. **参数类型选择原因**：必须是 CleanerCapabilities（三格可选 Provider），换 any 丢类型保护。
4. **参数的传入来源**：createCleanerAgent 转发的 options.capabilities。
5. **参数的内部使用逻辑**：三个 if 读三格；cleaning 格的工具用同一 provider 变量（getStatus 与 start 共用一份实现——**这正是 04 文档"双方法合同"在工具层的兑现**）。
6. **参数的取值范围**：不传或三格任意组合；null 会在取格子时崩（类型层也拦）。
7. **参数的最终作用**：决定清洁工"有几只手、会什么活"。

### 参数 2：`tools`（工作篮子）

1. **名称 + 类型**：`tools`，`DomainTool[]`，局部变量，初始 `[]`。
2. **参数设计原因**：收集 4 个工具统一返回。
3. **参数类型选择原因**：显式标注 `DomainTool[]` 防塞错。
4. **参数的传入来源**：函数内部新建。
5. **参数的内部使用逻辑**：cleaning 块 push 两次、另两块各一次；最后整体 return。
6. **参数的取值范围**：0-4 个工具（cleaning 一格贡献 2 个）。
7. **参数的最终作用**：工具列表的装配容器。

### 参数 3：`provider`（各 if 块内的能力实现）

1. **名称 + 类型**：`provider`，对应 Provider 接口（CleaningProvider / ServiceSchedulingProvider / LaundryProvider）。
2. **参数设计原因**：回调执行时刻与 if 判断时刻分离，必须把收窄后的实现存 const 供闭包使用（02 文档模块4第 2 条的完整机理，此处不赘）。
3. **参数类型选择原因**：const 固定类型收窄——TS 严格模式硬要求。
4. **参数的传入来源**：面板对应格。
5. **参数的内部使用逻辑**：被 execute 闭包捕获；cleaning 块的**同一个 provider 被两个工具的回调共享**（同一份设备实现服务"查"和"做"两个工具）。
6. **参数的取值范围**：对应接口的合法实现。
7. **参数的最终作用**：工具与真实设备/平台之间的"对接销钉"。

### 参数 4：`area`（start_cleaning 工具的入参字段）

1. **名称 + 类型**：`area`，字符串，Zod 校验 `.min(1)`。
2. **参数设计原因**：**因为**"扫哪儿"是开工指令的靶心，没有它指令无法执行。
3. **参数类型选择原因**：区域是文本标签 → string；min(1) 拦空值。
4. **参数的传入来源**：AI 模型（通常从 cleaning_status 返回的区域清单里挑名字——**这就是为什么两个工具共用一个能力**：查到的名字才能准确地下单）。
5. **参数的内部使用逻辑**：校验 → 进入原样转发的 input → 设备执行。
6. **参数的取值范围**：非空字符串；**强烈建议用设备认识的区域名**（与 getStatus 输出一致），否则 rejected + message 解释。
7. **参数的最终作用**：清洁指令的对象。

### 参数 5：`mode`（start_cleaning 工具的入参字段）

1. **名称 + 类型**：`mode`，枚举字符串 `z.enum(['quick', 'standard', 'deep'])`，可选（`.optional()`）。
2. **参数设计原因**：**因为**清洁力度影响耗时/效果，人类会说"随便扫扫"或"大扫除"，**所以**留三档模式；**因为**不说就应让设备用默认档，**所以**可选（AI 不必替人类瞎选）。
3. **参数类型选择原因**：**因为**三档固定，**所以**用 z.enum（运行校验锁死）+ 类型层面与 CleaningRequest.mode 的字面量联合对齐；**不填的语义**（undefined）与"填了 quick"不同，optional 精准表达。
4. **参数的传入来源**：AI 按人类语义挑选。
5. **参数的内部使用逻辑**：校验 → 原样转发 → 设备按档执行。
6. **参数的取值范围**：不填或三值之一；其他值校验直接拒。
7. **参数的最终作用**：清洁力度档位。

### 参数 6：`note`（start_cleaning / schedule_cleaning_service 共用的入参字段）

1. **名称 + 类型**：`note`，字符串，可选。
2. **参数设计原因**：**因为**两个动作都常有补充交代（"沙发底下多扫扫"/"有宠物请按铃"），**所以**各留一格备注（两个工具各自定义自己的 note，形状相同但互不相干）。
3. **参数类型选择原因**：自由文本 → string + optional。
4. **参数的传入来源**：AI 按人类要求。
5. **参数的内部使用逻辑**：随 input 原样转发到设备/平台。
6. **参数的取值范围**：不填或任意字符串。
7. **参数的最终作用**：动作的附加说明。

### 参数 7：`service`（schedule_cleaning_service 工具的入参字段）

1. **名称 + 类型**：`service`，字符串，Zod 校验 `.min(1)`。
2. **参数设计原因**：**因为**"约什么服务"是预约的标的（深度清洁/洗鞋/收纳），没它预约无从谈起。
3. **参数类型选择原因**：服务类型是文本标签；不用枚举——**因为**服务目录由平台侧决定且会扩充，框架锁死枚举反而卡宿主（与 mode 的取舍恰好相反：**设备认死的档位用枚举，平台可扩的目录用自由文本**）。
4. **参数的传入来源**：AI 按人类要求填。
5. **参数的内部使用逻辑**：校验 → 原样转发 book。
6. **参数的取值范围**：非空字符串；太偏门的写法平台匹配不到时由回执 message 说明。
7. **参数的最终作用**：预约标的。

### 参数 8：`preferredTime`（schedule_cleaning_service 的入参字段）

1. **名称 + 类型**：`preferredTime`，字符串，可选。
2. **参数设计原因**：**因为**上门要挑时间；**因为**人类说法多样（"周六上午"），**所以**字符串兼容自然语言（04 文档核心定义 5 的理由）。
3. **参数类型选择原因**：string + optional。
4. **参数的传入来源**：AI 按人类要求。
5. **参数的内部使用逻辑**：原样转发。
6. **参数的取值范围**：不填或任意时间表述。
7. **参数的最终作用**：时间意向。
8. **纪律提醒**：**涉及上门时间的预约按 systemPrompt 应先走 needs_human 获人类确认**——这个工具通常在人类点头后才被 AI 调用。

### 参数 9：无参数工具的空参数表（cleaning_status / laundry_status 的 `z.object({})`）

1. **名称 + 类型**：`z.object({})`——空对象校验器。
2. **参数设计原因**：两个查询动作不需要 AI 传参；但框架必须有 inputSchema，空对象校验器明确表达"无参数可填"，防模型瞎编参数（02 文档模块3参数 7 的机理）。
3. **参数类型选择原因**：同上。
4. **参数的传入来源**：写死。
5. **参数的内部使用逻辑**：框架按它校验（只接受空对象）。
6. **参数的取值范围**：仅空对象。
7. **参数的最终作用**：把"纯查询工具"表达清楚。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、cleaning 格里的"连续两次 push"——为什么一格要出两个工具

**因为**"查清洁状态"和"开始清洁"对模型是**两种意图**（想知道 vs 想行动），工具是按意图划分的：合成一个工具就得靠参数区分（比如 `action: 'query' | 'start'`），模型容易混淆且参数表臃肿；**而**拆成两个工具后，名字和描述各自把意图说死（cleaning_status"读取状态" / start_cleaning"开始清洁"），模型选对工具的概率大幅提高。**代价**是管家看到两个工具（上下文多两行描述）——换来的是操作边界的清晰，值得。

### 2、三个 if 守卫——为什么一个都不能少（与 chef 同理但各有侧重）

**如果删掉 if 无条件注册 start_cleaning**：没接设备的宿主那里，模型看到"能开工"就去调 → provider undefined → 兜底失败 JSON → 但模型已信"我能扫地"，反复尝试刷失败；**更隐蔽的是 laundry_status**：删了 if，AI 会对着一个必然失败的工具反复"查洗衣"——**对"查"类工具的执念比"做"类更顽固**（模型总觉得再查一次就有了）。**所以三段 if 同等重要**，一格都不能松。

### 3、start_cleaning / schedule_cleaning_service 的 execute"原样转发"——为什么不用像 chef 下单那样重组

**因为**这两个工具的 Zod 参数表（area/mode/note、service/preferredTime/note）与对应合同接口（CleaningRequest/ServiceRequest）**字段名和结构完全一致**——校验后的 input 已经就是合同形状；**而**chef 的 order_groceries 参数表（items 数组平铺 + note）与请求对象虽然最终一致，但其参数表是"按模型填写习惯设计的平铺结构"，组装一次更保险。**两个包两种写法都在传达同一件事：转发处必须保证实参形状 == 合同形状**，形状已一致时原样透传即可。

### 4、schedule_cleaning_service 没有"金额/人数"参数——为什么

**因为**预约的费用与规格属于**平台侧的服务目录**（同一个"深度清洁"在不同城市价格不同），框架不该也没法在参数表里表达价格；**而**"涉及费用要人类确认"的纪律已写在 systemPrompt（06 文档）——**参数表管"要什么信息"，纪律管"什么时候能动"**，两套机制各管一段。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 编译期：tsc 核对工具参数表与合同接口的形状一致性（原样转发处尤其依赖）；
2. 装配期：createCleanerAgent 调本函数 → 三段 if → 产出 0-4 个工具（cleaning 格贡献 2 个）；
3. 工具列表进 defineSubAgent → 挂到每次新建的清洁工工作间；
4. 运行期：AI 按意图选工具 → 参数过 Zod → defineDomainTool 流水线兜底执行 → provider 转发到宿主设备/平台 → 标准 JSON 回 AI。

### 2、文件在整个工程中不可替代的作用

**它是清洁域"能力 → AI 双手"的转换器**，并示范了"一格能力多个工具"（查/做分离）的进阶工厂写法——未来任何"既可查又可控"的领域能力都照这个模式拆。

### 3、运行依赖的环境与前置条件

- 依赖 agent-sdk、zod、本包 capabilities 类型；
- 前置条件：空面板合法（返回空数组）；无网络/设备依赖（转发者不碰现实）。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **"一格能力 → 查/做两工具"模式**：一切设备类能力（空调、灯光、门锁）的标准拆法；
- **"参数表与合同同形 → 原样转发"**：省一次组装且类型安全（改形状时编译器立刻报错提醒同步）；
- **provider 共享闭包**：同一实现服务多工具，注入一次即可。

### ⚠️ 易错点

1. **只 push 了 start_cleaning 忘了 cleaning_status**（或反之）：半截能力——模型"能扫不能问"或"能问不能扫"，行为怪异难查；**cleaning 块的两个 push 是一个整体**；
2. **改了 CleaningRequest/ServiceRequest 字段名忘了同步 Zod**：原样转发处编译报错（好事，按提示同步）；
3. **给 schedule_cleaning_service 加价格参数**：价格属平台目录，参数表表达不了——要走 needs_human 纪律而不是加字段；
4. **区域名对不上**：AI 填的 area 设备不认识 → rejected——引导 AI 用 getStatus 返回的原名（两个工具同源正是为此）。

### 🔍 调试关键点

- **AI 看不到某工具**：查对应能力格是否有值；
- **start_cleaning 报失败**：看 error 文案（设备占用/区域不识别多见）；
- **AI 反复调失败工具**：查是否绕过了 if 守卫（手工注册了无能力的工具）。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| 三段 if 守卫 | 🚫 不能删 | 删了 = 无能力也有工具 = 模型误信 + 反复失败 |
| 工具名（cleaning_status/start_cleaning/schedule_cleaning_service/laundry_status） | 🚫 不能改 | systemPrompt 意图、协议文档、既有数据按这些名字约定 |
| cleaning 块"查/做两工具"的拆分 | 🚫 不能合并 | 合并 = 意图边界模糊（见模块4第 1 条） |
| Zod 校验（min(1)/enum/optional） | 🚫 不能放松 | 放松 = 空区域、野模式值直达设备 |
| mode 三档的档位词 | ✅ 可扩展 | 设备支持新档位时同步 Zod enum 与 CleaningRequest 联合 |
| 新增能力的 if 块 | ✅ 可扩展 | 按现有结构抄（含一格多工具写法） |
