## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`index.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agent-sdk/src/index.ts`
- 编译产物：`packages/agent-sdk/dist/index.js`
- **特殊身份**：它是 `package.json` 里 `"main": "dist/index.js"` 和 `"exports"` 指定的**包入口**——别的包写 `import ... from '@meimaohouse/agent-sdk'` 时，Node.js 实际加载的就是这个文件的编译产物。

### 2、文件存在的核心原因

**因为**这个包里有 5 个功能文件（protocol / model / memory / capability / sub-agent），如果不设统一出口，使用方就得写 `import { ... } from '@meimaohouse/agent-sdk/dist/protocol.js'` 这样深入包内部路径的引用——包内部文件一改名/一重组，所有使用方集体报错，包的内部结构等于完全裸奔；**所以**必须有一个"统一出货窗口"：包内部怎么分文件是自家的事，外人只认 `@meimaohouse/agent-sdk` 这一个地址。

**如果没有这个文件，程序会出现的问题：**

- 所有使用方（管家核心、厨师、清洁工）被迫引用包内具体文件路径，包内一重构就是一次全工程连锁报错；
- `package.json` 的 `main`/`exports` 没有可指的入口，包作为 npm 包的形态不完整（装了也 import 不进来）；
- 使用方要记住"哪个东西在哪个文件里"才能写 import，接入成本翻倍。

### 3、文件的整体定位

这个文件**只做一件事：转发**。它不含任何业务逻辑、不定义任何新东西，是纯粹的"出口清单/转发台"。工程里这类文件通常叫"桶文件"（barrel file）——像木桶的桶口，所有东西从一个口进出。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- 本包全部 5 个功能文件：`protocol.js`、`model.js`、`memory.js`、`capability.js`、`sub-agent.js`（各转发一次）。

**谁来调用它（下游）：**

- 一切写 `from '@meimaohouse/agent-sdk'` 的地方：`packages/butler-core/butler.ts`、`packages/agents/chef`、`packages/agents/cleaner`，以及未来的所有使用方——**它们 import 的表面地址都是包名，实际落点都是本文件**。

**一句话：它是包的"前台"，内部分工再复杂，客人只跟前台说话。**

## 模块2：文件内核心定义与核心函数超详细说明

> 本文件没有函数、没有类、没有运行逻辑，唯一的"核心成员"是 5 行转发语句 + 文件头的注释说明。按模板要求，把这 5 行转发当作 5 个核心条目逐个说明，并解释这条注释的作用。

### 核心条目 0：文件头注释（包的自我介绍）

1. **名称**：文件顶部的 JSDoc 注释块：`@meimaohouse/agent-sdk 子 Agent 接入 SDK：协议信封 + SubAgent 基类 + 模型工厂 + 记忆接口`。
2. **设计的根本原因**：**因为**打开任何源文件，读者第一个问题都是"这是干嘛的"，**所以**在文件头用一句话给包定位；它同时是全包的"功能清单"——协议信封（01 文档）、SubAgent 基类（05 文档）、模型工厂（04 文档）、记忆接口（03 文档），与 5 个功能文件一一对应（能力适配器在 capability 里，注释未单列）。
3. **语法写法的原因**：**因为** JS/TS 的注释语法 `/** ... */`（JSDoc 风格）是给"人不执行的说明文字"的标准载体，**所以**这么写——编译时注释被完全忽略，不占任何运行成本。
4. **内部逻辑分步讲解**：纯文字，无逻辑。
5. **触发条件**：不运行；人读代码时、IDE 悬停提示时显示。
6. **最终作用**：30 秒读懂这个包是干嘛的。
7. **使用场景**：代码审阅、交接、IDE 悬浮提示。
8. **缺陷/注意事项**：注释与实际功能要保持同步——将来包内新增大模块（比如新增文件），这行简介应同步更新，否则误导读者。

### 核心条目 1：`export * from './protocol.js'`（转发协议层）

1. **名称**：第一行转发语句。
2. **设计的根本原因**：**因为**协议信封（任务/结果的所有校验器、类型、createTaskId）是使用方最常拿的东西，**所以**第一个转发——不转发，外面就 import 不到 TaskRequestSchema 等任何协议成员。
3. **语法写法的原因**：
   - **因为** TS/ESM 的 `export * from '...'` 语法表示"把那个文件里**所有**导出成员原样再导出一遍"，**所以**用它——一行等于转发几十个成员，手写逐个 export 既啰嗦又容易漏；
   - **因为**工程编译配置是 `module: NodeNext`（见 `tsconfig.base.json`），ESM 规范下**相对导入必须写明文件扩展名**，且写的是**编译后的 .js**（TS 编译时会把 `./protocol.js` 对应到源文件 `./protocol.ts`）——**这是语法/规范强制**：不写 .js 后缀，编译产物在 Node 里运行时直接报"找不到模块"；
   - **因为**转发的是"导出集合"而不是某个成员，**所以**路径开头是 `./`（同目录相对路径）。
4. **内部逻辑分步讲解**：加载本文件时执行到这行 → 去加载 `protocol.js` 的编译产物 → 把它的全部导出挂到本包的出口上。没有条件、没有判断。
5. **触发条件**：任何使用方 import 本包（整包加载时 5 行转发都会执行）。
6. **最终作用**：`TaskRequestSchema`、`TaskEnvelopeSchema`、`ResultEnvelopeSchema`、`TaskStatus`、`createTaskId` 等全部协议成员可从包名直接导入。
7. **使用场景**：管家核心（派活、记任务）、子 Agent 开发（校验信封）。
8. **缺陷/注意事项**：`export *` 是"全量转发"——如果两个被转发文件导出了**同名**成员，会冲突且静默地变成 undefined（TS 会警告），**所以**各文件起名要自觉避撞（目前 5 个文件无重名，安全）。

### 核心条目 2：`export * from './model.js'`（转发模型工厂）

1. **名称**：第二行转发语句。
2. **设计的根本原因**：**因为**入口程序必须能拿到 `configureModel/getModel/setModel` 和错误类 `ModelNotConfiguredError`、类型 `ModelEnv/ModelInstance`，**所以**转发模型工厂——不转发，程序连模型都配不了。
3. **语法写法的原因**：同条目 1（`export *` + .js 后缀强制的理由完全一致，不再重复）。
4. **内部逻辑分步讲解**：加载时转发 model.js 的全部导出。
5. **触发条件**：同上。
6. **最终作用**：`configureModel`、`getModel`、`setModel`、`createModel`、`ModelNotConfiguredError` 等可从包名直接导入。
7. **使用场景**：工程入口（await configureModel）、管家/子 Agent（getModel）、测试（setModel）。
8. **缺陷/注意事项**：注意 `getModel` 在未配置时抛错——转发层不管业务，"什么时候能取"的纪律由 04 文档的机制保证。

### 核心条目 3：`export * from './memory.js'`（转发记忆模块）

1. **名称**：第三行转发语句。
2. **设计的根本原因**：**因为**管家要给自己的记忆工具、db 包要提供 SQLite 版记忆实现，都需要 `Memory` 类型、`InMemoryMemory`、`createMemory`、`createMemoryTools`，**所以**转发记忆模块。
3. **语法写法的原因**：同条目 1。
4. **内部逻辑分步讲解**：加载时转发 memory.js 的全部导出。
5. **触发条件**：同上。
6. **最终作用**：记忆三件套 + 4 个记忆工具生成器可从包名直接导入。
7. **使用场景**：butler-core（管家记忆）、db 包（实现 Memory 接口）、装配代码。
8. **缺陷/注意事项**：无特别——转发是透明的，注意事项都在源文件（03 文档）。

### 核心条目 4：`export * from './capability.js'`（转发能力适配器）

1. **名称**：第四行转发语句。
2. **设计的根本原因**：**因为**领域包（chef/cleaner）的工具工厂要拿 `defineDomainTool` 和 `DomainTool` 类型，**所以**转发能力适配器。
3. **语法写法的原因**：同条目 1。
4. **内部逻辑分步讲解**：加载时转发 capability.js 的全部导出。
5. **触发条件**：同上。
6. **最终作用**：`defineDomainTool`、`DomainTool`、`DomainToolResult` 三件套等可从包名直接导入。
7. **使用场景**：chef/cleaner 的 tools.ts、一切新领域能力接入。
8. **缺陷/注意事项**：无特别。

### 核心条目 5：`export * from './sub-agent.js'`（转发子 Agent 基类）

1. **名称**：第五行转发语句。
2. **设计的根本原因**：**因为** `defineSubAgent` 是子 Agent 开发者的主入口、`SubAgent/SubAgentSpec` 是贯穿管家与领域包的核心类型，**所以**转发子 Agent 基类——**这是 5 个转发里使用频率最高的一行**。
3. **语法写法的原因**：同条目 1。
4. **内部逻辑分步讲解**：加载时转发 sub-agent.js 的全部导出。
5. **触发条件**：同上。
6. **最终作用**：`defineSubAgent`、`SubAgent`、`SubAgentSpec`、`ButlerTool` 可从包名直接导入。
7. **使用场景**：chef/cleaner 的 index.ts（declare 自己）、butler-core（收成品）。
8. **缺陷/注意事项**：无特别。

## 模块3：文件内每一个参数超详细说明

> 本文件**没有任何参数、变量、常量**——它是纯转发文件。为了不违反"逐参数解析"的要求同时不虚构内容，这里如实说明"为什么本文件没有参数"，并说明被转发成员的参数不在本文件解析（在各自详解文档里）。

1. **本文件为什么没有参数**：**因为**它的全部工作是"把别的文件的导出集合转发出去"，转发语句 `export * from '...'` 的语法里根本没有可传的东西——**没有业务逻辑就没有数据进出，没有数据进出就没有参数**。这不是偷懒，而是这类文件的正确形态：**出口文件一旦自己长出逻辑，出口和实现就搅在一起了**（改实现会动出口、动出口会惊动所有使用方），恰恰是"零逻辑"保护了包的内部自由。
2. **被转发成员的参数去哪了**：比如 `createTaskId(agentId)` 的 agentId、`createMemoryTools(memory, namespace)` 的两个参数，它们属于**源文件**的详细说明——分别在 01/03/04/05 文档的模块3里逐个拆解，本文件不重复（文档职责单一，避免同一内容两处维护、两处失真）。

## 模块4：文件关键逻辑 & 特殊代码说明

> 本文件没有 if/循环/异常捕获等逻辑段。唯一需要"专门讲清为什么"的是两条语法级规定，单独说明如下。

### 1、为什么每个路径都要写 `.js` 后缀——语法强制，不是风格偏好

**因为**工程的 TypeScript 编译配置是 `module: NodeNext` + `moduleResolution: NodeNext`（见 `tsconfig.base.json`），这套配置下 TS 完全按 **Node.js 原生 ESM 的规则**处理模块：Node 的 ESM 加载器**不像 CommonJS 那样自动补全扩展名**，import 路径必须写到具体文件（含扩展名）；而 TS 源码将来编译成 .js 运行，**所以**源码里就要写"编译后的名字" `.js`（编译器自动把 `./protocol.js` 映射到 `./protocol.ts` 源文件）。**如果不写 .js**：编译阶段直接报错（TS2571 类错误——NodeNext 模式下模块解析失败），**连编译都过不去**；就算绕过去，运行时 Node 也会报 ERR_MODULE_NOT_FOUND。这是"语法/工程规范强制要求必须这么写"的教科书案例。

### 2、为什么用 `export *` 而不是逐个列出成员名

**因为**被转发的文件（如 protocol.ts）导出成员有几十个，逐个列出意味着"源文件每加一个导出，出口文件要同步加一行"——必然出现漏同步（新成员外面 import 不到，还以为是 bug）；**所以**用全量转发，源文件的导出集合自动同步到出口。**代价**是失去"出口白名单"的管控（源文件导出什么外面就看得见什么）——**对策**是源文件自觉（不该暴露的成员不加 export），这套分工在本包里执行得很干净。

### 3、为什么转发顺序是 protocol → model → memory → capability → sub-agent

**因为** JS 的 `export * from` 执行顺序是按书写顺序加载的：protocol 和 capability 无内部依赖（先加载无风险）→ memory 依赖 capability → sub-agent 依赖 protocol/model/memory。**当前顺序恰好与依赖方向兼容**（依赖别人的排在后面或同批加载都可行，ESM 会自动处理循环外的顺序）；更重要的是这个顺序与"阅读顺序"一致（01→05 文档的编排），维护者看出口清单就能看出包的层次。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 使用方代码执行 `import { defineSubAgent } from '@meimaohouse/agent-sdk'`；
2. Node 按 package.json 的 `exports`/`main` 定位到 `dist/index.js`（本文件的编译产物）；
3. 本文件依次执行 5 行转发 → 5 个功能文件的编译产物被加载（各自的顶层定义随之生效）；
4. 使用方从本包出口拿到所需成员，import 完成。
5. **注意**：整个加载过程无任何模型加载（04 文档的"零绑定"从这里就开始成立——出口文件只转发，不触发任何厂商 SDK 加载）。

### 2、文件在整个工程中不可替代的作用

**它是包的"门面与合同"**：对外只有一个稳定地址，对内可以自由重构——这正是 npm 包工程的标准形态。没有它，包不成立（入口不可达）；改它 = 改变全工程使用方的可见范围。

### 3、运行依赖的环境与前置条件

- 依赖本包 5 个功能文件全部编译就位（`dist/` 目录存在且完整）；
- 前置条件：使用方的 Node 环境支持 ESM（工程 `"type": "module"`，Node 14+ 均可）；
- 自身无任何第三方依赖。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **桶文件模式**（`export * from` 清单 + package.json exports 指向）：任何 TS 包的出口层标准写法，工程内其他包（db、butler-core）也是同款结构。

### ⚠️ 易错点

1. **新建了源文件但忘了在 index.ts 加转发**：症状是"明明编译过了，外面 import 不到"——先查出口清单有没有那一行；
2. **转发语句写了 `.ts` 后缀**：TS 的 NodeNext 规则要求写编译后名字 `.js`，写 .ts 编译报错；
3. **两个文件导出同名成员**：`export *` 冲突会让那个名字变成不可用——起名时按文件前缀区分。

### 🔍 调试关键点

- **"找不到模块 '@meimaohouse/agent-sdk'"**：多半是包没构建（dist 不存在）——去包目录跑 `npm run build`；
- **"某成员不是函数/undefined"**：查是否同名冲突或忘了转发；
- **改动包内结构后外面报错**：出口清单与 package.json 的 exports 要一起核对。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| 5 行转发的成员覆盖面 | 🚫 不能随意删 | 管家/厨师/清洁工按包名 import 这些成员，删一行 = 使用方集体编译报错 |
| `.js` 后缀写法 | 🚫 不能改成 .ts 或省略 | NodeNext 语法强制（见模块4第 1 条） |
| 文件头注释 | ✅ 可更新 | 包内新增大模块时同步一句，保持简介准确 |
| 改为逐成员具名转发（白名单） | ✅ 可优化（有代价） | 换来出口管控，代价是每次新增导出要同步——除非要收口 API，否则维持现状最省心 |
