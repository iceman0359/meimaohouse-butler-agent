# 05 · sub-agent.ts 源码白话详解（子 Agent 基类与组装线）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`sub-agent.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agent-sdk/src/sub-agent.ts`
- 编译产物：`packages/agent-sdk/dist/sub-agent.js`

### 2、文件存在的核心原因

**因为**前面四个文件各自造好了零件——协议信封（01）、工具包装流水线（02）、记忆模块（03）、模型工厂（04）——但**零件不会自己组装成能干活的工人**；而每个子 Agent 要做的事又高度雷同：接任务信封、开独立工作间、用模型思考、调工具干活、按结果信封交差。如果每个子 Agent 都手写一遍这套流程，既重复又会各写各的、格式走样。**所以**必须有这条"组装线 + 操作手册"：子 Agent 开发者只需填一张"身份登记表"（SubAgentSpec：我叫什么、管什么领域、擅长什么、有什么本领），其余全部自动装配。

文件头注释把封装内容总结为 4 件套：① 用自己的 model + systemPrompt + tools 构建独立 Strands Agent（每次任务隔离）；② 约定结构化输出为 ResultEnvelope（Zod 校验，SDK 自动重试）；③ handleTask(task)：以任务信封为入参返回结果信封；④ toButlerTool()：把本子 Agent 包装成管家可调用的工具（Agent-as-Tool 模式）。

**如果没有这个文件，程序会出现的问题：** 每个领域包都要手写 Agent 创建、信封校验、异常兜底、工具包装全套代码；漏写兜底的子 Agent 一炸就把管家的对话带崩；输出格式不统一导致管家无法统一转述。

### 3、文件的整体定位

这个文件是 `agent-sdk` 的**总装车间**：对外只有一个入口函数 `defineSubAgent`（填表 → 领一个装配完整的子 Agent），内部负责把协议、工具、记忆、模型四个零件拼起来，并定义子 Agent 与管家的对接方式。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- `@strands-agents/sdk`：`Agent`（框架的智能体底座——真正"会思考的工人"类）和 `tool`（造工具的工厂）；
- `./model.js`：`getModel`（兜底取模型）+ `ModelInstance` 类型；
- `./protocol.js`：任务/结果信封校验器、`createTaskId`、相关类型——对接管家的全部"表格"；
- `./memory.js`：`Memory` 类型 + `createMemoryTools`（有记忆就给 Agent 挂记忆工具）。

**谁来调用它（下游）：**

- `packages/agents/chef/src/index.ts` 和 `packages/agents/cleaner/src/index.ts`：两个领域 Agent 都用 `defineSubAgent({...})` 声明自己（厨师那份填表代码是最佳参考样例）；
- `packages/butler-core/butler.ts`：管家的注册表收的就是这里产出的 `SubAgent` 对象，并调用其 `toButlerTool()`（Agent-as-Tool）；
- 测试代码：直接调 `handleTask` 测子 Agent。

**一句话：这是 SDK 的"总装出口"，一个 defineSubAgent 调用 = 一个完整子 Agent。**

## 模块2：文件内核心定义与核心函数超详细说明

### 核心定义 1：`ButlerTool`（管家工具类型别名）

1. **名称**：`ButlerTool`，写法 `export type ButlerTool = ReturnType<typeof tool>`。
2. **设计的根本原因**：**因为** `tool()` 是框架的造工具工厂，它返回的类型名 SDK 没有公开承诺，**所以**用"函数返回值类型推导"拿到这个类型并起短名（与 02 文档的 `DomainTool` 同款手法）。注释原话："由 tool() 工厂推导，避免依赖 SDK 未公开的类型名"。
3. **语法写法的原因**：**因为** TypeScript 的 `ReturnType<>` 能在编译期自动算出函数返回类型，**所以**不必手抄 SDK 内部类型名——SDK 内部改名也不受影响。
4. **内部逻辑分步讲解**：一行纯类型定义，编译后消失。
5. **触发条件**：不运行；`SubAgentSpec.tools`、`toButlerTool()` 返回值的类型标注处引用。
6. **最终作用**：全工程对"包装好的工具"一个说法。
7. **使用场景**：`SubAgentSpec.tools` 参数、管家注册工具列表。
8. **缺陷/注意事项**：与 `DomainTool` 是两个独立别名（同一个底层类型）——语义上一个指"领域本领工具"、一个指"挂到管家身上的工具"，分开命名是为了读代码时能区分角色。

### 核心定义 2：`SubAgentSpec`（子 Agent 身份登记表）

1. **名称**：`SubAgentSpec`，接口，8 个字段：`id`、`name`、`domain`、`description`、`systemPrompt`（必填）+ `tools`、`model`、`memory`（可选）。
2. **设计的根本原因**：**因为**组装一个子 Agent 所需的全部"个性化信息"必须有一个标准的收集格式——必填的是身份与规则（是谁、管哪摊、怎么找他干活、按什么规矩干活），可选的是装配选项（本领、大脑、记性，不填有合理默认），**所以**定义这张表。**这是新子 Agent 开发者唯一要填的东西**——填好表，其余全自动。
3. **语法写法的原因**：
   - **因为**TypeScript 接口语法要求必填项不加 `?`、可选项加 `?`，**所以** 5 个必填 3 个可选的区分直接写在类型上——漏填必填项编译期就报错（第一道防线）；
   - **因为**"本领列表"可能暂时没有（空壳 Agent），**所以** `tools?: ButlerTool[]` 可选；
   - **因为**模型通常走全局配置（getModel 兜底）、特殊场景才注入，**所以** `model?: ModelInstance` 可选；
   - **因为**记忆是可选能力，**所以** `memory?: Memory` 可选。
4. **内部逻辑分步讲解**（8 个字段逐个看，详细参数解析见模块3）：
   - `id`：唯一标识，注释明确格式要求"小写字母开头，仅允许 a-z 0-9 _ -"——它同时是任务信封的 domain 值、记忆命名空间、工具名后缀；
   - `name`：展示名（如"厨师"）——给人看的名字；
   - `domain`：领域名（如"厨房域"）——描述管辖范围；
   - `description`：**能力描述**——注释特别强调"管家模型靠它决定何时派活给你……写不好 = 管家找不到你"，这是整张表最重要的自由文本；
   - `systemPrompt`：领域职责与判断规则——注释强调"不要写历史数据/对话记录，记忆走 Memory"（岗位说明书只写规矩，不写流水账）；
   - `tools` / `model` / `memory`：三个装配选项。
5. **触发条件**：不运行；`defineSubAgent(spec)` 的入参类型。
6. **最终作用**：新子 Agent 的接入成本降为"填一张表"。
7. **使用场景**：chef/cleaner 的 index.ts、未来一切新领域 Agent。
8. **缺陷/注意事项**：description 写得好坏直接影响管家派活准确率——它会被拼进管家的工具描述（见 toButlerTool），不是"给人看的注释"而是"给 AI 看的广告位"。

### 核心定义 3：`SubAgent`（装配完成的成品规格）

1. **名称**：`SubAgent`，接口，4 个成员：`spec`、`createAgent()`、`handleTask(task)`、`toButlerTool()`。
2. **设计的根本原因**：**因为**调用方（管家、测试）需要以统一方式使用任何子 Agent——看身份表、开工作间、直接派任务、包装成管家工具——**所以**定义成品的"操作面板"：4 个成员就是对外提供的全部按钮。
3. **语法写法的原因**：
   - **因为**TypeScript 接口里可以声明方法签名（参数类型 + 返回类型），**所以** 3 个方法的契约直接写在类型上——实现不符编译报错；
   - **因为** `handleTask` 内部要调模型（网络等待），**所以**签名是 `Promise<ResultEnvelope>`（异步承诺）——**语法硬要求**：异步操作必须以 Promise 表达，调用方必须 await；
   - **因为** `createAgent`/`toButlerTool` 是同步动作，**所以**不带 Promise。
4. **内部逻辑分步讲解**：`spec` 原样保存登记表（身份可查）；`createAgent()` 开一个新工作间；`handleTask(task)` 收信封干活交差；`toButlerTool()` 产出挂到管家身上的工具。
5. **触发条件**：`defineSubAgent` 返回值即此形状。
6. **最终作用**：任何子 Agent 在管家和测试手里用法完全一致——这就是"多态"带来的统一。
7. **使用场景**：管家注册表存 `Map<string, SubAgent>`；测试直调 handleTask。
8. **缺陷/注意事项**：`createAgent` 对外暴露意味着调用方可以绕过 handleTask 手动开工作间——除非知道自己在干嘛，否则统一走 handleTask。

### 核心函数 1：`defineSubAgent(spec)`（总装车间入口）

1. **函数名称**：`defineSubAgent`，入参 `spec: SubAgentSpec`，返回 `SubAgent`。
2. **函数设计的根本原因**：**因为**"登记表 → 验表 → 配记忆工具 → 定义三个方法 → 交付成品"这套组装流程每个子 Agent 都要完整走一遍，**所以**必须封装成单一入口函数；**且验表必须前置**（身份信息错了，越晚发现越难查——错误会在模型调用深处才爆出来），**所以**验表逻辑放最前面。**不封装的弊端**：每个领域包复制粘贴组装代码，一处升级处处漏改。
3. **函数语法写法的原因**：
   - **因为**组装动作本身是同步的（创建 Agent 实例推迟到了 createAgent 里，这里只是"定义怎么造"），**所以**它是同步函数——返回承诺反而会误导调用方以为这里有异步操作（懒加载设计，注释明确写了"defineSubAgent 只是声明，不创建模型/Agent"）；
   - **因为**内部三个方法（createAgent/handleTask/toButlerTool）都要访问 spec、memory、tools 这些局部变量，**所以**用闭包定义在函数体内——把配置"关"在自己身边。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：**验表**——5 个 if 检查（详见模块4第 1 条）：id 过正则、description/name/domain/systemPrompt 都不能是空白；任何一项不过直接 throw 带具体原因的中文错误；
   - 第 2 步：**收敛配置**——`const memory = spec.memory`、`const tools = [...(spec.tools ?? []), ...(memory ? createMemoryTools(memory, spec.id) : [])]`：本领列表 = 你声明的本领 + （有记忆就自动追加的 4 个记忆工具）。**两个语法点**：`?? []` 是"没传本领就当空数组"（否则展开 undefined 直接报错）；三元表达式决定"没配记忆就不产生记忆工具"（**与工程原则一致：没有的能力绝不假装有**）；
   - 第 3 步：**定义 createAgent 闭包**（详见核心函数 2）；
   - 第 4 步：**定义 handleTask 闭包**（详见核心函数 3）；
   - 第 5 步：**定义 toButlerTool 闭包**（详见核心函数 4）；
   - 第 6 步：`return { spec, createAgent, handleTask, toButlerTool }`——交付成品。
5. **函数的触发条件**：领域包的 `createChefAgent` / `createCleanerAgent` 等工厂函数调用它（应用启动装配阶段）。
6. **函数的最终作用**：产出一张"验明正身、装备齐全、待命"的子 Agent 成品。
7. **函数的使用场景**：一切子 Agent 的出生地；管家不直接调它（管家收成品）。
8. **函数的缺陷/注意事项**：它是同步纯函数——调用两次会得到两个独立成品（id 相同会撞名），同一 id 只应 define 一次。

### 核心函数 2：`createAgent`（开新工作间——闭包方法）

1. **函数名称**：`createAgent`（defineSubAgent 内部定义），无参数，返回 `Agent`（框架智能体实例）。
2. **函数设计的根本原因**：**因为**本工程的核心设计是"**每次任务用独立 Agent 实例**"（文件头注释第 1 条 + 00 总览红线 4）：不同任务的工作间必须互相隔离，A 任务的对话历史绝不能泄漏进 B 任务的上下文（串台 = 模型被无关信息污染、行为不可预测）；**所以**把"开工作间"封装成可反复调用的函数——每来一个任务调一次，用完即弃。
3. **函数语法写法的原因**：
   - **因为**它要访问外部的 spec/memory/tools（闭包），**所以**定义在 defineSubAgent 内部而不是模块顶层；
   - **因为** `new Agent({...})` 是同步构造（模型实例已由 getModel 兜底准备好——这就是 04 文档"异步造、同步取"存在的意义），**所以**它不需要 async。
4. **函数内部完整逻辑分步讲解**（Agent 构造参数逐个看）：
   - `id: spec.id`：工作间的工号；
   - `systemPrompt: buildSubAgentSystemPrompt(spec, memory)`：岗位说明书（详见核心函数 5）——每次开间都重新拼一次，**因为**说明书内容取决于 spec 和 memory 是否存在，统一走一个函数保证口径一致；
   - `tools`：本领 + 记忆工具（组装线第 2 步备好的）；
   - `model: spec.model ?? getModel()`：**兜底链**——登记表里显式给了模型就用给的，没给就从模型工厂领全局配置的（04 文档核心函数 8）；**为什么在这里兜底而不是 defineSubAgent 时**：**因为** getModel 在未配置时会抛错，如果提前到 defineSubAgent，"只是声明但还没用"的空壳 Agent 也会炸——推迟到"真要开间"才检查，**懒加载**（注释："懒加载：defineSubAgent 只是声明，不创建模型/Agent；每次 handleTask 才创建 Agent"）；
   - `structuredOutputSchema: ResultEnvelopeSchema`：**强制交差格式**——告诉框架"最终回答必须能通过结果信封校验"，不合格框架会自动让模型重试（文件头注释第 2 条："Zod 校验，SDK 自动重试"）；**这是"不做假成功"的技术兜底**：模型想随口说两句糊弄过关，格式关就过不去；
   - `printer: false`：关掉框架自带的控制台打印——**因为**子 Agent 在后台干活，过程细节不该刷到用户屏幕上（人类只见管家的转述），打印会污染命令行输出/日志。
5. **函数的触发条件**：`handleTask` 每处理一个任务调一次；测试代码也可直调。
6. **函数的最终作用**：产出一个配置完整、格式受控、上下文干净的一次性工作间。
7. **函数的使用场景**：handleTask 内部（主用户）；需要精细控制对话过程的测试。
8. **函数的缺陷/注意事项**：每次开间都有构建成本（拼提示词、装配工具）——频繁小任务下这个开销可忽略，但不要在循环里无意义地反复开间干同一件事。

### 核心函数 3：`handleTask(input)`（接单干活交差——闭包方法）

1. **函数名称**：`handleTask`，入参 `input: TaskEnvelope`（任务信封），返回 `Promise<ResultEnvelope>`（结果信封的异步承诺）。
2. **函数设计的根本原因**：**因为**"校验入参 → 开间 → 干活 → 提取结果 → 补全字段 → 兜底异常"是一条完整的作业流程，必须有一个**无论内部怎么炸、对外永远交出一张合法结果信封**的总闸函数——管家靠它才能放心派活（管家不该担心子 Agent 直接抛异常把自己带崩）；**所以**整个流程包在 try/catch 里、所有失败路径都折算成 `status: 'failed'` 的结果信封。
3. **函数语法写法的原因**：
   - **因为**内部要 await 模型推理（网络等待），**所以**必须是 async 函数、返回 Promise（语法硬要求）；
   - **因为**入参来自两个渠道（管家适配器、测试直调），来源数据可能不规范，**所以**第一件事是用 `TaskEnvelopeSchema.parse(input)` 过审（Zod 语法：parse 不合格直接抛错）。
4. **函数内部完整逻辑分步讲解**：
   - 第 0 步（try 之前）：**先记下保底编号**——`fallbackTaskId = input && typeof input.task_id === 'string' && input.task_id ? input.task_id : 'unknown'`：**为什么要在校验前先干这个**：**因为**如果信封本身是坏的（parse 会抛错），此时还没有合法的 task_id 可用，catch 里总要有个编号能写进失败结果——先把能拿到的编号抄在手心，炸了也不至于两张单子对不上号；
   - 第 1 步：`TaskEnvelopeSchema.parse(input)`——信封过审（缺 task_id/domain、字段类型不对都在这里打回）；
   - 第 2 步：`await createAgent().invoke(JSON.stringify(task))`——开一个新工作间，把信封**序列化成 JSON 文本**喂给模型（**为什么 stringify**：模型只能读文本，不能读 JS 对象；把整张信封给它是**因为** intent/params/priority 等字段都是模型决策的依据）；
   - 第 3 步：`const envelope = (raw as { structuredOutput?: ResultEnvelope }).structuredOutput`——从框架返回值里取"结构化输出"（框架按第 2 步配置的 schema 收口后的产物）；**为什么要 `as` 断言 + 可选链式的问号**：**因为**类型层面框架没有承诺这个字段一定存在（万一模型重试多次仍不合格），**所以**按"可能有、可能没有"处理；
   - 第 4 步：`if (!envelope)`——没拿到结构化结果 → 返回一张 `failed` 结果信封（summary："厨师未返回结构化结果"，error 写明 structuredOutput 为空）——**宁可明确失败，不许含糊成功**；
   - 第 5 步：拿到结果 → `return { ...envelope, task_id: task.task_id, completed_at: envelope.completed_at ?? new Date().toISOString() }`——**强制回填 task_id**（用任务信封里的编号覆盖，**防止模型报错号或漏号**——信封编号的唯一来源必须是系统，不能信模型）；完成时间没填就补当前时间（**为什么 `??`**：模型不填是常态，系统兜底让下游永远有时间可用）；
   - 第 6 步（catch）：任何异常（parse 失败、模型超时、框架异常……）→ 返回 `failed` 信封：task_id 用第 0 步的保底编号，error 用 `err instanceof Error ? err.message : String(err)` 转成文本（与 02 文档同款转译技巧）。
5. **函数的触发条件**：管家的 delegate 直派流程；子 Agent 自身工具（toButlerTool 的 callback）内部；测试直调。
6. **函数的最终作用**：无论成功失败，输出一张合法、带编号、带完成时间的结果信封——管家的"永不崩"依赖从这里建立。
7. **函数的使用场景**：管家 delegate、toButlerTool、测试。
8. **函数的缺陷/注意事项**：它把所有失败都折算成"正常返回"，调用方**必须**按 status 分支处理，不能假设"返回 = 成功"。

### 核心函数 4：`toButlerTool()`（包装成管家的工具——Agent-as-Tool）

1. **函数名称**：`toButlerTool`，无参数，返回 `ButlerTool`。
2. **函数设计的根本原因**：**因为**管家模型不会"派任务信封"这种抽象动作——它只会**调用工具**；**所以**必须把子 Agent 伪装成一个工具：工具名字叫 `subagent_chef`、描述写着"厨师（厨房域）。……需要该领域的能力时，调用此工具派发任务"、入参格式就是派活单（TaskRequestSchema）。管家模型填派活单 = 点名这个子 Agent。**这就是 Agent-as-Tool 模式的落地**。**为什么不直接把 handleTask 给管家**：handleTask 要的是完整信封（含 task_id/domain），**而这两个是系统字段，不能让管家模型编**——**所以**工具入参刻意收窄为 TaskRequestSchema（模型只填业务格子），系统格子由 callback 里的代码补全（01 文档"派活单 vs 任务信封"分工的落地处）。
3. **函数语法写法的原因**：
   - **因为**要调框架的 `tool()` 工厂并传入校验器，**所以** callback 的入参类型与 TaskRequestSchema 对齐（`input: TaskRequest`）；
   - **因为**内部要 await handleTask，**所以** callback 是 async（语法硬要求）；
   - **因为**这是闭包方法，**所以**能直接访问 spec/handleTask。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：`tool({ name: \`subagent_${spec.id}\`, description: ..., inputSchema: TaskRequestSchema, callback })`——工具名加 `subagent_` 前缀（**为什么**：管家的工具列表里还有记忆工具等杂项，前缀让"派活给子 Agent"的工具一眼可辨，也避免与别的工具重名）；描述由"名字（领域）。能力描述 + 派活指引"拼成——**这段描述是管家模型决定"派不派、什么时候派"的全部依据**；
   - 第 2 步（callback 内）：`const task = { ...input, task_id: createTaskId(spec.id), domain: spec.id }`——把模型填的派活单展开，补上系统生成的任务编号（03/01 文档的函数在此上岗）和目标领域（就是自己的 id）；
   - 第 3 步：`const result = await handleTask(task)`——完整作业流程启动（开间、干活、交差）；
   - 第 4 步：`return JSON.stringify(result)`——把结果信封序列化成文本交回管家模型。注释原话："返回 JSON 字符串，模型在下一轮推理中可读到结构化内容"——**为什么返回文本而不是对象**：管家模型只能读文本；**为什么保留 JSON 结构**：下一轮推理时模型能按字段读懂状态/建议，转述和转派才有依据。
5. **函数的触发条件**：管家启动装配阶段调用一次（把返回的工具挂进管家 Agent 的工具列表）；之后每次管家模型决定派活，框架自动执行它的 callback。
6. **函数的最终作用**：子 Agent 从此对管家而言"就是一个工具"——派活的入口、格式的约束、编号的生成、隔离的执行全部封装在这一个工具背后。
7. **函数的使用场景**：管家核心的注册表装配（README 架构图："子 Agent 注册表 → 每个子 Agent 包装成一个 tool()"）。
8. **函数的缺陷/注意事项**：工具名 `subagent_${id}` 依赖 id 合法（验表第 1 步保证）；管家模型一次填错 params 时，错误会在子 Agent 内部被折算成 failed 信封返回——管家能收到失败原因，但那轮派活已消耗一次模型调用。

### 核心函数 5：`buildSubAgentSystemPrompt(spec, memory)`（岗位说明书组装器）

1. **函数名称**：`buildSubAgentSystemPrompt`，入参 `spec: SubAgentSpec` 和 `memory?: Memory`，返回 `string`。
2. **函数设计的根本原因**：**因为**子 Agent 的"规矩"由两部分拼成——领域自述（spec.systemPrompt，各不相同）+ 全体子 Agent 共守的工作纪律（格式要求、不造假、单任务原则，人人相同）；**又因为**有没有记忆会影响一条纪律（有记忆才提醒"重要事实写记忆"），**所以**需要一个统一的组装器把"固定纪律 + 领域自述 + 条件条款"拼成一份完整说明书。**不封装的弊端**：每家纪律口径不一，格式崩坏、造假横行。
3. **函数语法写法的原因**：
   - **因为**它只被本文件使用，**所以**不加 export（模块私有函数——收窄可见面，防止外部误用）；
   - **因为**说明书本质是多行文本，**所以**用"数组装行 + join('\n') 连接"的写法——比一长串字符串拼接可读性好、增删行只动数组；
   - **因为**memory 参数只是"要不要多加一条"的开关，**所以**声明为可选、函数体内 if 判断。
4. **函数内部完整逻辑分步讲解**（说明书内容逐行看）：
   - 第 1 行：`你是庄园的${spec.name}，${spec.domain}由你全权负责。`——身份宣示（名字和领域插进去）；
   - 空行 + `spec.systemPrompt`——领域自述原样嵌入（登记表里的职责与规则）；
   - 空行 + "工作要求：" + 4 条纪律：
     - "收到的是任务信封（TaskEnvelope），按 intent 判断意图，必要时调用工具完成"——教它怎么读单子；
     - "必须以 ResultEnvelope 格式返回：status(summary 用面向人的一句话) + detail(结构化) + suggestions(需要其他子 Agent 协作时提出，由管家转派)"——交差格式，与 01 文档协议严格对齐（**双保险**：既在 structuredOutputSchema 里强制格式，又在说明书里教格式）；
     - "不要编造数据：工具没返回的信息，明确写'暂无数据'"——**工程红线"不做假成功"在模型层面的执行令**；
     - "一次只处理一个任务，不要臆测任务之外的请求"——防跑偏（工作间是一次性的，别自作主张干别的）；
   - 条件条款（if memory）：你有长期记忆可用，重要事实（库存、计划、偏好）写入记忆，而不是留在对话里——**为什么这条要条件化**：没有记忆工具的 Agent 被要求"写记忆"只会困惑或幻觉出工具调用报错。
5. **函数的触发条件**：每次 `createAgent()` 开工作间时被调用（每个任务拼一次）。
6. **函数的最终作用**：产出一份身份明确、纪律统一、条款贴合配置的岗位说明书——子 Agent 行为一致性的源头。
7. **函数的使用场景**：仅 createAgent 内部；想统一调整全体子 Agent 纪律时改这一个函数即可。
8. **函数的缺陷/注意事项**：纪律文案与协议字段名（TaskEnvelope/ResultEnvelope/status/suggestions）是"文字联动"——改协议字段名时这里要同步（文字失效模型就教错了）。

## 模块3：文件内每一个参数超详细说明

> SubAgentSpec 的 8 个字段是本文件的参数主体，逐个拆解；函数内部参数在模块2的步骤讲解里已随行说明（input/fallbackTaskId/raw/envelope/err），此处对仍有独立意义的补足维度。

### 参数 1：`id`（子 Agent 唯一标识）

1. **名称 + 类型**：`id`，字符串（string），必填。
2. **参数设计原因**：**因为**这个标识要在四处被当作"名字"复用——任务信封的 domain、生成的任务编号第一段、记忆工具的命名空间、管家工具名后缀（subagent_xxx）——**没有唯一且格式合法的 id，这四处全部失灵**，**所以**它是登记表第一项且必须验格式。
3. **参数类型选择原因**：**因为**它要拼进字符串、要当 Map 的键、要过正则校验，**所以** string；**为什么用正则 `/^[a-z][a-z0-9_-]*$/` 卡格式**：小写开头保证在 URL/文件名/键名等场景安全（不与大小写敏感系统冲突），限定字符集杜绝空格和特殊符号进各种拼接场景。
4. **参数的传入来源**：领域包开发者填（chef/cleaner）。
5. **参数的内部使用逻辑**：验表 → 进 spec 原样保存 → createTaskId(spec.id) / createMemoryTools(memory, spec.id) / `subagent_${spec.id}` / domain: spec.id 四处复用。
6. **参数的取值范围**：小写字母开头，仅 a-z 0-9 _ -；其余（空串、大写开头、含空格/中文）一律 throw。
7. **参数的最终作用**：子 Agent 在全工程的"身份证号"。

### 参数 2：`name`（展示名）

1. **名称 + 类型**：`name`，字符串（string），必填。
2. **参数设计原因**：**因为**说明书第一句（"你是庄园的厨师"）、失败结果（"厨师未返回结构化结果"）、管家工具描述都以它出场，**没有它，人和 AI 都没法自然地称呼这个 Agent**。
3. **参数类型选择原因**：**因为**它是给人（和模型）看的自然语言名词（如"厨师"），**所以** string；用 `.trim()` 验非空——纯空格等于没填。
4. **参数的传入来源**：领域包开发者填。
5. **参数的内部使用逻辑**：验表 → 说明书第一句 → handleTask 的兜底 summary → toButlerTool 描述开头。
6. **参数的取值范围**：任何非空白字符串；惯例为两三个字的中文角色名。
7. **参数的最终作用**：Agent 的"人设名片"。

### 参数 3：`domain`（领域名）

1. **名称 + 类型**：`domain`，字符串（string），必填。
2. **参数设计原因**：**因为**管家转述时要能说清"这是厨房域的事"，工具描述也要标明管辖范围，**所以**需要比 id 更"说人话"的领域称呼。**注意区分**：协议里的 `domain` 字段（任务信封）值是 **id**（chef），而这里的 `domain` 是**领域中文名**（"厨房域"）——同名不同义，读代码时容易混。
3. **参数类型选择原因**：**因为**是自然语言标签，**所以** string + trim 非空。
4. **参数的传入来源**：领域包开发者填。
5. **参数的内部使用逻辑**：验表 → toButlerTool 描述（"厨师（厨房域）"）→ 说明书身份句。
6. **参数的取值范围**：任何非空白字符串。
7. **参数的最终作用**：Agent 管辖范围的"对外门牌"。

### 参数 4：`description`（能力描述）

1. **名称 + 类型**：`description`，字符串（string），必填。
2. **参数设计原因**：**因为**管家模型决定"这句话该派给谁"的唯一依据就是各子 Agent 的能力描述——描述含糊 = 管家派错门或漏派，**所以**注释用了最重的语气："管家模型靠它决定何时派活给你，必须写清：'负责什么 + 典型任务意图有哪些'。写不好 = 管家找不到你。"
3. **参数类型选择原因**：**因为**是给 AI 读的自然语言说明书，**所以** string + trim 非空（内容质量代码管不了，但空描述必须挡住）。
4. **参数的传入来源**：领域包开发者填（厨师的范例："掌管厨房域：冰箱库存与食材新鲜度、食材采购……"——范围 + 意图清单式写法）。
5. **参数的内部使用逻辑**：验表 → 原样拼进 toButlerTool 的工具描述（管家模型每次决策都读）。
6. **参数的取值范围**：任何非空白字符串；写法惯例"负责什么领域 + 典型意图动词短语列表"。
7. **参数的最终作用**：子 Agent 在管家面前的"招聘广告"，派活准确率的决定因素。

### 参数 5：`systemPrompt`（领域职责与规则）

1. **名称 + 类型**：`systemPrompt`，字符串（string），必填。
2. **参数设计原因**：**因为**每个领域的干活规矩只有领域开发者自己知道（厨师要懂食材判断、清洁工要懂区域划分），SDK 没法替他写，**所以**留这个"自述区"；**为什么注释强调"不要写历史数据/对话记录"**：**因为**工作间是一次性的，写进说明书的"历史"会变成每单都带的死数据，既浪费上下文预算又会过期失真——动态数据该走记忆（03 文档）。
3. **参数类型选择原因**：**因为**说明书是多行自然语言文本，**所以** string；trim 非空兜底。
4. **参数的传入来源**：领域包开发者填（厨师的范例里连"当前可用能力：无"都写清了，还规定了 unavailable 时必须带 error_code）。
5. **参数的内部使用逻辑**：验表 → buildSubAgentSystemPrompt 嵌入说明书中段（身份句之后、统一纪律之前）。
6. **参数的取值范围**：任何非空白字符串；惯例为"工作范围 + 行为准则"两段式。
7. **参数的最终作用**：子 Agent 的"岗位规章"，领域专业性的全部来源。

### 参数 6：`tools`（本领列表）

1. **名称 + 类型**：`tools`，`ButlerTool[]`（工具数组），可选。
2. **参数设计原因**：**因为**领域本领（查库存、下单）是领域包用 defineDomainTool 造好后带进来的，**所以**登记表要有地方挂它们；**因为**空壳 Agent（没注入能力）合法且是工程默认形态，**所以**可选。
3. **参数类型选择原因**：**因为**本领是"一组"工具且数量不定，**所以**数组；元素类型 ButlerTool（框架工具类型）。
4. **参数的传入来源**：领域包的 createChefTools(options.capabilities) 等工厂产出——**注意**：没配对应能力实现时，工厂就少造/不造对应工具（"没有的能力不注册"）。
5. **参数的内部使用逻辑**：`[...(spec.tools ?? []), ...(memory ? createMemoryTools(...) : [])]`——与记忆工具合并成最终工具列表，传给每次 createAgent。
6. **参数的取值范围**：undefined 或工具数组；**注意**：传 `null` 会被 `??` 当成 undefined 处理（?? 只认 null/undefined 都算"没有"），但数组里混入非法元素不会被这里检查（信任上游包装器产出）。
7. **参数的最终作用**：子 Agent 的"双手"——能干什么活的物理边界。

### 参数 7：`model`（模型实例）

1. **名称 + 类型**：`model`，`ModelInstance`，可选。
2. **参数设计原因**：**因为**绝大多数场景统一走全局配置（04 文档），个别场景（某 Agent 想用更便宜的小模型、测试注入假脑）需要单独指定，**所以**可选、且不填有兜底（getModel）。
3. **参数类型选择原因**：**因为**要保证"塞进来的必须是框架认的模型"，**所以**类型必须是 ModelInstance（编译期把关）。
4. **参数的传入来源**：领域包工厂的 options.model → 应用装配时决定。
5. **参数的内部使用逻辑**：createAgent 里 `spec.model ?? getModel()`——有就用，没有现领。
6. **参数的取值范围**：undefined 或合法模型实例。
7. **参数的最终作用**：Agent 的"大脑型号"个性化通道。

### 参数 8：`memory`（记忆实现）

1. **名称 + 类型**：`memory`，`Memory` 接口，可选。
2. **参数设计原因**：**因为**记忆是可选能力（演示可无、生产要 SQLite 版），**所以**可选；**且它影响两处装配**——追加记忆工具（createMemoryTools）和说明书条件条款（buildSubAgentSystemPrompt），**所以**必须在组装期就确定。
3. **参数类型选择原因**：**因为**要兼容内存版/SQLite 版/未来任意实现，**所以**声明为接口类型（只认标准不认牌子，03 文档的核心设计）。
4. **参数的传入来源**：领域包工厂 options.memory → 应用装配时传入（Web 应用传 createSqliteMemory 的产物）。
5. **参数的内部使用逻辑**：defineSubAgent 第 2 步决定是否追加记忆工具；createAgent 时作为说明书开关传给 buildSubAgentSystemPrompt；最终被记忆工具的闭包捕获。
6. **参数的取值范围**：undefined 或 Memory 接口实现。
7. **参数的最终作用**：Agent 的"记性"开关与实现指定。

### 参数 9：`input`（handleTask 的入参）与 `task`（过审后的信封）

1. **名称 + 类型**：`input: TaskEnvelope`（调用方给的，可能不规范）；`task: TaskEnvelope`（parse 之后的，保证合规）——两个变量一先一后。
2. **参数设计原因**：**因为**入参来源不全是可信代码（测试直调、未来新调用方），**所以**"收到"和"过审"必须分成两个变量——用未校验的 input 干活是隐患。
3. **参数类型选择原因**：**因为**协议已定义信封类型，**所以**直接用 TaskEnvelope（不另造形状）。
4. **参数的传入来源**：toButlerTool 的 callback（管家派活）、管家 delegate、测试。
5. **参数的内部使用逻辑**：input 先被抄走 task_id 当保底 → parse 成 task → 后续全部用 task（stringify 喂模型、取 task.task_id 回填结果）。
6. **参数的取值范围**：能过 TaskEnvelopeSchema 的对象；过不了的进 catch 变 failed 信封。
7. **参数的最终作用**：整条作业流程的"原材料"。

### 参数 10：`raw` 与 `envelope`（模型产出与结构化结果）

1. **名称 + 类型**：`raw`（框架返回值，用 `as { structuredOutput?: ResultEnvelope }` 断言后的对象）；`envelope`（取出的结构化结果，可能 undefined）。
2. **参数设计原因**：**因为**框架的 invoke 返回值类型宽泛、且"模型一定交出合格结构"这个假设不可靠（schema 强制 + SDK 重试也只是降低概率，不是清零），**所以**必须"取出、判空、分路"。
3. **参数类型选择原因**：**因为** SDK 未公开承诺返回值形状，**所以**用类型断言声明期望形状并用可选标记（structuredOutput?）——诚实反映"可能有、可能没有"。
4. **参数的传入来源**：createAgent().invoke(...) 的返回。
5. **参数的内部使用逻辑**：envelope 为空 → 返回 failed 信封；非空 → 展开覆盖 task_id、补 completed_at 后返回。
6. **参数的取值范围**：envelope 为 undefined 或合法结果信封（框架按 schema 收口保证）。
7. **参数的最终作用**：模型"想法"到"合法交差单"的最后一道转换。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、开头的 5 连验表（5 个 throw）——为什么一个都不能少

**因为**登记表是"人手填的"，必然有手滑：id 大写开头（后面任务编号、键名、工具名全带毒）、description 空着（管家永远派不来活）、systemPrompt 空着（Agent 没规矩乱干活）……这些问题**必须在出生时拦下**——**如果删掉验表**：坏 Agent 能正常"出生"，错误推迟到某次任务执行时才以诡异方式爆发（比如正则没拦的 id 让记忆键变成 `小写混大写:xxx` 与数据对不上），排查成本高一个数量级。**语法说明**：正则 `/^[a-z][a-z0-9_-]*$/` 里 `^` 开头、`$` 结尾（整串匹配，不允许局部合格）、`test()` 返回布尔；`.trim()` 去首尾空白后判断真值（空串和纯空格都是假值）。

### 2、工具合并那行的两个防坑写法

`[...(spec.tools ?? []), ...(memory ? createMemoryTools(memory, spec.id) : [])]`
- **`spec.tools ?? []`**：**因为** tools 可选（undefined），**而**展开运算符 `...undefined` 会直接抛 TypeError，**所以**必须先兜底成空数组——语法强制；
- **三元表达式**：**因为**"没配记忆"必须落成"没有记忆工具"，而不是"带一个空记忆的工具"（那会骗模型"有记忆可用"），**所以**用三元直接决定"追加与否"——这正是工程"不做假成功/没有的能力不注册"原则在组装层的体现。

### 3、`structuredOutputSchema: ResultEnvelopeSchema` + 说明书里的格式教学——为什么要"双重约束"

**因为**模型是"可能不听话的学生"：只靠 schema（硬约束），格式错了框架重试，但模型不知道自己为什么错，重试效率低；只靠说明书（软约束），模型可能仍然跑偏。**所以**两手抓：schema 管底线（不合格过不去），说明书管认知（教它该怎么写）——重试少了、格式稳了。

### 4、`printer: false`——为什么要关打印

**因为**子 Agent 的工作过程属于"幕后"，人类只见管家的转述（工程核心原则"见面隔离"）；**如果**开着框架打印：CLI 界面被中间过程刷屏、Web 界面的对话流被混入无关文本。一行配置守住"人类只见管家"的体验边界。

### 5、handleTask 的"保底编号"先于 try——为什么顺序不能反

**因为** parse 在 try 里、且 parse 失败时手里还没有任何合法字段；**如果**把"抄编号"放在 parse 之后：信封是坏的时候 catch 里拿不到编号，只能写 'unknown'——失败结果与哪单对不上号。**所以**先抄再验，双保险。

### 6、结果信封的 task_id 强制覆盖（`{ ...envelope, task_id: task.task_id, ... }`）——为什么不信模型

**因为**模型返工时可能抄错编号、漏写编号——而编号是全链路对账的唯一钥匙（01 文档）；**所以**系统侧用入参信封的编号**无条件覆盖**模型的值。**展开顺序有讲究**：`...envelope` 在前、`task_id: task.task_id` 在后——后写的键覆盖先写的，这利用了 JS 对象展开"后者覆盖前者"的规则。

### 7、`completed_at ?? new Date().toISOString()`——为什么要补时间

**因为**模型不填完成时间是常态，而下游（管家记录、界面排序）需要时间恒可用；**所以**系统兜底补当前时刻——把"可选字段"在出口处变成"必有字段"，下游少一层判空。

### 8、callback 返回 `JSON.stringify(result)`——为什么不像领域工具那样包 ok 标记

**因为**领域工具（02 文档）的返回是"本领执行结果"，模型要用 ok 分流；而这里是"一次完整任务的交差单"，**信封自带 status 字段**（done/failed/...）——职责已由协议承担，再包一层 ok 反而让模型要拆两层。**所以**直接给信封文本，格式越少层越不容易被模型读错。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 程序启动，领域包 import 本文件（经 index.ts）；
2. 领域包工厂调用 `defineSubAgent(spec)` → 验表 → 备好工具列表（含条件性的记忆工具）→ 定义三个闭包方法 → 交付 `SubAgent` 成品（**此时还没创建任何 Agent/模型实例——懒加载**）；
3. 管家启动，调用各成品的 `toButlerTool()` → 工具挂进管家 Agent 的工具列表（管家此刻才第一次"见到"子 Agent）；
4. 运行期某单：管家模型填派活单 → 工具 callback 补编号/领域 → `handleTask` → parse 过审 → `createAgent()` 开新工作间（此刻才领模型、拼说明书、装工具）→ 模型按信封干活、可调工具与记忆 → 产出被 schema 收口成结果信封 → 回填编号/时间（失败则走兜底信封）；
5. 结果 JSON 文本回到管家模型 → 管家转述人类；工作间即弃，记忆因存在 Memory 实例而幸存。

### 2、文件在整个工程中不可替代的作用

**它是"一个总协调管家 + 平级领域子 Agent"架构从图纸变成实体的总装线**：见面隔离（printer + 信封转述）、上下文预算保护（每次开新间 + 记忆外置）、不做假成功（schema 强制 + 判空失败 + 无能力不注册）——工程四大核心原则里有三条的技术落地都在这个文件里。

### 3、运行依赖的环境与前置条件

- 依赖本包其余四件（protocol/capability/memory/model）+ Strands SDK；
- 前置条件：入口已 `await configureModel()`（或登记表显式给了 model）；领域包已备好工具（或接受空壳形态）；
- 创建时是同步的（懒加载），首次 handleTask 才发生真正的模型调用。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **`defineSubAgent` + SubAgentSpec**：**新增子 Agent 的唯一正规通道**——园艺 Agent、宠物 Agent 等新领域，照 chef 的填表样例填表即可，绝不自建组装流程；
- **`buildSubAgentSystemPrompt` 的"身份句 + 自述 + 统一纪律"结构**：任何要给 AI 写岗位说明书的场景都值得套用；
- **"每次任务新开工作间"模式**：一切需要任务隔离的多任务 Agent 场景通用。

### ⚠️ 易错点

1. **id 格式不合法**：报错信息已经很具体，照着改；别试图绕过正则（下游四处拼接全依赖它）；
2. **description 写成给人看的简介**（如"一个可爱的厨师"）：管家模型靠它派活，要写"负责什么 + 典型意图"，不是写文案；
3. **systemPrompt 里写历史数据**：说明书是一次一配的死数据，动态内容请走 Memory；
4. **handleTask 返回了就当成功**：必须按 `status` 分支——failed/unavailable/needs_human 都是"正常返回"；
5. **给 spec.tools 直接传 undefined 以外的假值**：`??` 只救 null/undefined，传 0 或空串等会被当真值展开报错（正常不会发生，但自定义工厂要小心）。

### 🔍 调试关键点

- **子 Agent 说"未返回结构化结果"**：模型没按 schema 交卷——先查该 Agent 的 systemPrompt 是否被改短/丢失，再看模型是否支持结构化输出；
- **管家从不派活给某子 Agent**：十有八九是 description 写得让管家认不出场景——对照 chef 的写法重写；
- **任务串台**（B 任务知道 A 任务的事）：查是否有人改成了"复用 Agent 实例"（红线 4）；
- **failed 信封里的 error 是天书**：那是 catch 转译的原始异常，去 createAgent/工具链路里定位。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| 5 连验表 | 🚫 不能删 | 出生时的最后一道质检，删了错误全部后置到运行深处 |
| 每任务 `createAgent()` 新开工作间 | 🚫 不能改成复用实例 | 改了 = 上下文串台（00 总览红线 4） |
| `structuredOutputSchema: ResultEnvelopeSchema` | 🚫 不能删 | 交差格式的硬约束，删了管家收到的将是散文 |
| task_id 强制覆盖 + completed_at 兜底 | 🚫 不能删 | 编号/时间必须系统说了算，信模型 = 对账崩坏 |
| handleTask 的 try/catch 总兜底 | 🚫 不能删 | 删了子 Agent 异常直接穿透管家 |
| 统一纪律 4 条文案 | ✅ 可微调措辞 | 但"不编造数据""单任务原则"的意思不能变；改协议字段名时必须同步 |
