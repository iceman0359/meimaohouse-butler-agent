# 02 · capability.ts 源码白话详解（领域能力适配器）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`capability.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agent-sdk/src/capability.ts`
- 编译产物：`packages/agent-sdk/dist/capability.js`

### 2、文件存在的核心原因

**因为** AI 模型本身"手无缚鸡之力"——它不会真的打开冰箱数鸡蛋、不会真的去超市下单，所有"真实本领"都要靠程序员写的代码（连真实硬件、连真实电商接口、连真实数据库）来提供；而这些本领来源五花八门（有的连传感器、有的连网站、有的连自家数据库），如果每个领域包直接把自家代码塞给 AI 框架，格式会各写各的、报错会满天飞，**所以**需要一个统一的"插座转接头"：规定所有领域本领都按同一个标准插进来，插上之后 AI 就能用同一个姿势调用。

这个文件解决的是三个具体问题：

1. **格式统一**：不管底下连的是冰箱还是电商，AI 看到的工具都是一个长相（名字 + 说明 + 参数表）；
2. **报错兜底**：本领执行时炸了（网络断、硬件没响应），不能让异常直接穿透到 AI 模型——否则模型会把"程序崩了"当成"任务完成了"（假成功事故）；
3. **真假分离**：框架只定义"插座标准"，不内置任何假数据；有真实本领就插真实本领，没插就是没有，Agent 必须老实说 `unavailable`（这条原则写在整个工程的 README 里："不做假成功"）。

**如果没有这个文件，程序会出现的问题：** 每个领域包自己包装工具，返回格式五花八门；工具一报错整个任务流程直接崩；框架被迫内置假数据来"演示"，违背工程"不做假成功"的红线。

### 3、文件的整体定位

这个文件**专门负责"把领域能力实现包装成 AI 可调用工具"**，是领域真实代码与 AI 框架之间的"转接头层"。它只管包装和兜底，不管本领具体怎么实现——实现由宿主（使用框架的应用）注入。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- `@strands-agents/sdk`：只取两样东西——`tool()` 工厂函数（AI 框架规定的"造工具"入口）和 `ToolContext` 类型（工具执行时的上下文信息类型）；
- `zod`：只取类型 `z`，用来给"入参校验器"标注类型（不实际执行校验，校验由 `tool()` 内部做）。

**谁来调用它（下游）：**

- `memory.ts`（本包内）：4 个记忆工具（memory_get 等）全部通过 `defineDomainTool` 包装——它是本文件最直接的内部用户；
- `packages/agents/chef/src/tools.ts` 和 `packages/agents/cleaner/src/tools.ts`：厨师和清洁工的所有真实本领（查库存、下单、清洁记录）都是用它包装的；
- `sub-agent.ts`：类型上引用 `DomainTool`（通过 memory.ts 间接）。

**一句话：所有"要给 AI 用的本领"，出厂前都得从这个文件的流水线上过一遍。**

## 模块2：文件内核心定义与核心函数超详细说明

### 核心定义 1：`DomainTool`（领域工具类型别名）

1. **名称**：`DomainTool`，写法 `export type DomainTool = ReturnType<typeof tool>`。
2. **设计的根本原因**：**因为**"包装好的工具"这个类型名在框架里写得出来但很长、而且 SDK 没有公开承诺这个名字永远不变，**所以**用 `ReturnType<typeof tool>`（"tool 函数返回什么类型，我就是什么类型"）让 TypeScript 自己推导，再起个短名字 `DomainTool` 方便到处引用。**不这么做的弊端**：每个文件里都写一遍长长的推导类型，SDK 升级时几十处跟着改。
3. **语法写法的原因**：**因为**TypeScript 的类型系统提供了 `ReturnType<函数类型>` 这个工具类型，它能在编译期自动算出函数返回值类型，**所以**可以用它"跟着实现走"而不是"抄死类型名"——SDK 内部类型改名也不受影响，这是对第三方库做类型适配的标准姿势。
4. **内部逻辑分步讲解**：就一行——"看 `tool` 这个函数的返回值类型是什么，`DomainTool` 就是什么"。没有任何运行时代码，纯类型层面的定义，编译后完全消失。
5. **触发条件**：不运行；所有声明"这是领域工具"的变量/参数/返回值处被引用。
6. **最终作用**：让整个工程用同一个短名字称呼"包装好的工具"，SDK 升级不改工程代码。
7. **使用场景**：`memory.ts` 的 `createMemoryTools` 返回值、`sub-agent.ts` 的 `ButlerTool` 同款写法、各领域包的工具列表类型。
8. **缺陷/注意事项**：它是"跟着 SDK 走"的类型，如果 SDK 大版本改了 `tool()` 的签名，所有使用处会一起编译报错——这是特性也是风险，升级 SDK 时要全量编译验证。

### 核心定义 2：`DomainToolFailure`（失败结果的标准长相）

1. **名称**：`DomainToolFailure`，一个接口：`{ ok: false, error: string, code?: string }`。
2. **设计的根本原因**：**因为**工具失败时 AI 需要读到"明确说了失败 + 失败原因"，而不能只拿到一个异常文本甚至什么都拿不到，**所以**规定失败结果必带 `ok: false` 和 `error` 文案，选带 `code` 错误码。**没有它**，AI 判断成败只能靠猜文本，容易把失败当成功。
3. **语法写法的原因**：**因为**TypeScript 用 `interface` 定义对象形状；`ok: false` 是"字面量类型"——它把 ok 锁死为 false 这一个值，AI/代码一看 ok 就知道结果性质，不用再解析别的字段；`code?` 的问号表示可选项（错误码不是每次失败都有）。
4. **内部逻辑分步讲解**：三个字段——`ok` 永远是 false（性质标记）；`error` 必填，给人看的失败描述；`code` 选填，给程序看的错误标识（包装器统一填 `capability_error`，见核心函数）。
5. **触发条件**：不运行；`defineDomainTool` 的 catch 分支、以及下游判断结果性质时引用。
6. **最终作用**：失败结果有固定格式，AI 能稳定读出"这事没成、为什么没成"。
7. **使用场景**：与 `DomainToolSuccess` 组合成 `DomainToolResult`（见核心定义 4）；管家和子 Agent 解析工具返回时按它理解失败。
8. **缺陷/注意事项**：`error` 是自由文本，AI 可能读不懂太技术化的报错——领域包写实现时尽量用通俗中文写错误信息。

### 核心定义 3：`DomainToolSuccess<T>`（成功结果的标准长相）

1. **名称**：`DomainToolSuccess<T>`，接口：`{ ok: true, data: T }`。
2. **设计的根本原因**：**因为**成功时 AI 需要拿到"真实数据本体"，而且必须和失败结果长得"同族不同种"（都带 ok 标记），AI 才能一眼分辨，**所以**规定成功必带 `ok: true` 和 `data`。
3. **语法写法的原因**：**因为**不同工具返回的数据结构不同（查库存返回清单、下单返回订单号），**所以**用泛型 `<T>` 表示"data 的类型由每个工具自己定"——一个模板套所有工具，而不是为每种数据写一个接口。
4. **内部逻辑分步讲解**：两个字段——`ok` 锁死为 true；`data` 类型为 T（泛型占位）。
5. **触发条件**：不运行；`defineDomainTool` 成功分支、下游解析时引用。
6. **最终作用**：成功结果带统一"成功标记 + 数据本体"，配合失败定义构成完整的二选一。
7. **使用场景**：同上，且 `satisfies DomainToolSuccess<TOutput>` 那行（见核心函数）用它做编译期检查。
8. **缺陷/注意事项**：`data` 内容本文件不校验——工具实现返回什么就是什么，领域包自己要保证数据正确。

### 核心定义 4：`DomainToolResult<T>`（二选一的结果类型）

1. **名称**：`DomainToolResult<T>`，写法 `= DomainToolSuccess<T> | DomainToolFailure`（成功或失败，二选一）。
2. **设计的根本原因**：**因为**工具只有"成"和"败"两种结局，把两种标准长相用竖线（联合类型）绑在一起，下游拿到结果只需要判断 `ok` 真假就能安全分流，**所以**定义了这个联合类型。
3. **语法写法的原因**：**因为**TypeScript 的联合类型（`|`）+ 判别字段（ok）是处理"互斥情况"的标准语法：判断 `result.ok === true` 后，TypeScript 自动知道此时它是成功形状、可以安全访问 `data`——写错代码编译期就报错。
4. **内部逻辑分步讲解**：纯类型运算——"DomainToolResult 要么是成功形状、要么是失败形状"。因为两种形状的 `ok` 一个是 true 一个是 false，TypeScript 靠它区分，这个技巧叫"判别联合"。
5. **触发条件**：不运行；作为工具返回值的推荐类型标注被各处引用。
6. **最终作用**：让"工具结果"在整个工程里有一个统一、可类型安全分流的标准形状。
7. **使用场景**：领域包工具实现的返回值标注、解析工具结果的代码分支。
8. **缺陷/注意事项**：实际传给 AI 的是 JSON 字符串（见核心函数），这个类型是"包装前/解析后"的类型——解析 JSON 后记得按它判别，别直接当对象乱用。

### 核心定义 5：`DomainToolSpec<TInput, TOutput>`（能力说明书格式）

1. **名称**：`DomainToolSpec<TInput extends z.ZodType, TOutput>`，接口，4 个字段：`name`、`description`、`inputSchema`、`execute`。
2. **设计的根本原因**：**因为**领域包手里有的是"一个会干活的函数"，但要交给 AI 用还差"名字、说明、参数表"这三样 AI 必需的信息，**所以**规定了"能力说明书"标准格式：本领叫什么、干什么用的、收什么参数、本体函数是谁——填齐这四样才能上流水线。
3. **语法写法的原因**：
   - **因为**TypeScript 泛型约束语法要求"inputSchema 必须是 Zod 校验器"，**所以**写 `TInput extends z.ZodType`——不写约束，传个字符串进来编译也能过，运行时框架才会炸（把错误推迟到运行期是最糟的）；
   - **因为**入参类型要跟校验器"联动"（校验器规定了什么字段，execute 拿到的就该是什么类型），**所以** `execute` 的第一个参数写成 `z.infer<TInput>`——从校验器自动推导出入参类型，说明书里的参数表和本体函数的参数永远不会对不上；
   - **因为**本领执行可能涉及网络/硬件等待，**所以** `execute` 返回 `Promise<TOutput>`（异步承诺）；
   - **因为**框架可能传入上下文（如调用来源信息），**所以**第二个参数 `context?: ToolContext` 是可选的。
4. **内部逻辑分步讲解**：四个字段的含义——`name`：工具名（AI 按名字点名调用，全工程内要唯一）；`description`：给 AI 看的用途说明（写不清 AI 就不会用/乱用）；`inputSchema`：Zod 校验器（AI 填的参数先过它）；`execute`：真实本领本体。
5. **触发条件**：不运行；调用 `defineDomainTool(spec)` 时作为入参传入。
6. **最终作用**：把"注册一个领域本领"需要的全部信息收敛成一个对象，填错漏错在编译期就能被发现。
7. **使用场景**：`defineDomainTool` 的唯一入参；`memory.ts` 和各领域包的 tools.ts 全在按它填表。
8. **缺陷/注意事项**：`name` 的唯一性本文件不查——两个工具重名会在 Agent 注册时出问题，各包起名要带领域前缀（如 `fridge_check`）。

### 核心函数：`defineDomainTool(spec)`（流水线本体）

1. **函数名称**：`defineDomainTool`，入参 `spec: DomainToolSpec<TInput, TOutput>`，返回 `DomainTool`。
2. **函数设计的根本原因**：**因为**"把本领包装成工具"这套动作（带参数校验、统一返回格式、异常兜底）每个本领都要来一遍，不封装就会出现：几十个工具各自手写 try/catch、返回格式五花八门、漏写兜底的工具一炸就把模型带崩，**所以**必须有一个统一的包装流水线，所有本领进来、标准工具出去。**封装的好处**：兜底逻辑只写一遍；新领域接本领零心智负担（填说明书就行）；查问题只需要查这一处。
3. **函数语法写法的原因**：
   - **因为**TypeScript 泛型函数语法要把"校验器类型"和"输出类型"都接到函数上，**所以**签名是 `defineDomainTool<TInput extends z.ZodType, TOutput>(spec: DomainToolSpec<TInput, TOutput>)`——两个泛型从 spec 里自动推断，调用方不用手写；
   - **因为**它内部直接调用框架的 `tool()` 工厂，**所以**返回类型就是 `DomainTool`（见核心定义 1）；
   - **因为**callback 里要 await 异步执行，**所以** callback 是 async 函数，这是 JS 异步语法的硬要求（在普通函数里 await 会直接语法报错）。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：调 `tool({ name, description, inputSchema, callback })`——把说明书里的名字、说明、参数表原样交给框架，**因为**这三样是框架注册工具的必需项，缺一个工具就注册不上；
   - 第 2 步：callback 开头先 `await spec.execute(input, context)`——把 AI 填好且过完校验的参数交给真实本领本体执行，**为什么这里不自己干活**：它只是转接头，活必须由领域实现干；
   - 第 3 步：成功则 `JSON.stringify({ ok: true, data } satisfies DomainToolSuccess<TOutput>)`——把成功结果打成统一格式的 JSON 字符串返回；
   - 第 4 步：失败（execute 抛异常）则 catch 住，返回 `JSON.stringify({ ok: false, error: ..., code: 'capability_error' })`——把异常变成标准失败结果；
   - 第 5 步：callback 结束，字符串交回框架，框架再交给 AI 读。
5. **函数的触发条件**：Agent 运行中，AI 模型决定调用某个领域工具时（比如厨师想查库存），框架执行该工具的 callback——流水线开始运转。
6. **函数的最终作用**：无论底下本领是什么、无论成败，AI 拿到的永远是"ok 标记 + 数据/错误"的标准 JSON 字符串——AI 能稳定判断成败并决定下一步，程序异常不再穿透。
7. **函数的使用场景**：`memory.ts` 的 4 个记忆工具、厨师/清洁工的全部领域能力工具——全工程所有"本领注册"都走它。
8. **函数的缺陷/注意事项**：错误码固定填 `capability_error`，没有细分（比如区分超时和拒绝连接）；领域想细分错误码，得在自己的 execute 里把错误信息写清楚，或扩展本函数（属于可优化点，见模块6）。

## 模块3：文件内每一个参数超详细说明

### 参数 1：`spec`（defineDomainTool 的入参）

1. **名称 + 类型**：`spec`，`DomainToolSpec<TInput, TOutput>` 对象（含 name/description/inputSchema/execute 四个字段，见核心定义 5）。
2. **参数设计原因**：**因为**包装一个本领需要"一份说明书 + 一个本体"，散着传 4 个参数没有整体感、也容易被漏传，**所以**打包成一个对象传入。
3. **参数类型选择原因**：**因为**要同时约束"说明书形状"和"校验器与本体函数的类型联动"，**所以**必须用带双泛型的接口类型——换成普通 object 类型会丢掉全部类型保护。
4. **参数的传入来源**：领域包的 tools.ts / `memory.ts` 手工构造（都是编译期写死的对象字面量）。
5. **参数的内部使用逻辑**：name/description/inputSchema 三项直接透传给框架的 `tool()`；`spec.execute` 被包进 callback 的 try/catch 中调用；`spec.input` 的类型通过 `z.infer<TInput>` 与 callback 入参联动。
6. **参数的取值范围**：必须是一个完整填齐 4 个字段的合法 spec；缺任何一个字段编译期报错（interface 必填项检查）；inputSchema 不是 Zod 校验器会在 `tool()` 注册时运行报错。
7. **参数的最终作用**：它是"本领注册申请表"——整个流水线的唯一信息来源。

### 参数 2：`input`（callback 收到的入参）

1. **名称 + 类型**：`input`，类型 `z.infer<TInput>`（由说明书里的校验器推导出的对象）。
2. **参数设计原因**：**因为**AI 调工具时必须填参数，框架校验完要交给本领本体，**所以**callback 必须接住这个参数并向下传递。
3. **参数类型选择原因**：**因为**参数形状由每个工具的 inputSchema 决定，**所以**类型用 `z.infer<TInput>` 动态推导而不是写死——写死会让所有工具共享一个错误类型。
4. **参数的传入来源**：AI 模型填写 → 框架按 inputSchema 校验通过后传入 callback。
5. **参数的内部使用逻辑**：只有一处使用——原样传给 `spec.execute(input, context)`，包装器自己不解读、不修改参数。
6. **参数的取值范围**：能通过该工具 inputSchema 校验的任何对象；校验不过的到不了这里（框架层面就打回了）。
7. **参数的最终作用**：把 AI 的"调用意图"落地成"真实本领的实参"。

### 参数 3：`context`（工具执行上下文）

1. **名称 + 类型**：`context`，`ToolContext`（框架定义的类型），可选（`context?`）。
2. **参数设计原因**：**因为**有的本领需要知道"是谁在哪个会话里调用我"（比如记日志要带会话 ID），框架会把上下文传进来，**所以**包装器要预留通道向下传。
3. **参数类型选择原因**：**因为**上下文结构由框架定义且本文件不关心内容，**所以**直接引用框架的 `ToolContext` 类型并用可选标记——框架哪天传了就转，没传也不报错。
4. **参数的传入来源**：AI 框架在执行工具时自动注入。
5. **参数的内部使用逻辑**：只有一处使用——原样传给 `spec.execute`；包装器自己不读。
6. **参数的取值范围**：框架合法上下文对象或 undefined。
7. **参数的最终作用**：本领本体获得调用现场信息的正规通道。

### 参数 4：`err`（catch 捕获到的异常）

1. **名称 + 类型**：`err`，`unknown` 类型（JS 异步函数 catch 到的东西类型未知）。
2. **参数设计原因**：**因为**真实本领可能抛出任何东西（Error 对象、字符串、甚至 undefined），包装器必须全部接住转成标准失败格式，**所以** catch 里必然有这个变量。
3. **参数类型选择原因**：**因为** TypeScript 严格模式下 catch 的变量是 unknown（不能用 any——那是关闭检查），**所以**必须先判断类型再用：`err instanceof Error ? err.message : String(err)`——是 Error 就取 message 文案，不是就强制转字符串。这个判断是语法强制要求：unknown 类型不收窄直接访问 `.message` 会编译报错。
4. **参数的传入来源**：`spec.execute` 执行过程中抛出的任何异常。
5. **参数的内部使用逻辑**：仅一处使用——被转成字符串塞进失败结果的 `error` 字段。
6. **参数的取值范围**：任意（unknown 就意味着任意）；任何类型都能被这段代码安全转成文本。
7. **参数的最终作用**：异常信息的"翻译官"，把五花八门的异常统一成 AI 能读的失败文案。

### 参数 5：`data`（成功时的数据）

1. **名称 + 类型**：`data`，`TOutput`（泛型，由本领本体的返回值决定）。
2. **参数设计原因**：**因为**成功结果必须携带真实数据，**所以**要把 execute 的返回值接住再打包。
3. **参数类型选择原因**：**因为**各工具数据结构不同，**所以**用泛型占位——类型从 `spec.execute` 的返回类型自动推导，声明和实现永不脱节。
4. **参数的传入来源**：`await spec.execute(input, context)` 的返回值。
5. **参数的内部使用逻辑**：仅一处使用——被塞进 `{ ok: true, data }` 后整体 JSON 序列化。
6. **参数的取值范围**：本领本体返回的任何值；但注意**必须能被 JSON 序列化**（函数、循环引用的对象会在 stringify 时丢字段或报错）。
7. **参数的最终作用**：AI 拿到的"劳动成果"本体。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、整个 callback 包在 try/catch 里——为什么必须这么做

**因为**本领本体连的是现实世界（网络、硬件、数据库），现实世界必然偶发故障；而 AI 模型读不到"异常"这个概念——如果异常直接抛出去，模型要么看到空结果、要么框架直接中断，模型极可能把这次调用理解成"没查到/干完了"，造成假汇报。**所以**必须由包装器统一兜底：任何异常都转成 `{ ok: false, error: '...' }` 的标准失败 JSON。**如果删掉这段 try/catch**：本领一崩，AI 以为任务完成，管家向人类汇报成功——这正是工程红线里"不做假成功"要防的事故。

### 2、`satisfies DomainToolSuccess<TOutput>` ——为什么返回 JSON 字符串还要加类型检查

**因为** `JSON.stringify` 的返回类型永远是字符串（编译器看不出字符串里装的是成功还是失败形状），如果不加约束，"失败时手滑装了成功格式"这种 bug 编译期完全查不出来；**所以**在序列化前的对象字面量上加 `satisfies` 关键字——它让编译器按指定类型检查这个对象（字段名对不对、ok 是不是布尔字面量），但不改变对象本身的类型。这是 `satisfies`（TypeScript 4.9+ 语法）相对 `as` 断言的优势：`as` 是"我说是什么就是什么"（强扭），`satisfies` 是"你检查我说得对不对"（真验证）。**不这么写的后果**：包装器的输出格式错乱只能在运行时被 AI 的"懵逼"暴露。

### 3、`err instanceof Error ? err.message : String(err)`——为什么要分两种情况

**因为** JS 里 throw 的东西不一定是 Error 对象（`throw '字符串'` 完全合法），而只有 Error 对象才有 `.message` 属性；**所以**必须先判断——是 Error 取 message（正规文案），不是就 `String(err)` 强转（兜底可读）。**如果直接写 `err.message`**：遇到 throw 字符串的代码，这里直接"异常处理函数自己抛异常"，兜底变成二次事故。

### 4、错误码统一写死 `capability_error`——为什么

**因为**包装器不知道每个领域的错误分类体系（厨房的错误和清洁的错误没法共用一张码表），**所以**它只能给一个"我这里出过错"的通用标记，细分语义让本领本体写进 error 文案里。**这是刻意保守的设计**：宁可错误码粗糙，也不假装自己懂各领域。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 程序启动，经由 `index.ts` 被领域包/记忆模块 import 加载；
2. 加载时仅创建类型与函数定义（纯类型在编译后消失，实际只剩一个函数）；
3. 领域包/记忆模块启动时调用 `defineDomainTool(spec)` 注册各自的工具（此时包装完成、工具就位，**还没有执行任何本领**）；
4. Agent 运行中，AI 决定用某个工具 → 框架校验参数 → 调用包装好的 callback → callback 转交 `spec.execute` 干真活；
5. 成功 → 统一成功 JSON 返回给 AI；失败 → try/catch 兜底 → 统一失败 JSON 返回给 AI。

### 2、文件在整个工程中不可替代的作用

**它是"AI 的手"的统一接驳口**：保证了全工程所有工具返回格式一致、异常必被兜底、本领实现与 AI 框架解耦（本领只管干活，框架细节由包装器扛）。"领域抽象 > 工具具象、不做假成功"这两条工程核心原则，全靠这个文件落地。

### 3、运行依赖的环境与前置条件

- 依赖 `@strands-agents/sdk`（提供 `tool()` 与 `ToolContext`）和 `zod`（仅类型层）；
- 前置条件：注册工具时所在领域包的依赖已安装（`tool()` 可用）；
- 无任何模型/数据库/网络依赖，可在测试环境独立运行。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- `defineDomainTool`：**全工程通用的"本领注册器"**。新增任何领域（园艺、宠物……）接真实能力时，第一件事就是用它包装，不需要也不允许自创包装方式。
- `DomainToolResult` 三件套（Success/Failure/Result）：任何"要区分成败"的函数返回值都适用。

### ⚠️ 易错点

1. **execute 里返回了不可序列化的东西**（函数、Date 对象、循环引用）：`JSON.stringify` 会丢字段或抛错——数据请先转成纯 JSON 形状（Date 用 `toISOString()`）。
2. **description 写得太潦草**：AI 是靠这段话决定"用不用这个工具、怎么填参数"的，写"处理数据"这种废话等于没写，模型会漏用或误用工具。
3. **在 execute 里自己吞异常返回"假装成功的值"**：比如查不到库存时返回 `{ ok: true, data: { count: 0 } }`——这属于造假，查不到就该 throw，让包装器统一转失败格式。
4. **工具重名**：两个领域都注册 `check` 这种泛化名字，Agent 里后注册的会覆盖/冲突，起名带领域前缀。

### 🔍 调试关键点

- AI 说"工具调用失败"但找不到原因：先在 `spec.execute` 里加日志——包装器只会转述它抛的东西；
- AI 把失败当成功：检查是否绕过了 `defineDomainTool`（自包装的工具没有兜底），或返回的 JSON 被二次包装；
- 编译报错在 `satisfies` 行：是包装器输出格式与类型定义不符，按编译提示补字段。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| callback 的 try/catch | 🚫 不能删 | 删了 = 异常穿透给 AI = 假成功事故（见模块4） |
| `{ ok: true/false }` 统一返回格式 | 🚫 不能改 | 全工程工具的"普通话"，改了所有领域包解析全崩 |
| `satisfies` 类型检查 | 🚫 不能删 | 它是格式错乱唯一的一道编译期防线 |
| 错误码细分（把 `capability_error` 做成可配置） | ✅ 可优化 | 修改时保持默认值兼容现有领域包 |
| 在包装器里加入参日志（调试用） | ✅ 可优化 | 别在日志里打印敏感信息（API Key、住址类数据） |
