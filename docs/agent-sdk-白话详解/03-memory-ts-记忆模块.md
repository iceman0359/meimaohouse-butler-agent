# 03 · memory.ts 源码白话详解（记忆模块）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`memory.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agent-sdk/src/memory.ts`
- 编译产物：`packages/agent-sdk/dist/memory.js`

### 2、文件存在的核心原因

**因为** AI 模型有个天生的毛病：**记性只活在当前这次对话里**——对话一结束（甚至子 Agent 的独立工作间一关闭，见 05 文档"每次任务新建 Agent"），这次说过的一切就全忘了。而管家场景恰恰需要记性：冰箱里还剩什么、"主人不吃香菜"这种偏好、上次买菜花了多少钱……没有记忆，Agent 每次都从零开始，什么都答不上或者瞎编。

但"把记忆存哪儿"是个可替换的决定：演示时存内存就行，生产环境要存数据库、甚至存专门的记忆服务。**所以**这个文件干了两件事：

1. 规定一个"记忆插座标准"（`Memory` 接口）——不管存哪儿，都必须会"读、写、追加、删除"这四个动作；
2. 提供一个最简单的插座实现（进程内存版）+ 一套把记忆变成 AI 工具的转换器（让 AI 能自己存取记忆）。

**如果没有这个文件，程序会出现的问题：** 子 Agent 没有任何跨任务记性（每次都失忆）；或者记忆代码写死在某一种存储上，想换成数据库就得大改所有 Agent 代码。

### 3、文件的整体定位

这个文件**专门负责"Agent 长期记忆的抽象标准 + 默认实现 + AI 工具化"**，是 Agent 的"记性零件包"。它不关心记忆里存的是什么内容（那是各领域业务的事），只关心"怎么存、怎么取"。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- `zod`：给 4 个记忆工具定义入参校验器（AI 填的参数先过审）；
- `capability.ts`（本包内）：用 `defineDomainTool` 把记忆操作包装成标准工具——**它是 02 文档那条"包装流水线"的头号客户**。

**谁来调用它（下游）：**

- `sub-agent.ts`：创建子 Agent 时，若传入了记忆实现，就调 `createMemoryTools(memory, spec.id)` 生成记忆工具挂到 Agent 上，并把"你有记忆可用"写进系统提示词；
- `packages/butler-core/butler.ts`：管家也用同一套 `createMemoryTools` 给自己配记忆；
- `packages/db`（数据库层）：提供 `createSqliteMemory(db, …)`——按本文件的 `Memory` 接口实现的"落库版记忆"， demonstrating 接口可插拔（README 明确说明记忆工具直接落到 SQLite）；
- 各应用（`apps/butler-web`）启动时构造记忆实现传给 Agent。

**一句话：接口是插座标准，InMemoryMemory 是最便宜的插座，createMemoryTools 是"把插座变成 AI 能用的工具"的转换器。**

## 模块2：文件内核心定义与核心函数超详细说明

### 核心定义 1：`Memory`（记忆插座标准 / 接口）

1. **名称**：`Memory`，TypeScript 接口（interface），声明 4 个方法：`get` / `set` / `append` / `del`。
2. **设计的根本原因**：**因为**记忆的存放位置必须可替换（内存 → SQLite → 未来记忆服务），如果不先定一个标准，每种存储各写各的调用方式，Agent 代码就和一个具体存储焊死了，换存储等于重写所有 Agent，**所以**必须先立"插座标准"：任何想当记忆的存储，实现这 4 个方法就够格。**接口的好处**：Agent 代码只认标准不认牌子，插内存版能跑，插数据库版照样跑。
3. **语法写法的原因**：
   - **因为**TypeScript 的 interface 语法专门用来"只定形状、不给实现"，**所以**用它——这正是接口的本职（声明"能干什么"，不声明"怎么干"）；
   - **因为**4 个操作都可能涉及真实存储（哪怕是内存，未来换数据库就是网络/磁盘等待），**所以**全部声明为 `async` 风格——返回值都是 `Promise<...>`（异步承诺）。**这是语法硬要求**：如果接口里不写 Promise，实现里想异步就得违约；现在写 Promise，内存版也只是"返回一个立刻完成的承诺"，成本为零，但未来换数据库零改动；
   - **因为**"键不存在"和"键存在但值是空"是两回事，**所以** `get` 的返回类型写 `Promise<string | null>`——用 `null` 明确表示"没查到"（JS 惯例：null = 查了没有，undefined = 连查没查都不确定）。
4. **内部逻辑分步讲解**（4 个方法各自含义）：
   - `get(key): Promise<string | null>`：按键取值；没有返回 null；
   - `set(key, value): Promise<void>`：写入/覆盖一个键的值；void 表示"干完就行，不返回东西"；
   - `append(key, entry): Promise<void>`：往一个键**追加一行**——**因为**有些记忆天然是流水账（每天的饮食记录），覆盖会丢历史，**所以**必须有追加动作；
   - `del(key): Promise<void>`：删除一个键（过期记忆要能清理，不然越积越脏）。
5. **触发条件**：不运行；作为类型被所有记忆实现（InMemoryMemory、createSqliteMemory）和所有使用记忆的代码引用。
6. **最终作用**：把"Agent 的记性存在哪"变成一个可插拔决定，Agent 代码一行不用改就能换存储。
7. **使用场景**：`sub-agent.ts` 的 `SubAgentSpec.memory` 参数、`butler-core` 的管家记忆参数、db 包的 `createSqliteMemory` 实现声明。
8. **缺陷/注意事项**：值类型只有 string——结构化数据要自己先 `JSON.stringify` 存、取出再 parse（工具层没做这层转换，领域里存复杂对象要自己注意）。

### 核心定义 2：`InMemoryMemory`（进程内存版记忆实现）

1. **名称**：`InMemoryMemory`，一个类（class），实现 `Memory` 接口。
2. **设计的根本原因**：**因为**接口只是标准，必须至少有一个实现才能真正跑起来；本地演示、单元测试时根本不需要数据库，**所以**提供这个"最便宜"的实现——数据存在程序自己的内存里，快、零依赖。**它同时是"接口可插拔"的活样板**：照着它抄一个数据库版就能无缝替换。
3. **语法写法的原因**：
   - **因为**TypeScript 声明"我承诺实现这个接口"的语法是 `implements Memory`，**所以**类声明这么写——少实现任何一个方法，编译期直接报错，标准执行有保障；
   - **因为**存储本体是内部细节，外部不该直接摸（一摸就可能绕过方法逻辑把数据弄乱），**所以**用 `private store`——TS 的 private 让外部访问直接编译报错；
   - **因为**键值对是"按键查找"场景，**所以**用 `Map<string, string>` 而不是普通对象——Map 的键不会跟 Object 内置属性撞名（比如键叫 "constructor" 时普通对象会出诡异问题），且增删查性能稳定。
4. **内部逻辑分步讲解**（4 个方法逐个看）：
   - `get(key)`：`return this.store.get(key) ?? null`——Map 的 get 查不到时返回 undefined，**为什么要 `?? null`**：接口承诺"没有就返回 null"，undefined 不符合承诺，**所以**用空值合并运算符把 undefined 换成 null；这一行不写 `?? null` 就是实现与接口不符（类型检查直接报错，又是语法强制）；
   - `set(key, value)`：`this.store.set(key, value)`——Map 自带"有则覆盖、无则新增"，一行搞定；
   - `append(key, entry)`：先查旧值——**有**旧值就"旧值 + 换行符 + 新内容"拼起来存回（形成一行一条的流水账），**没有**旧值就直接存新内容（第一个条目前面不能有空行）；**如果去掉这个判断**：第一条记录前面会多个空行，读出来格式脏；
   - `del(key)`：`this.store.delete(key)`——删了就没了（键本来就不存在也不会报错）。
5. **触发条件**：应用启动时由 `createMemory()` 创建实例；此后 Agent 每次调用记忆工具，实际执行的就是这个类的对应方法。
6. **最终作用**：让 Agent 在"没配任何外部存储"的默认情况下也拥有完整可用的记忆能力。
7. **使用场景**：本地演示（`npm run demo`）、单元测试、任何不想配数据库的场景。
8. **缺陷/注意事项**：**数据随进程消失**——程序一重启记忆全没了，所以只适合演示/测试；生产环境必须换 `createSqliteMemory`（db 包）这类持久实现。

### 核心函数 1：`createMemory()`（记忆实例工厂）

1. **函数名称**：`createMemory`，无入参，返回 `Memory`。
2. **函数设计的根本原因**：**因为**"创建记忆实例"这个动作应该有个统一入口，将来默认实现从内存换成数据库时，只需改这一个函数，所有调用方不用动（调用方只说"给我一个记忆"，不说"给我一个内存记忆"），**所以**封装成工厂函数——这是"具体实现只出现在一处"的经典收口。
3. **函数语法写法的原因**：**因为**函数体只有一行 `return new InMemoryMemory()`，同步完成、不会失败，**所以**不需要 async、不需要参数——参数留了反而是累赘（未来需要配置时再加，符合最小接口原则）。
4. **函数内部完整逻辑分步讲解**：就一步：new 一个内存版记忆实例并返回。注释里明确写了"默认内存实现，后续可替换为工厂注入外部存储"——替换点就在这一行。
5. **函数的触发条件**：应用/演示代码需要一个"默认记忆"时手动调用。
6. **函数的最终作用**：产出符合 Memory 标准的可用记忆实例。
7. **函数的使用场景**：演示脚本、测试代码；生产应用一般直接用 db 包的 `createSqliteMemory`，不走它。
8. **函数的缺陷/注意事项**：每次调用都产生**独立**的记忆实例（两个实例数据互不相通）——想共享记忆必须复用同一个实例，别每次都 new。

### 核心函数 2：`createMemoryTools(memory, namespace)`（记忆工具转换器）

1. **函数名称**：`createMemoryTools`，入参 `memory: Memory` 和 `namespace = 'default'`（带默认值），返回 `DomainTool[]`（工具数组）。
2. **函数设计的根本原因**：**因为** AI 模型不会直接调 `memory.get()` 这种程序函数——它只会"调用工具"，**所以**必须把记忆的 4 个动作翻译成 4 个 AI 能调用的工具（memory_get / memory_set / memory_append / memory_delete）；**又因为**管家和多个子 Agent 可能共用同一个存储，如果大家都能读写同一批键，厨师的记忆会被清洁工改掉，**所以**加了 `namespace`（命名空间）参数，把每个 Agent 的键都自动加上前缀，互不串门。**不封装的弊端**：每个 Agent 手写 4 个工具定义 + 各自搞命名隔离，代码重复且容易漏前缀造成记忆串号。
3. **函数语法写法的原因**：
   - **因为** namespace 绝大多数场景就是 Agent 的 id、且省略时也要能跑，**所以**用 TypeScript 的参数默认值语法 `namespace = 'default'`——调用时少传一个参数不报错；
   - **因为** 4 个工具都要用同一个"加前缀"逻辑，**所以**在函数里先定义小助手 `keyOf`（闭包函数），避免同一段模板字符串写 4 遍；
   - **因为**返回的是"一组工具"，**所以**返回类型是数组 `DomainTool[]`；
   - **因为**每个工具的入参都要过审，**所以**每个都用 `z.object({...})` 定义校验器（Zod 语法，见 01/02 文档）。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：定义 `keyOf = (key) => \`${namespace}:${key}\``——把"记忆键"加上"命名空间冒号前缀"（如 chef 下的 `fridge` 变成 `chef:fridge`），这是隔离机制的本体；
   - 第 2 步：定义 `memory_get` 工具——AI 给一个 key，工具实际执行 `memory.get(keyOf(key))`，把 `{ value: 查到的值或 null }` 返回给 AI（**注意**：查不到返回的是 `value: null`，AI 能读懂"没有这条记忆"）；
   - 第 3 步：定义 `memory_set` 工具——AI 给 key 和 value，实际执行 `memory.set(keyOf(key), value)`，返回 `{ stored: true }`（明确告诉 AI"存好了"）；
   - 第 4 步：定义 `memory_append` 工具——AI 给 key 和 entry，实际执行 `memory.append(keyOf(key), entry)`，返回 `{ appended: true }`；
   - 第 5 步：定义 `memory_delete` 工具——AI 给 key，实际执行 `memory.del(keyOf(key))`，返回 `{ deleted: true }`。
   - **每一步的共同点**：全都通过 `defineDomainTool` 包装（02 文档的流水线）——**所以**它们自动获得了"统一返回格式 + 异常兜底"，AI 永远拿到标准 JSON。
5. **函数的触发条件**：`sub-agent.ts` 的 `defineSubAgent` 在组装 Agent 时调用（传入了 memory 就调）；`butler-core` 给管家装配记忆时调用。
6. **函数的最终作用**：Agent 获得了"自己存、自己取、自己记账"的能力——重要事实写进记忆而不是留在对话里，对话关了记忆还在。
7. **函数的使用场景**：所有需要记忆能力的 Agent（管家、厨师、清洁工……）；未来接入新 Agent 也复用它。
8. **函数的缺陷/注意事项**：命名空间隔离是"键前缀"式的软隔离——如果 Agent 直接用带别的命名空间前缀的完整键去查（如 AI 手动查 `cleaner:xxx`），是拦不住的（keyOf 只管加前缀，不管检查）；此外 4 个工具都开放给 AI，意味着 AI 理论上能删掉自己的记忆——靠系统提示词约束使用规范。

## 模块3：文件内每一个参数超详细说明

### 参数 1：`key`（记忆键 / 四个接口方法共用）

1. **名称 + 类型**：`key`，字符串（string）。
2. **参数设计原因**：**因为**记忆必须能"按名字找回来"，没有键，存进去的东西就是一锅粥，**所以**每个动作都要带键。
3. **参数类型选择原因**：**因为**键的本质是"名字标签"，**所以**用字符串；工具层的校验器里还加了 `.min(1)`（至少 1 个字符）——空键等于没起名字，必须挡住。
4. **参数的传入来源**：接口层——调用记忆的代码传；工具层——AI 模型在调用记忆工具时填。
5. **参数的内部使用逻辑**：工具层先被 `keyOf` 加上命名空间前缀，再传给 Memory 实例的对应方法；接口层拿到的是已带前缀的完整键，直接操作存储。
6. **参数的取值范围**：接口层任意字符串（建议用有业务含义的名字如 `fridge_inventory`、`owner_preferences`）；工具层必须非空字符串（min(1) 把关）。
7. **参数的最终作用**：记忆的"门牌号"，是读写删定位的唯一依据。

### 参数 2：`value`（要存的值）

1. **名称 + 类型**：`value`，字符串（string）。
2. **参数设计原因**：**因为** set 的本职就是"把一段信息存进键里"，没有值参数，写操作无从谈起。
3. **参数类型选择原因**：**因为**接口统一把记忆值定为文本（简单、通用、任何存储都能存），**所以**是 string；工具层校验器对 value 没加 min(1)——存空字符串是合法的（比如"清空这个键的内容"是一种用法），这是与 key 的校验差异，属于刻意设计。
4. **参数的传入来源**：接口层——调用方传；工具层——AI 模型组织好的一段文本（比如"冰箱现有：鸡蛋 6 个、牛奶 1 盒"）。
5. **参数的内部使用逻辑**：set 直接整键覆盖（旧值被新值替换）；传给存储实现后原样落存。
6. **参数的取值范围**：任意字符串（含空串）；超长文本会撑大存储，建议单条控制在几 KB 内。
7. **参数的最终作用**：记忆键对应的具体内容本体。

### 参数 3：`entry`（要追加的一条）

1. **名称 + 类型**：`entry`，字符串（string），工具层校验 `.min(1)` 非空。
2. **参数设计原因**：**因为**流水账式记忆（饮食日志、事件记录）每次只多一条，如果让 AI "读出全部、拼好、整个存回"，既慢又容易在并发下丢数据，**所以**专门设计"只加一行"的参数和方法。
3. **参数类型选择原因**：**因为**一条记录是一句/一段文本，**所以**是 string；工具层强制非空——追加空行没有意义还脏数据。
4. **参数的传入来源**：工具层由 AI 填（如"2025-01-01 午餐：西红柿炒蛋"）。
5. **参数的内部使用逻辑**：在 InMemoryMemory.append 里与旧值用换行符拼接后覆盖存回（见模块2核心定义2）；换个存储实现（数据库）时由该实现自己决定怎么存行记录。
6. **参数的取值范围**：非空字符串；建议单行一条（含换行会破坏"一行一条"的约定）。
7. **参数的最终作用**：让"记账式记忆"有了低成本、不丢历史的写入方式。

### 参数 4：`memory`（createMemoryTools 的入参）

1. **名称 + 类型**：`memory`，`Memory` 接口类型（任何实现都行）。
2. **参数设计原因**：**因为**工具只是"壳"，真正存取要靠一个具体记忆实例，**所以**必须传入；**又因为**壳不该关心实例是内存还是数据库，**所以**参数类型声明为接口 `Memory`（只认标准不认牌子——这是接口作为参数类型的全部意义）。
3. **参数类型选择原因**：**因为**写具体类名（如 InMemoryMemory）会把工具焊死在内存版上，**所以**必须写接口类型；换实现时本函数一行不改。
4. **参数的传入来源**：`sub-agent.ts` 组装 Agent 时传 `spec.memory`；管家侧传自己的记忆实例（可能是 db 包的 SQLite 版）。
5. **参数的内部使用逻辑**：被 4 个工具的 execute 闭包捕获——每个工具执行时都调它的对应方法（**闭包**：函数把外部变量"记住"了，即使 createMemoryTools 已经返回，4 个工具依然握着这个 memory 实例不放）。
6. **参数的取值范围**：任何实现了 Memory 接口的实例；传 null/undefined 会运行报错（TypeScript 类型不允许）。
7. **参数的最终作用**：工具的"存储后端"，决定记忆存在哪、活多久。

### 参数 5：`namespace`（命名空间前缀）

1. **名称 + 类型**：`namespace`，字符串（string），默认值 `'default'`。
2. **参数设计原因**：**因为**多个 Agent 共用存储时必须互不串门（厨师改不了一个清洁工的记忆），**所以**每个 Agent 的记忆键都要加自己的前缀；又因为不传时也得能跑（比如只有管家一个 Agent 的简单场景），**所以**给了默认值 `'default'`。
3. **参数类型选择原因**：**因为**前缀就是拼进键名的文本，**所以**是 string；用参数默认值语法（`namespace = 'default'`）而不是可空类型，调用方代码更干净（不用写 undefined）。
4. **参数的传入来源**：`sub-agent.ts` 传 `spec.id`（子 Agent 的 id，如 'chef'）——**这是"谁的记忆"最天然的标识**。
5. **参数的内部使用逻辑**：只在一处使用——被 `keyOf` 闭包捕获，每次给键加前缀时拼上（`\`${namespace}:${key}\``）。
6. **参数的取值范围**：任意非空字符串都合法；正规取值是子 Agent 的 id（符合 05 文档的 id 规则）；传空串会导致前缀为空（键形如 `:xxx`），不同 Agent 会串号——要避免。
7. **参数的最终作用**：记忆世界的"门牌小区号"，多 Agent 共存时的隔离保障。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、`return this.store.get(key) ?? null` 里的 `?? null`——为什么必须写

**因为** JS 的 Map 取不到值时返回 undefined，而 Memory 接口承诺的是"没有就返回 null"（语义：明确查过、确实没有）；**所以**必须用空值合并运算符 `??`（左边是 null/undefined 时取右边）把 undefined 翻译成 null。**如果删掉它**：返回值类型与接口声明 `Promise<string | null>` 不符，TypeScript 直接编译报错（语法强制要求的典型）；就算绕过类型检查，下游也会因分不清"undefined 还是 null"而写出脆弱代码。

### 2、append 里"先查旧值再拼接"——为什么要两步而不是一步

**因为** Map 没有"追加"原语，追加本质是"读旧 → 拼新 → 写回"三步的复合动作；**而"旧值不存在"是特殊情形**：直接拼会得到 `\n新内容`（开头一个空行），**所以**代码用三元判断分流——有旧值才加换行。**如果去掉判断**：每条流水账的第一行前面都有空行，AI 读到的是脏格式，长期积累可能误导模型理解记忆内容。

### 3、4 个工具全部经 `defineDomainTool` 包装——为什么不用框架的 `tool()` 直接写

**因为**直接用 `tool()` 就得每个工具自己处理异常、自己定返回格式（4 个工具 4 份样板代码），而 `defineDomainTool` 已经把这些做成了流水线（见 02 文档）；**所以**复用它，记忆工具自动获得"统一 JSON 格式 + 异常兜底"。**如果绕开它**：记忆工具报错时（比如存储不可用），异常穿透给 AI，AI 可能以为"读到了空记忆"继续编数据——兜底体系出现缺口。

### 4、工具返回值里的 `value: null`——为什么查不到不报错而是返回 null

**因为**"查一条不存在的记忆"是**正常业务情况**（第一次查当然没有），不是错误；**所以**工具正常返回 `{ value: null }`，AI 读到 null 就明白"没这条，该问人或者先存一条"。**如果改成报错**：AI 每次第一次查记忆都会收到失败结果，行为会变得保守甚至不敢用记忆工具——把正常当异常是设计大忌。

### 5、闭包 `keyOf`——为什么它比"每个工具里写一遍前缀拼接"好

**因为**"加前缀"这个规则是 4 个工具共享的，写 4 遍意味着将来改规则（比如前缀从 `ns:` 换成 `ns/`）要改 4 处、漏一处就串号；**所以**收敛成一个小函数，4 个工具都调用它。**这就是"规则只写一遍"原则**——隔离规则改动时只动一个地方。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 程序启动，经由 `index.ts` 被 `sub-agent.ts`、管家核心等加载；
2. 加载时完成：接口/类/工厂函数定义（无副作用，不占资源）；
3. 应用装配阶段：`createMemory()` 或外部实现（如 `createSqliteMemory`）造出记忆实例，传给 Agent 的 `memory` 参数；
4. `defineSubAgent` 组装 Agent 时调 `createMemoryTools(memory, spec.id)` → 生成 4 个带命名空间前缀的记忆工具挂到 Agent 上，系统提示词同步加一句"你有长期记忆可用"；
5. 运行期：AI 判断某事实值得记住 → 调 `memory_set` / `memory_append` → 过 Zod 校验 → keyOf 加前缀 → Memory 实例落存；需要时调 `memory_get` 读回、`memory_delete` 清理。
6. 任务结束、Agent 工作间关闭——**记忆因为存在 Memory 实例里（而不是对话里）得以幸存**，下个任务接着用。

### 2、文件在整个工程中不可替代的作用

**它给"一次一开、用完即焚"的 Agent 工作模式补上了记忆这块短板**：接口定标准（可插拔）、内存版保底（零配置能跑）、工具转换器（AI 够得着）——三件套缺一不可。没有它，"重启不失忆、跨任务记账"全都无从谈起。

### 3、运行依赖的环境与前置条件

- 依赖 `zod` 与本包的 `capability.ts`（工具包装流水线）；
- 内存版无任何外部依赖；接入数据库版（db 包）时需要数据库环境；
- 前置条件：Agent 组装时正确传入 memory 实例与命名空间。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **`Memory` 接口**：任何"键值式存储"需求都能套（不止 Agent 记忆，比如缓存、配置快照）；
- **`InMemoryMemory`**：单测里的假存储首选——快速、隔离、随建随弃；
- **`createMemoryTools`**：所有 Agent 的记忆能力统一入口，新 Agent 接记忆零成本。

### ⚠️ 易错点

1. **每次调用 `createMemory()` 都是新实例**——想共享数据必须复用同一实例，否则出现"明明存了却读不到"的灵异现象；
2. **值只能是字符串**——存对象要先 `JSON.stringify`，读取后 `JSON.parse`，忘了 parse 直接把字符串当对象用会运行报错；
3. **命名空间传空串会串号**——多个 Agent 的键撞在一起互相覆盖；
4. **重启全丢**——InMemoryMemory 只适合演示/测试，生产必须换 SQLite 版（README 已说明 db 包提供 `createSqliteMemory`）。

### 🔍 调试关键点

- AI 说"我记性没问题"但数据没了：先查它调工具时填的 key 和实际存储的键（有没有前缀、前缀对不对）——`store` 里实际是 `chef:fridge` 这种带前缀的全键；
- 记忆串号（A 读到了 B 的数据）：查 `namespace` 是否传错或传空；
- 演示和测试里行为不一致：八成是两边用了不同 Memory 实现（内存版重启清零 vs SQLite 版持久）。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| `Memory` 接口的 4 个方法签名 | 🚫 不能改 | db 包的 SQLite 实现、管家、全部子 Agent 都按它实现/调用，改一处动全身 |
| get 返回 `null` 的语义 | 🚫 不能改 | "null = 查了没有"是全工程约定，改成 undefined 会让所有实现与调用方失配 |
| `keyOf` 前缀格式 `namespace:key` | 🚫 不能改 | 已落库的历史记忆键都是这个格式，改了旧数据全"失联" |
| 工具名 memory_get/set/append/delete | 🚫 不能改 | 系统提示词、README、交接文档都按这些名字写了 |
| 给工具加"列出所有键"等新工具 | ✅ 可优化 | 经 `defineDomainTool` 包装、注意别让 AI 拿到全量键后乱删 |
| 值类型扩展（支持 JSON 对象自动序列化） | ✅ 可优化 | 改接口是大动作，建议在工具层做转换，别动接口 |
