# 01 · protocol.ts 源码白话详解（任务与结果信封协议）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`protocol.ts`
- 存放路径：`meimaohouse-butler-agent/packages/agent-sdk/src/protocol.ts`
- 它编译后的成品在：`packages/agent-sdk/dist/protocol.js`（其他包实际引用的是编译产物）

### 2、文件存在的核心原因

**因为**整个工程的运行模式是"管家派活 → 子 Agent 干活 → 子 Agent 交差"，而管家和子 Agent 都是 AI 模型在驱动——AI 模型传话最容易出的问题就是：漏填字段、瞎填格式、该说的没说，**所以**必须有一份"双方都必须遵守的标准表格格式"，把派活单长什么样、交差单长什么样、每个格子能填什么，全部用代码写成铁规矩。

**如果没有这个文件，程序会出现的问题：**

- 管家派活时想填什么填什么，子 Agent 收到的任务五花八门，根本没法统一处理，功能直接无法实现；
- 子 Agent 交差时可能只回一句"干完了"，没说成功还是失败、没说失败原因，管家没法向人类汇报，还可能把失败当成功转述（"假成功"事故）；
- 两边的 AI 模型各说各话，出了问题连"是派活错了还是干活错了"都查不清。

### 3、文件的整体定位

这个文件**专门负责"传话格式的规定和把关"**，不负责具体干活。它干三件事：

1. 用 Zod 定义"派活单"（TaskRequest）和"任务信封"（TaskEnvelope）的标准格式；
2. 用 Zod 定义"结果信封"（ResultEnvelope）的标准格式，规定 5 种执行状态；
3. 提供一个小工具函数 `createTaskId`，负责给每个任务生成一个不重复的编号。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- `node:crypto`（Node.js 自带的加密工具模块）：只用其中的 `randomUUID()` 函数，用来生成随机字符串，防止任务编号撞车；
- `zod`（第三方数据校验库）：所有表格格式都是用它定义的。

**谁来调用它（下游）：**

- `sub-agent.ts`（本包内的子 Agent 基类）：拿它的表格当校验器、拿 `createTaskId` 生成任务编号——这是本文件最大的用户；
- `packages/butler-core/butler.ts`（大管家核心）：管家派活时也要用 `TaskRequestSchema`、`createTaskId`、任务/结果信封的类型；
- `packages/db`（数据库层）与各应用：数据库存任务记录、界面展示任务状态，都按这里的字段名来。

**一句话：这是全工程的"普通话字典"，谁跟谁传话都得按它的格式来。**

## 模块2：文件内核心定义与核心函数超详细说明

> 这个文件里没有一大堆传统函数，它的主体是 5 个"校验器定义"（Zod Schema）+ 1 个函数。每个校验器都当核心成员逐个拆解。

### 核心定义 1：`TaskPrioritySchema`（任务优先级表）

1. **名称**：`TaskPrioritySchema`，配套导出的类型名叫 `TaskPriority`。
2. **设计的根本原因**：**因为**管家派活时，有些事急（火警检查）、有些事不急（整理储藏室），如果不给任务分等级，子 Agent 只能按收到顺序傻干，急事可能被慢事堵在后面，**所以**需要一个字段专门标注"这活有多急"。
3. **语法写法的原因**：**因为**TypeScript + Zod 的规范要求，枚举（只能从几个固定值里选）用 `z.enum(['low', 'normal', 'high'])` 定义。不能随便写成普通字符串类型——普通字符串写"asap""很急"这种它也放行，等到了别的程序那里就是不认识的值。用 `z.enum` 后，**填这三个以外的任何词，校验直接打回**。下面一行 `export type TaskPriority = z.infer<typeof TaskPrioritySchema>` 是把校验器"翻译"成 TypeScript 类型，让写代码的人也有类型提示、写错编译时就报错。
4. **内部逻辑分步讲解**：只有一行——声明一个只认 `'low'`（不急）、`'normal'`（普通）、`'high'`（紧急）三个值的枚举校验器。没有更多逻辑，它的价值就在于"把可选项锁死"。
5. **触发条件**：定义后不主动运行；每当有数据经过 `TaskRequestSchema` 校验（里面引用了它），它就自动开始把关。
6. **最终作用**：保证全工程对"优先级"只有三种统一说法，下游程序可以放心按这三种情况写分支处理。
7. **使用场景**：被 `TaskRequestSchema` 里的 `priority` 字段引用；管家派活、界面显示任务紧急程度时都用它的类型。
8. **缺陷/注意事项**：只有三档，想加"urgent"档是全局改动（管家提示词、界面、数据库说明都要跟着改）；新增值时必须保持向后兼容，否则老数据里的值会校验失败。

### 核心定义 2：`TaskRequestSchema`（管家模型填的"派活单"）

1. **名称**：`TaskRequestSchema`，配套两个类型：`TaskRequestInput`（填表前的松散格式）和 `TaskRequest`（审完表后的标准格式）。
2. **设计的根本原因**：**因为**管家模型决定"派什么活"之后，需要一个途径把决定变成子 Agent 能读懂的指令；而模型只该负责"派什么活、参数是什么"这种业务判断，不该让它去编任务编号、目标领域这类系统信息（模型编的编号容易重复、领域容易填错），**所以**把派活单故意做得极简，只留 5 个业务格子，系统格子后面由代码补。
3. **语法写法的原因**：**因为**Zod 要求用 `z.object({...})` 把每个字段和规则写清楚；每个字段后面链式的 `.min(1)`、`.default()`、`.optional()`、`.describe()` 都是 Zod 的规则语法——不这么写，字段就没有约束、没有默认值、没有给 AI 看的说明文字。
4. **内部逻辑分步讲解**（5 个格子逐行看）：
   - `intent`：字符串，`.min(1)` 表示至少 1 个字符（不能空着），`.describe()` 写了给模型看的用法说明和举例（如 inventory_check 查库存、order_groceries 买菜）。`.describe` 不参与校验，它会被转成"给 AI 的参数说明书"，AI 决定怎么填全靠这段话；
   - `params`：`.record(z.string(), z.unknown())` 表示"一个对象，键必须是字符串，值随便什么类型都行"，`.default({})` 表示模型没填就自动补空对象。**因为**不同领域任务参数千差万别（查库存要品类、下单要数量），**所以**这里必须放得下任意结构；
   - `priority`：直接引用核心定义 1，`.default('normal')` 表示不填就当普通优先级；
   - `deadline`：字符串，`.optional()` 表示可以不填，说明文字里写了填 ISO 8601 时间或自然语言都行；
   - `source`：字符串，`.default('human')` 表示这活默认是人类发起的。
5. **触发条件**：管家调用子 Agent 工具时，模型填的参数先过它这关；过了关才有资格变成任务信封。
6. **最终作用**：保证管家模型"派活"的表达被锁死在这 5 个格子里，多填的会被丢掉（Zod 默认丢弃多余键），漏的会按 default 补上——进来的数据永远形状整齐。
7. **使用场景**：`sub-agent.ts` 的 `toButlerTool` 把它直接设为工具入参校验器；管家核心也引用它。
8. **缺陷/注意事项**：`params` 里放的是"任意对象"，等于没校验内容本身——各领域能力要自己再校验一层，别指望这关能查出"数量填成了汉字"这种事。

### 核心定义 3：`TaskEnvelopeSchema`（子 Agent 实际收到的"任务信封"）

1. **名称**：`TaskEnvelopeSchema`，配套类型 `TaskEnvelope`。
2. **设计的根本原因**：**因为**派活单里没有任务编号和目标领域，但子 Agent 干完活必须报"我是哪个号的任务"、管家记录任务也要按编号记账，系统层面必须知道"这活是派给谁的"，**所以**在派活单基础上补上 `task_id`（任务编号）和 `domain`（目标领域）两个系统格子，形成正式信封。派活单是"模型填的草稿"，任务信封是"系统盖章后的正式件"。
3. **语法写法的原因**：**因为**Zod 提供了 `.extend({...})` 语法，可以在已有校验器基础上追加字段而不用把 5 个字段重抄一遍——不这么写，代码就重复，以后派活单加字段时这里会忘着同步，出现两份格式对不上的事故。
4. **内部逻辑分步讲解**：
   - 第一行：`TaskRequestSchema.extend({...})`——先把 5 个业务格子原样继承过来；
   - `task_id`：字符串、至少 1 个字符，说明文字里写明了编号格式（`<agentId>_<时间戳>_<UUID前8位>`）；
   - `domain`：字符串、至少 1 个字符，说明"目标领域标识，即子 Agent 的 id"（如 chef）。
5. **触发条件**：管家侧把派活单补全成任务信封后，子 Agent 的 `handleTask` 收到任务先拿它过一遍校验（见 05 文档）。
6. **最终作用**：子 Agent 拿到的任务永远带编号、带归属，任务可以追踪、可以对账、可以记进数据库。
7. **使用场景**：`sub-agent.ts` 的 `handleTask` 校验入参；管家 delegate 直派任务时也要构造它；数据库任务表按它的字段存。
8. **缺陷/注意事项**：`domain` 没做"必须是已注册的子 Agent id"校验——填一个不存在的 id 会在管家路由层报错，这层校验不归本文件管，排错时先看管家注册表。

### 核心定义 4：`TaskStatusSchema`（执行状态的 5 个标准答案）

1. **名称**：`TaskStatusSchema`，配套类型 `TaskStatus`。
2. **设计的根本原因**：**因为**子 Agent 干完活后"结果"不只有成功和失败两种——有的活要人类拍板（大额采购）、有的活是排期了还没干（定时任务）、有的活是环境里压根没配能力（没接冰箱传感器），如果只有"成功/失败"，这些情况全得挤进"失败"，管家就无法向人类准确转述，**所以**规定了 5 种状态。
3. **语法写法的原因**：**因为**同样是"只能选固定值"，语法和优先级一样用 `z.enum`，不这么写就会放进乱七八糟的自造词。
4. **内部逻辑分步讲解**：5 个值分别是——`done` 成功干完；`failed` 执行失败；`needs_human` 需要人类决策/确认；`deferred` 暂缓/已排期；`unavailable` 当前环境没配执行该任务所需的能力。每个值的含义在下方 `ResultEnvelopeBaseSchema` 的注释里也有对应白话解释。
5. **触发条件**：子 Agent 交差时，`ResultEnvelopeSchema` 校验结果信封，会检查 `status` 是不是这 5 个之一。
6. **最终作用**：让"干活的结局"有统一的 5 种说法，管家按状态决定转述口径（比如 needs_human 就转成"这事需要你确认"）。
7. **使用场景**：结果信封校验、管家汇报逻辑、数据库任务状态列、界面状态标签。
8. **缺陷/注意事项**：这是全工程约定，**增删值是跨包大改动**（管家提示词、子 Agent 培训文档、界面都按它写的），千万别只改这里。

### 核心定义 5：`ResultEnvelopeBaseSchema` + `ResultEnvelopeSchema`（子 Agent 的"交差单"）

1. **名称**：`ResultEnvelopeBaseSchema`（交差单的公共底板，本文件内部用）、`ResultEnvelopeSchema`（对外正式校验器）、配套类型 `ResultEnvelope`。
2. **设计的根本原因**：**因为**子 Agent 交差必须说清：是哪个号的任务、干得怎么样、失败为什么、后续有什么建议——管家只看这张单子（看不到子 Agent 工作过程），单子缺信息管家就成了瞎子；**又因为**"失败必须写原因"这种规则跟状态有关（成功单不需要 error），一张底板表达不了"不同状态不同必填项"，**所以**先用公共底板装 7 个公共格子，再用"联合校验器"按状态分 5 份、每份单独加规则。
3. **语法写法的原因**：
   - **因为**Zod 的 `z.discriminatedUnion('status', [...])` 语法专门解决"同一批数据按某个字段的值走不同规则"的问题——它要求每个分支把那个字段写成"死值"（`z.literal('done')` 这种），校验时先看 status 是什么值，直接跳到对应那份规则检查，又快又准；
   - **因为**TypeScript 拿到校验结果后也会按 status 自动收窄类型（比如 `status === 'failed'` 时才让你访问 `error`），写管家代码时不会误用字段；
   - **为什么不写成一张普通表**：普通表里 `error` 只能统一"必填"或"选填"——统一必填则成功单也得编个错，统一选填则失败单可以不写原因，两头都是坑。
4. **内部逻辑分步讲解**：
   - 公共底板 7 个格子（详细拆解见模块3）：`task_id`、`summary`、`detail`、`error`、`error_code`、`suggestions`、`completed_at`；
   - 然后 5 份分支：底板 + `status: z.literal('done')`（成功版）；底板 + `status: z.literal('failed')` + **把 error 从"选填"覆盖成 `.min(1)` 必填**（失败版，这是关键设计：失败不给理由的单子直接打回）；底板 + 各自的 literal（needs_human 需人类拍板版、deferred 已排期版、unavailable 能力未配置版）。
5. **触发条件**：子 Agent 每次交差，其内部模型被强制按这个格式输出（`structuredOutputSchema` 就指到它，见 05 文档），输出结果还要再过它校验。
6. **最终作用**：管家收到的每一张交差单都格式统一、信息完整、失败必有原因——管家才能照单转述、照单记账、照单转派后续协作。
7. **使用场景**：`sub-agent.ts` 的 Agent 构造（当强制输出格式）、`handleTask` 的返回类型；管家核心的 `ResultEnvelope` 类型引用；数据库任务表存结果。
8. **缺陷/注意事项**：`summary` 只要非空就算合格，AI 可能写得很敷衍——本文件管不了"写得好不好"，只能靠 `sub-agent.ts` 的系统提示词要求"面向人的一句话"（见 05 文档模块2）。

### 核心函数：`createTaskId(agentId)`（任务编号生成器）

1. **函数名称**：`createTaskId`，入参 `agentId: string`，返回 `string`。
2. **函数设计的根本原因**：**因为**每个任务都必须有一个全工程不重复的编号，否则管家分不清两次派活、数据库记录会互相覆盖；而编号不能让 AI 模型去编（模型会重复、会漏），**所以**必须由代码用"领域 ID + 时间戳 + 随机数"三件套机械生成，既唯一又自带信息量。不封装这个函数，各处就会自己拼编号，格式五花八门，排查问题时没法按编号检索。
3. **函数语法写法的原因**：**因为**它是纯工具函数（不依赖对象状态），所以用普通 `export function` 导出；**因为**生成编号瞬间完成、不需要等待外部（不像调模型要联网），**所以**不需要 async，直接同步返回字符串——同步还能让调用方少写一个 await，用起来更省事。
4. **函数内部完整逻辑分步讲解**：就一行返回语句，但拆开看是三段拼接（用反引号模板字符串 `` `${agentId}_${...}_${...}` `` 把三段用下划线连起来）：
   - 第 1 段：`agentId`——谁家的任务（如 chef），编号一眼看出归属；
   - 第 2 段：`Date.now().toString(36)`——当前时间的毫秒数转成 36 进制（0-9 + a-z）的短字符串。**为什么要转进制**：毫秒数字直接用有 13 位，36 进制只要 8 位左右，编号短；**为什么不能只用它**：同一毫秒内可能生成两个编号，会撞车，所以还需要第 3 段；
   - 第 3 段：`randomUUID().replaceAll('-', '').slice(0, 8)`——先用 `randomUUID()` 生成一个标准随机 UUID（如 `3b241101-e2bb-4255-8caf-4136c566a962`），再把里面的 `-` 全部删掉，只截取前 8 位作为随机尾巴。三段合起来：同一毫秒内随机尾巴几乎不可能相同，编号唯一性就有了双保险。
5. **函数的触发条件**：管家侧每次把"派活单"补全成"任务信封"时调用（`sub-agent.ts` 的 `toButlerTool` 回调里、管家核心的 delegate 流程里）。
6. **函数的最终作用**：产出格式统一的任务编号（如 `chef_lx3k9f2a_4f8a2b1c`），贯穿任务信封、结果信封、数据库任务记录、事件日志，让一次任务的全链路可追踪。
7. **函数的使用场景**：`sub-agent.ts` 的 `toButlerTool`（管家派活）、`butler-core` 的 delegate 直派——所有"生成新任务"的地方都用它，全工程只此一处编号逻辑。
8. **函数的缺陷/注意事项**：**改不得**：编号三段式的格式写进了协议说明（`task_id` 字段的 describe 文字）和交接文档，擅自改格式会导致按编号做的统计/检索全部失灵；8 位随机尾巴在单机场景足够，但理论上非绝对唯一，若未来多机并发海派任务需评估加长。

## 模块3：文件内每一个参数超详细说明

> 按出现顺序：先派活单 5 个格子、任务信封 2 个格子，再交差单 8 个格子，最后函数入参。

### 参数 1：`intent`（任务意图）

1. **名称 + 类型**：`intent`，字符串（string）。
2. **参数设计原因**：**因为**子 Agent 收到任务第一件事是判断"这活是要我干什么"，没有这个字段子 Agent 只能瞎猜，**所以**派活单必须有意图字段，用动词短语写清楚要干什么。
3. **参数类型选择原因**：**因为**意图本质是一句人话/机话短语（如 inventory_check），不是数字也不是复杂结构，**所以**用字符串；又因为空字符串等于没说，**所以**加 `.min(1)` 强制非空——选数字或布尔都表达不了意图，选对象又过度复杂。
4. **参数的传入来源**：管家模型派活时填（AI 根据"人说了什么"和子 Agent 的能力描述，自己组织出意图词）。
5. **参数的内部使用逻辑**：校验时只查"非空"；通过后随信封进入子 Agent，`sub-agent.ts` 的系统提示词明确要求"按 intent 判断意图"——子 Agent 模型读它来决定调哪个工具。
6. **参数的取值范围**：任何非空字符串都合法；但工程惯例是用 `小写_下划线` 动词短语（如 `inventory_check`、`order_groceries`、`safety_check`）。空字符串不合法，直接校验失败。
7. **参数的最终作用**：它是任务信封的"灵魂字段"——决定子 Agent 干什么活，也是任务记录里"这活是什么"的依据。

### 参数 2：`params`（任务参数）

1. **名称 + 类型**：`params`，对象（键为 string、值不限类型的记录，Zod 写法 `z.record(z.string(), z.unknown())`），带默认值 `{}`。
2. **参数设计原因**：**因为**光有意图不够——"买菜"得知道买什么买多少，"查库存"得知道查哪个品类，**所以**需要一个兜底格子装具体参数。
3. **参数类型选择原因**：**因为**不同领域任务参数结构完全不同（厨房要食材名+数量，清洁要房间名），固定结构装不下，**所以**用"键值不限"的记录类型；用 `.unknown()` 而不是 `.any()` 是 Zod 的严谨写法：unknown 表示"先不检查但保持类型安全"，any 会把类型检查彻底关掉，编译器就帮不上忙了。`.default({})` 保证模型不填也不会校验失败（有的任务确实不需要参数）。
4. **参数的传入来源**：管家模型从人类话语里提取（"买两斤西红柿"→ `{ item: '西红柿', quantity: 2 }` 这类结构）。
5. **参数的内部使用逻辑**：本文件只做"形状检查"（必须是对象）；通过后随信封进子 Agent，由各领域工具的入参校验器做二级检查（见 02 文档）——这是刻意设计的两级校验。
6. **参数的取值范围**：任意 JSON 对象都合法（包括空对象）；填数组、字符串、数字等非对象会校验失败。
7. **参数的最终作用**：把"干什么"（intent）和"干活的细节"（params）分开，让派活协议能适配无限多种领域任务而不需要改协议。

### 参数 3：`priority`（优先级）

1. **名称 + 类型**：`priority`，枚举字符串（`'low' | 'normal' | 'high'`），默认 `'normal'`。
2. **参数设计原因**：**因为**管家同时面对多件事时需要区分轻重缓急，**所以**派活单必须带优先级，让子 Agent 和记录系统知道处理顺序。
3. **参数类型选择原因**：**因为**可选项固定且少，**所以**用枚举而不是自由字符串——自由字符串会混进"asap""最高"这类没法程序化排序的值；用数字分档（1/2/3）又可读性差、容易约定错位，三档英文枚举是双方 AI 都能准确理解的写法。
4. **参数的传入来源**：管家模型根据语境判断填写；模型不填时 `.default('normal')` 自动补普通级。
5. **参数的内部使用逻辑**：校验时对照三档枚举；通过后随信封进子 Agent 和数据库，供排序/展示用（本文件自身不做排序逻辑）。
6. **参数的取值范围**：仅 `'low'`、`'normal'`、`'high'` 三个值合法，其他一律打回。
7. **参数的最终作用**：任务有轻重标签，管家汇报时能说"这单是加急件"，下游排序有依据。

### 参数 4：`deadline`（截止时间）

1. **名称 + 类型**：`deadline`，字符串（string），选填。
2. **参数设计原因**：**因为**有些任务有时限（"下班前把厨房收拾好"），没有截止时间，子 Agent 和排期系统就不知道什么时候算违约，`deferred`（已排期）状态也无从谈起，**所以**留了这个格子。
3. **参数类型选择原因**：**因为**时间格式需要兼容两种写法——标准的 ISO 8601（`2025-01-01T18:00:00`）和自然语言（"今晚六点前"），后者没法用 Date 类型直接表达，**所以**用字符串装，具体解析交给下游（要精确处理时间时再转 Date）；用 Date 类型会把"自然语言"这种 AI 擅长理解但程序不好解析的写法直接堵死。
4. **参数的传入来源**：管家模型填（人类说了时限就填，没说就不填）。
5. **参数的内部使用逻辑**：本文件只检查"如果填了，必须是字符串"；内容语义不做校验（这是刻意的宽松，因为自然语言时限是合法输入）。
6. **参数的取值范围**：不填 = 合法；填了则任意非空字符串都通过校验，但工程惯例推荐 ISO 8601 或清晰的自然语言。填乱码会导致下游解析不了时间，属于"校验放行但业务出错"的情况。
7. **参数的最终作用**：让任务带上时限信息，支撑排期、催办和 `deferred` 状态的语义。

### 参数 5：`source`（请求来源）

1. **名称 + 类型**：`source`，字符串（string），默认 `'human'`。
2. **参数设计原因**：**因为**派活的不一定是人——可能是定时任务自动派、可能是另一个系统转派，追溯"这活最初谁发起的"对排查问题和权限控制很重要，**所以**留了来源字段。
3. **参数类型选择原因**：**因为**来源是开放集合（human、timer、system……未来还会加），**所以**不能用枚举锁死，用自由字符串 + 默认值最合适；默认 `'human'` 是因为绝大多数请求是人发起的，少填一个字的成本最低。
4. **参数的传入来源**：管家模型或调用代码填写；不填自动补 `'human'`。
5. **参数的内部使用逻辑**：校验只查"是字符串"；随后随信封流转，供审计和展示。
6. **参数的取值范围**：任意字符串合法；惯例值 `human`（人类）、系统类的来源由调用方自行约定。空字符串在 Zod 默认下不报错（这里没加 min(1)），属于本文件校验较松的一处，注意别依赖它做严格判断。
7. **参数的最终作用**：任务可溯源，出问题时能查到"最初是谁要干这件事"。

### 参数 6：`task_id`（任务编号）

1. **名称 + 类型**：`task_id`，字符串（string），至少 1 个字符。
2. **参数设计原因**：**因为**"派活"和"交差"是两次独立传输，中间隔了很久，没有编号就对不上是哪单，**所以**信封必须带唯一编号，把请求和结果绑死。
3. **参数类型选择原因**：**因为**编号是"由三段文本拼成的标识"（见 `createTaskId`），**所以**必须是字符串；不能用数字——数字做不了带语义的三段拼接，也容易在大数场景出精度问题。加 `.min(1)` 防止空编号混进来。
4. **参数的传入来源**：管家侧代码调用 `createTaskId(spec.id)` 生成（**不是模型填的**——这是本协议的关键分工）。
5. **参数的内部使用逻辑**：派活时写进任务信封；子 Agent 交差时必须原样带回来（`sub-agent.ts` 的 `handleTask` 会强制用入参的 task_id 覆盖返回值，防止子 Agent 乱改号）。
6. **参数的取值范围**：任何非空字符串通过校验；正规取值是 `createTaskId` 生成的 `<agentId>_<base36时间戳>_<UUID前8位>` 格式。
7. **参数的最终作用**：全工程任务的"身份证号"，请求与结果对账、数据库主键关联、日志检索全靠它。

### 参数 7：`domain`（目标领域）

1. **名称 + 类型**：`domain`，字符串（string），至少 1 个字符。
2. **参数设计原因**：**因为**信封要能回答"这活是派给谁的"，管家记录、转发、统计都要按领域分组，**所以**必须有领域字段；而且它必须由系统填（等于子 Agent 的注册 id），不能让模型乱填。
3. **参数类型选择原因**：**因为**领域标识就是子 Agent 的 id（如 chef、cleaner），id 本身被 `defineSubAgent` 规定为小写字母开头的字符串（见 05 文档），**所以**这里用字符串并强制非空，两边格式才能咬合。
4. **参数的传入来源**：管家侧代码填，值就是 `spec.id`（`sub-agent.ts` 的 `toButlerTool` 里 `domain: spec.id`）。
5. **参数的内部使用逻辑**：随任务信封传给子 Agent；数据库按它归类任务；管家按它判断该转给谁。
6. **参数的取值范围**：任何非空字符串过校验；正规取值 = 已注册子 Agent 的 id。
7. **参数的最终作用**：任务的"收件地址"，保证派活不会派错门。

### 参数 8：`status`（执行状态）

1. **名称 + 类型**：`status`，枚举字符串（5 个值，见核心定义 4）。
2. **参数设计原因**：**因为**交差单必须一眼看出"结局是什么"，管家的转述逻辑完全由它驱动，**所以**它是结果信封的第一个字段、也是分派校验规则的"开关字段"。
3. **参数类型选择原因**：**因为**Zod 的 discriminatedUnion 要求判别字段必须是"死值"（`z.literal`），**所以**它必须是能精确比对的字符串枚举——换成数字或布尔虽然技术上也能当判别符，但可读性极差（AI 也不知道 3 是什么意思）。
4. **参数的传入来源**：子 Agent 模型按系统提示词要求填写；若模型没返回结构化结果，`sub-agent.ts` 会兜底填 `failed`。
5. **参数的内部使用逻辑**：校验时它是"分诊台"——先看它是 5 个值中的哪个，决定套用哪份分支规则（比如是 failed 就强制检查 error 非空）。
6. **参数的取值范围**：仅 `done / failed / needs_human / deferred / unavailable` 五个值合法。
7. **参数的最终作用**：决定管家下一步怎么说、怎么做；也是任务表状态列的取值来源。

### 参数 9：`summary`（一句话总结）

1. **名称 + 类型**：`summary`，字符串（string），至少 1 个字符。
2. **参数设计原因**：**因为**人类最终只听管家转述一句话结果，管家也只看交差单——没有这个字段，管家就得自己去 detail 里挖结论，转述质量不可控，**所以**强制子 Agent 用"面向人的语言"给出结论。
3. **参数类型选择原因**：**因为**结论是一句自然语言，**所以**是字符串；`.min(1)` 保证不能交白卷。
4. **参数的传入来源**：子 Agent 模型填写（系统提示词里专门要求"summary 用面向人的一句话"）。
5. **参数的内部使用逻辑**：校验非空；管家拿它直接作为向人类汇报的主文案。
6. **参数的取值范围**：非空字符串合法；惯例是简短、口语、不带专业术语的一句中文。
7. **参数的最终作用**：全链路"最后一公里"的体验担当——人类看到的答复质量主要由它决定。

### 参数 10：`detail`（结构化详情）

1. **名称 + 类型**：`detail`，对象（键 string、值不限），选填。
2. **参数设计原因**：**因为**一句话装不下所有信息（查库存的实际清单、订单号、报价明细），管家后续任务或其他系统可能需要引用原始数据，**所以**留一个可选的"附件包"格子。
3. **参数类型选择原因**：**因为**各领域详情结构不同，**所以**与 `params` 同理用"键值不限"的记录类型，保持协议通用。
4. **参数的传入来源**：子 Agent 模型把工具返回的关键数据整理后填入。
5. **参数的内部使用逻辑**：校验"填了就必须是对象"；管家可读可存（落库到任务记录的详情字段）。
6. **参数的取值范围**：不填合法；填了必须是 JSON 对象（不能是数组/字符串直接塞顶层）。
7. **参数的最终作用**：结果的可追溯数据底座——summary 给人看，detail 给程序和后续任务看。

### 参数 11：`error`（失败原因）

1. **名称 + 类型**：`error`，字符串（string）；在公共底板里是选填，但在 `failed` 分支里被覆盖为必填（至少 1 字符）。
2. **参数设计原因**：**因为**失败任务如果不说原因，管家没法向人类解释、没法决定重试还是换方案，**所以**专门规定"失败必须写原因"。
3. **参数类型选择原因**：**因为**原因是给人看的描述（"冰箱传感器没响应"），**所以**用字符串；用"判别联合"的分支覆盖语法（failed 分支里重新定义 error 为 `.min(1)`）来实现"状态相关必填"——这是 Zod 表达条件规则的正规手法。
4. **参数的传入来源**：子 Agent 模型写（业务失败时）；或 `sub-agent.ts` 的 catch 兜底自动填（程序异常时）。
5. **参数的内部使用逻辑**：status=failed 时校验强制非空，空着整张单子打回；其他状态下填了也只是附带信息。
6. **参数的取值范围**：failed 时必须非空；其他状态可省略。
7. **参数的最终作用**：失败的"病历本"，支撑管家向人类解释、决定补救方案，也是排查问题的第一线索。

### 参数 12：`error_code`（机器可读错误码）

1. **名称 + 类型**：`error_code`，字符串（string），选填。
2. **参数设计原因**：**因为**error 是给人看的自然语言，程序没法可靠判断"到底是哪种失败"（是没配能力还是网络超时？），管家要做自动化决策（比如 unavailable 就建议去配能力）需要稳定不变的标识，**所以**加了机器可读的错误码格子。工程惯例值：`capability_not_configured`（能力未配置）。
3. **参数类型选择原因**：**因为**错误码是程序比对的短标识（`snake_case` 短语），**所以**用字符串；不用枚举是为了让各领域自由扩展自己的码表，协议不做死。
4. **参数的传入来源**：子 Agent 模型或领域代码填写；比如厨师 Agent 的系统提示词明确规定"能力未配置时 status=unavailable 且 error_code=capability_not_configured"。
5. **参数的内部使用逻辑**：本文件只查类型；管家和界面按码值做分支展示/决策。
6. **参数的取值范围**：任意字符串合法；惯例用 `小写下划线` 短语，且应保持稳定不要频繁改名。
7. **参数的最终作用**：让"失败"可以被程序可靠分类处理，而不是只能靠读人话猜。

### 参数 13：`suggestions`（后续建议）

1. **名称 + 类型**：`suggestions`，字符串数组（string[]），选填。
2. **参数设计原因**：**因为**子 Agent 是平级、互相不认识的（工程铁律：子 Agent 之间不直接来往），厨师发现"得先修冰箱"时不能直接喊清洁工，**所以**设计了"把协作请求写进建议、由管家转派"的机制，这是跨域协作的唯一正规通道。
3. **参数类型选择原因**：**因为**建议可能有多条（先修冰箱、顺便补货），**所以**用数组；每条是给人/AI 看的一句话，**所以**元素是字符串。
4. **参数的传入来源**：子 Agent 模型填写。
5. **参数的内部使用逻辑**：校验"填了必须是字符串数组"；管家读到后会评估并转派给对应领域子 Agent（新任务从头走一遍派活流程）。
6. **参数的取值范围**：不填合法；填则必须是 `string[]`（每条一个建议）。
7. **参数的最终作用**：子 Agent 之间的"协作申请书"，是整个"平级不互聊、一切经管家"架构能运转起来的关键部件。

### 参数 14：`completed_at`（完成时间）

1. **名称 + 类型**：`completed_at`，字符串（string），选填。
2. **参数设计原因**：**因为**管家记录任务、生成报表需要知道"什么时候干完的"，而子 Agent 自己最清楚完成时刻，**所以**让它随单报告时间。
3. **参数类型选择原因**：**因为**时间要在 JSON 里传输（全协议要求所有字段 JSON 可序列化，见文件头注释），**所以**用 ISO 8601 字符串而不是 Date 对象——Date 直接 JSON 序列化会变成国际标准时间字符串，信息易失真，不如一开始就约定字符串格式。
4. **参数的传入来源**：子 Agent 填；若它没填，`sub-agent.ts` 会自动补当前时间（`envelope.completed_at ?? new Date().toISOString()`）。
5. **参数的内部使用逻辑**：校验"填了必须是字符串"；管家存档、排序、超时分析时使用。
6. **参数的取值范围**：不填合法（会被下游补）；填则惯例为 ISO 8601 格式字符串。
7. **参数的最终作用**：任务时间线的终点标记，支撑"这单花了多久"类统计。

### 参数 15：`agentId`（createTaskId 的入参）

1. **名称 + 类型**：`agentId`，字符串（string）。
2. **参数设计原因**：**因为**编号第一段要标明"这是哪个领域的任务"，而调用方（管家侧）手里正握着子 Agent 的 id，**所以**设计为必传参数，让编号天然带归属。
3. **参数类型选择原因**：**因为**它要直接拼进字符串模板，且来源就是 `spec.id`（字符串），**所以**类型为 string；本函数没加格式校验，信任上游的 id 已经过 `defineSubAgent` 的正则检查（两层防线的设计：注册时严查、生成时信任）。
4. **参数的传入来源**：调用方传入，通常是子 Agent 的 `spec.id`（如 'chef'）。
5. **参数的内部使用逻辑**：仅有一处使用——作为模板字符串的第一段拼进编号。
6. **参数的取值范围**：任意字符串都能跑（不报错）；正规取值必须符合子 Agent id 规则（小写字母开头，仅 a-z 0-9 _ -），否则生成的编号会带非法字符，下游按格式解析时会出错。
7. **参数的最终作用**：让任务编号自带"归属领域"信息，看编号就知道这活是谁家的。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、`z.record(z.string(), z.unknown())`——为什么要两个参数

**因为**本工程用的 Zod 是 v4 版（见 `packages/agent-sdk/package.json` 的 `"zod": "^4.1.12"`），v4 的 record 语法**强制要求**把"键的校验器"和"值的校验器"都写出来（旧版 v3 允许只写一个），**所以**代码里是两个参数。如果按旧版习惯只写一个参数，编译/运行会直接报错——这是"语法强制要求必须这么写"的典型例子。

### 2、`TaskRequestInput`（z.input）与 `TaskRequest`（z.output）——为什么要导出两个类型

**因为**带 `.default()` 的字段在"填表前"和"审表后"类型不一样：填表前 `priority` 可以不填（所以类型里它是可缺省的），审表后它一定有值（所以是必有的）。**所以**用 `z.input<>` 描述"进去前的松散形状"（给填表的管家模型侧用），用 `z.output<>` 描述"出来后的标准形状"（给用表的子 Agent 侧用）。如果只用一个类型，要么填表侧被逼着填默认值（麻烦），要么用表侧还得手动判空（隐患）——两个类型各管一头，类型安全两头都不破。

### 3、`ResultEnvelopeSchema` 的"判别联合"（discriminatedUnion）——为什么不能简化

**因为**"失败必须带原因"是跨字段的条件规则（status=failed 才要求 error 必填），普通对象校验器表达不了"字段 A 的值决定字段 B 的必填性"，**所以**必须用判别联合把 5 种状态拆成 5 份规则。**如果去掉它**、把 5 份合并成一张普通表：error 要么全必填（成功单被逼造假错误信息）、要么全选填（失败单可以不写原因，管家变成瞎子）——两种结局都破坏协议初衷。

### 4、`createTaskId` 的三段式编号——为什么每一段都不可少

- 去掉 `agentId` 段：看编号不知道是谁家的任务，按领域检索要查库才能对上；
- 去掉时间戳段：编号失去时间顺序，人肉排查日志时无法按时间粗排；
- 去掉随机段：同一毫秒派两单必撞号，任务记录互相覆盖。
**所以**三段缺一不可，这是"唯一性 + 可读性 + 碰撞兜底"的三角平衡。

### 5、文件头注释里的硬性约定——"全部字段必须 JSON 可序列化"

**因为**任务信封要被 `JSON.stringify` 成文本塞给子 Agent 模型（AI 之间只能传文字），结果信封也要以 JSON 文本形式回到管家，**所以**所有字段都必须是能被 JSON 无损表示的类型（字符串、数字、数组、普通对象）。这就是为什么时间用字符串、参数用普通对象——**一旦有人塞进函数、Date 对象这类不可序列化的东西，传输环节就会丢数据或报错**。这条约定是全协议的隐形地基。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 程序启动，其他包通过 `import ... from '@meimaohouse/agent-sdk'`（经 `index.ts` 转发）加载本文件；
2. 加载时执行的操作仅仅是：向 `node:crypto`、`zod` 拿工具；创建 6 个校验器常量和 1 个函数（**不执行任何校验**——校验器只是"规则定义"，不是"检查动作"）；
3. 运行期第一次被真正使用：管家模型派活 → 模型填的参数过 `TaskRequestSchema` → 管家侧代码调 `createTaskId` 补编号、补领域 → 生成正式任务信封；
4. 子 Agent 收到信封 → 过 `TaskEnvelopeSchema` 校验 → 干活 → 按 `ResultEnvelopeSchema` 的格式产出交差单；
5. 交差单回到管家 → 管家按 `status` 转述、按 `task_id` 记账、按 `suggestions` 决定是否转派。

### 2、文件在整个工程中不可替代的作用

**它是全工程的"通信宪法"**：管家与子 Agent 说同一种语言、任务全链路可追踪、AI 的不确定性被校验器兜底——没有它，"一个管家 + N 个平级子 Agent"的架构根本组装不起来。

### 3、运行依赖的环境与前置条件

- 依赖 Node.js 内置的 `crypto` 模块和第三方库 `zod`（v4）；
- 不依赖任何模型厂商、数据库、网络——**纯规则文件**，配置好依赖就能跑；
- 编译要求 TypeScript 严格模式开启（工程 `tsconfig.base.json` 的 `strict: true`），本文件的类型定义在严格模式下才有完整的类型保护效果。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- `createTaskId`：任何需要"不重复编号"的场景都能直接用（不限于任务，比如事件记录、请求追踪）；
- `TaskStatusSchema` 的 5 状态设计：任何"AI 干活交差"的场景都适用，新增子 Agent 不要另造状态词。

### ⚠️ 易错点（写代码时最容易踩的坑）

1. **类型用错对**：给"填表侧"代码标注类型时要用 `TaskRequestInput`（允许缺省默认字段），给"用表侧"用 `TaskRequest`——用反了会莫名报"属性可能不存在"。
2. **failed 忘写 error**：直接构造结果信封（不走模型）时，忘了 error 会在校验时被 Zod 打回，报错信息是"Required at error"——看到它先查 status 是否为 failed。
3. **手写 task_id**：任何地方都别手搓编号，一律调 `createTaskId`，否则格式分裂。

### 🔍 调试关键点

- 报错含 `TaskEnvelope`：先打印收到的原始信封，对照模块3逐字段检查——大概率是漏了 `task_id` 或 `domain`；
- 模型交差被拒：Zod 的报错会精确到"哪个字段、哪条规则"，如 `String must contain at least 1 character(s) at summary`，按字段名定位；
- 编号疑似重复：先确认两次调用是否在同一毫秒且随机段相同（概率极低），再查是否有人绕过 `createTaskId` 手写编号。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| `TaskStatusSchema` 的 5 个值 | 🚫 不能改 | 全工程约定，改动等于跨包大手术（见 00 总览全局红线 2） |
| 字段名（task_id/intent/status 等） | 🚫 不能改 | 管家、子 Agent、数据库三方按名字读写 |
| `failed` 分支 error 必填规则 | 🚫 不能删 | 删了等于允许"失败不交代原因"，管家汇报质量崩塌 |
| `createTaskId` 三段式格式 | 🚫 不能改 | 格式已写进协议说明与交接文档 |
| 给字段补 `.describe` 说明文字 | ✅ 可优化 | 纯提示文字，写清楚反而能提升模型填表准确率 |
| 增加新的校验（如 domain 白名单） | ✅ 可优化 | 注意评估对现有调用方的影响，需同步管家侧 |
