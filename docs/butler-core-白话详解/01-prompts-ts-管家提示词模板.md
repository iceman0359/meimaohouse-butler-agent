# 01 · prompts.ts 源码白话详解（管家提示词模板）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`prompts.ts`
- 存放路径：`meimaohouse-butler-agent/packages/butler-core/src/prompts.ts`
- 编译产物：`packages/butler-core/dist/prompts.js`

### 2、文件存在的核心原因

**因为**管家也是 AI 模型——它不知道"我是管家、我手下有谁、我该守什么规矩"，这些全要靠一段"岗位说明书"（system prompt）在每次对话时告诉它；**而**这份说明书有两个特殊难题：① 手下工人是动态的（今天注册了厨师清洁工，明天可能加园丁），写死就要每加一个工人改一次代码；② 规矩必须和整个工程的架构原则（见面隔离、只调度不干活、平级转派）逐条对齐，漏一条管家行为就跑偏。**所以**必须有一个模板函数：每次创建管家 Agent 时，把"当前花名册 + 是否有记忆工具"现场拼进说明书——**新增子 Agent 零改动，说明书自动更新**。

文件头注释原话："核心纪律：管家只做调度/记忆/汇报，不亲自执行领域事务；子 Agent 清单（花名册）由注册表动态生成，保证新增子 Agent 无需改 prompt。"

**如果没有这个文件，程序会出现的问题：** 要么管家没有说明书（行为完全失控：亲自瞎编领域答案、把内部工具名和任务编号念给人类听）；要么说明书写死花名册（每加一个子 Agent 就要改两处代码，迟早不同步）。

### 3、文件的整体定位

这个文件**专门负责"管家说什么话、守什么规矩"的内容生产**：1 个类型（花名册条目）+ 1 个模板函数。它是纯文案 + 少量拼接逻辑，但它是管家行为的"总开关"——管家模型的一切决策都以此为纲。

### 4、文件的依赖关系

**它需要调用谁（上游）：** 谁都不依赖——零 import（文案文件保持纯净，与 chef 的 capabilities.ts 同理：最底层的东西不牵连别人）。

**谁来调用它（下游）：**

- `butler.ts` 的 `buildAgent()`：`this.customPrompt ?? buildButlerSystemPrompt(this.listAgents(), Boolean(this.memory))`——没自定义就用内置模板；
- `index.ts`：把 `buildButlerSystemPrompt` 和 `RosterEntry` 导出给外部（想自己拼说明书的高级用法）。

**一句话：管家的"员工手册印刷厂"，每次开机按当前员工名单现印一份。**

## 模块2：文件内核心定义与核心函数超详细说明

### 核心定义 1：`RosterEntry`（花名册条目的形状）

1. **名称**：`RosterEntry`，接口，4 个必填字段：`id`、`name`、`domain`、`description`。
2. **设计的根本原因**：**因为**模板函数的入参是"一份工人名单"，名单每一行要有什么信息必须先说清——恰好是"管家模型决定派活"需要的最小四件套（工号、称呼、管辖范围、能力描述），**所以**定义这个接口。它其实和 agent-sdk 的 `SubAgentSpec` 前四个字段一一对应——**但刻意单独定义而不直接引用 SubAgentSpec**：模板只需要"派活决策所需的信息"，不需要把 tools/model/memory 等装配细节也暴露给提示词层（信息最小化，依赖也最小化）。
3. **语法写法的原因**：四个字段全必填 string——**因为**四样缺一不可（没有 id 就没法派活、没有 description 管家就不知道派不派），**所以**不加 `?`，调用方漏填编译期就报错。
4. **内部逻辑分步讲解**：id 工号（chef）；name 称呼（厨师）；domain 管辖（厨房域）；description 能力描述（会什么活）。
5. **触发条件**：不运行；作为 buildButlerSystemPrompt 的入参元素类型 + listAgents() 的返回类型。
6. **最终作用**：花名册的标准行格式。
7. **使用场景**：butler.ts 的 listAgents 产出它、本文件的模板消费它。
8. **缺陷/注意事项**：description 的质量直接决定派活准确率（agent-sdk 05 文档强调过的"给 AI 的广告位"）——写含糊了管家就派错门。

### 核心函数：`buildButlerSystemPrompt(subAgents, hasMemory)`（说明书印刷机）

1. **函数名称**：`buildButlerSystemPrompt`，入参 `subAgents: RosterEntry[]`（当前花名册）和 `hasMemory = false`（是否配了记忆工具，默认没配），返回 `string`（完整说明书）。
2. **函数设计的根本原因**：**因为**说明书里"手下有哪些人"和"有没有长期记忆"这两块是**随装配变化的**，不能写死；**而**角色定位、工作纪律、对话风格是**永远不变的**，**所以**函数把"不变的部分"写死、"变的部分"现场拼——这就是"模板"二字的含义。
3. **函数语法写法的原因**：
   - **因为** TypeScript 参数默认值语法让 `hasMemory` 可以不传（大多数场景先不配记忆），**所以** `hasMemory = false`；
   - **因为**说明书是多行大文本，**所以**用模板字符串（反引号）整段书写、用 `${roster}` 和 `${memorySection}` 两个变量嵌进去——比一行行字符串拼接可读性强得多；
   - **因为**函数是纯函数（同样输入永远同样输出、无副作用），**所以**可以放心在每次 buildAgent 时反复调用。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：**拼花名册**——有工人：每个工人生成一行 `- chef（厨师 / 厨房域）：掌管厨房域……`（工号、称呼、领域、能力描述一次给全），多行用换行符连接；没工人：占位文案 `（暂无专职人员，注册子 Agent 后此处自动出现）`——**为什么空名单也要给文案**：**因为**空着会让模型困惑"这里是坏了吗"，占位文案明示"这不是错误，是人还没到岗"；
   - 第 2 步：**拼记忆段**——有记忆工具时生成一句"【长期记忆】你可以使用 memory_get / memory_set / memory_append / memory_delete 工具保存长期事实。"，没有时是空串——**为什么工具名要在这里念一遍**：**因为**模型只有在说明书里被明确告知工具名和用途，才会主动使用记忆工具（工具虽然挂在身上，没人教就基本不会用）；
   - 第 3 步：**组装整份说明书**——身份宣示（"你是庄园的大管家，人类主人只与你对话"）→ 你的角色（向上接需求/向下派任务）+ 花名册 → 六条工作纪律 → 对话风格 + 记忆段。
5. **函数的触发条件**：每次 `buildAgent()` 创建管家 Agent 实例时调用（无 db 模式只在首次 chat 时建一次；有 db 模式每轮都重建——所以每轮拿到的花名册都是最新的）。
6. **函数的最终作用**：产出一份"身份明确、手下清清楚楚、纪律一条不少、记忆能力如实告知"的管家说明书。
7. **函数的使用场景**：butler.ts 默认装配；外部自定义拼接（导出可用了）。
8. **函数的缺陷/注意事项**：花名册越长说明书越长——每个工人的 description 都占上下文预算；子 Agent 数量很大时要考虑精简 description 或分级派活（当前规模无碍）。

## 模块3：文件内每一个参数超详细说明

### 参数 1：`subAgents`（当前花名册）

1. **名称 + 类型**：`subAgents`，`RosterEntry[]`（花名册条目数组）。
2. **参数设计原因**：**因为**说明书的核心可变部分就是"手下有谁"，**所以**它是第一个入参。
3. **参数类型选择原因**：**因为**人数可零可多，**所以**用数组；元素类型 RosterEntry（四件套最小集，见核心定义 1）。
4. **参数的传入来源**：butler.ts 的 `this.listAgents()`——由注册表现算（每次 buildAgent 都是最新的）。
5. **参数的内部使用逻辑**：两处——① `.map(...).join('\n')` 生成花名册行；② `.length > 0` 判断走真名单还是占位文案。
6. **参数的取值范围**：空数组（合法，出占位文案）或任意多行条目。
7. **参数的最终作用**：管家"认识手下"的全部依据。

### 参数 2：`hasMemory`（是否配了记忆工具）

1. **名称 + 类型**：`hasMemory`，布尔（boolean），默认 `false`。
2. **参数设计原因**：**因为**记忆工具是可选装配（ButlerOptions.memory 不传就没有），**而**"告知模型有记忆可用"这段话只有在工具真存在时才能说（说了没有的话，模型会调不存在的工具然后困惑），**所以**需要这个开关。
3. **参数类型选择原因**：**因为**它是纯二值条件，**所以**布尔最直接；默认 false 符合"记忆是可选能力"的现实。
4. **参数的传入来源**：butler.ts 的 `Boolean(this.memory)`——把"记忆实现存在与否"转成布尔（**为什么包一层 Boolean**：this.memory 是"实现对象或 undefined"，直接放进 if 能用但作为参数传入前显式转布尔更清晰、类型也更整齐）。
5. **参数的内部使用逻辑**：唯一使用点——三元表达式决定 memorySection 是整句还是空串。
6. **参数的取值范围**：true / false。
7. **参数的最终作用**：说明书里"记忆条款"的出现开关。

### 参数 3：返回的说明书本身（出参视角）

1. **名称 + 类型**：返回值，`string`。
2. **参数设计原因**：**因为** system prompt 的载体就是一段文本，**所以**返回字符串。
3. **参数类型选择原因**：Agent 构造参数 systemPrompt 就是 string。
4. **参数的传入来源**：模板 + 两个插值拼出。
5. **参数的内部使用逻辑**：被 new Agent({ systemPrompt }) 直接使用——模型每轮推理都"读"它。
6. **参数的取值范围**：恒定的模板骨架 + 可变的两段插值。
7. **参数的最终作用**：管家行为的总纲。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、花名册动态生成——为什么这是本文件最重要的设计

**因为**子 Agent 是持续增加的（工程路线图明确还会接真实工具/硬件/更多领域），**如果**说明书把"手下有厨师和清洁工"写死：每加一个工人就要改这个文件 → 重新编译 → 不同步就出现"工人已注册但管家不认识"的分裂；**而**动态生成后，注册表是唯一事实源，说明书永远自动对齐。**"新增子 Agent 无需改 prompt"**——文件头注释把它列为这个文件存在的核心理由。

### 2、六条工作纪律逐条讲为什么（一条都不能少）

1. **"人类永远不直接接触专职人员"**——见面隔离原则的模型层执行令（管家不得引导人类去找子 Agent）；
2. **"你只做调度、记忆与汇报，不亲自执行领域内具体事务"**——防管家瞎编：它没有领域工具，亲自答 = 编数据；
3. **"专职人员平级、不直接联系，多领域任务由你依次派发、汇总"**——平级转派架构（agent-sdk 结果信封的 suggestions 机制的对口接收方）；
4. **"返回 needs_human 时清楚转述给人类"**——协议 5 状态里 needs_human 的对口处理（子 Agent 说"要人类拍板"，管家必须把事说清而不是自己替人类决定）；
5. **"汇报简洁口语、不暴露内部工具名/任务 ID/信封字段；失败说明原因并给替代方案"**——体验守门：人类要听人话（这条与 printer: false、extractReplyText 的"只提纯文本"是三件套）；
6. **"不确定时向人类澄清，不要臆测"**——防幻觉的最后闸门。

**删任何一条的具体后果**：删 1/2 → 管家亲自答题或让人类去找工人（架构崩）；删 3 → 跨域协作断路；删 4 → 需人类决策的事被擅自执行；删 5 → 人类听到"task_8f2k 信封 unavailable"这类黑话；删 6 → 信息不足时模型开编。

### 3、`hasMemory ? '…' : ''` 与 `${memorySection}`——为什么记忆条款是"附加段"而不是写死在正文里

**因为**没有记忆工具的管家如果被要求"保存长期事实"，会去调不存在的工具（工具调用失败 → 模型困惑 → 可能编造"已保存"）；**而**空串插进模板不留痕迹——**条款与工具同生共死**，这正是"不做假成功"在提示词层的表达。

### 4、结尾的对话风格句——为什么要有这句"软要求"

**因为**前六条是"硬纪律"（什么不能做），但管家还有"质感"维度（先办结、再主动给下一步建议）——这是纯风格偏好，用一句软要求收尾，让管家的语气向"高效又体贴"对齐。**软硬分开**：硬的用编号条款，软的用描述句——模型对两种约束的执行力度天然有区分。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 程序启动，butler.ts import 本文件（函数与类型就位，无副作用）；
2. 每次 buildAgent 创建管家 Agent 时：listAgents() 现算花名册 → 调本函数 → 拼出当轮说明书；
3. 说明书随 new Agent 注入 → 管家模型的每一轮推理都以它为纲；
4. 有 db 模式下每轮重建 → 工人名单变化下一轮即刻生效；无 db 模式下缓存实例只建一次 → 名单以首次为准（**这是两种模式的一个行为差异**，改注册表时机时要注意）。

### 2、文件在整个工程中不可替代的作用

**它是管家行为的内容源头**：见面隔离、只调度不干活、平级转派、人话汇报——工程四大原则在"管家怎么说"层面的全部实现都在这 42 行里。

### 3、运行依赖的环境与前置条件

- 零依赖、零副作用；
- 前置条件：无——只要有花名册数据就能拼（空名单也是合法输入）。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **"固定纪律 + 动态花名册"模板模式**：任何"队长带队员"的多 Agent 场景通用（队员名单动态、纪律恒定）；
- **RosterEntry 最小四件套**：一切"给决策者看的成员简介"通用。

### ⚠️ 易错点

1. **自定义 systemPrompt（ButlerOptions.systemPrompt）时忘了拼花名册**：管家不认识手下 → 派不出活——自定义的是"整份说明书"不是"补充段"，慎用；
2. **在 description 里写内部黑话**（如"调用 subagent_chef 工具"）：会顺着纪律 5 的反面泄露给人类——description 写能力不写机制；
3. **改纪律文案时丢了编号顺序**：条款是按"对外隔离→自我定位→协作→汇报→兜底"排的，乱序会稀释模型对纪律层次的理解。

### 🔍 调试关键点

- **管家亲自回答领域问题**：查纪律第 2 条是否被改弱；
- **管家报出 task_id/工具名**：查纪律第 5 条 + 说明书是否被自定义替换；
- **加了子 Agent 管家却不知道**：无 db 模式下缓存实例的花名册是旧的（见模块5第 4 步的行为差异）——重启或改用 db 模式；
- **模型不主动用记忆工具**：查 hasMemory 是否传了 false 而工具实际挂了。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| 六条工作纪律 | 🚫 不能删改 | 工程原则的模型层落地（见模块4第 2 条逐条后果） |
| 花名册动态生成机制 | 🚫 不能改回写死 | "新增子 Agent 无需改 prompt"是设计承诺 |
| 记忆条款与 hasMemory 联动 | 🚫 不能解耦 | 条款必须与工具同生共死 |
| 空名单占位文案 | ✅ 可润色 | 保持"不是错误"的语义 |
| 对话风格句 | ✅ 可润色 | 纯风格软要求 |
| 纪律新增（如"连续失败 N 次后主动上报"） | ✅ 可扩展 | 注意总长度——说明书每字都占上下文 |
