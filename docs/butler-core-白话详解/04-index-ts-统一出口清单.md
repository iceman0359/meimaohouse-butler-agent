# 04 · index.ts 源码白话详解（白名单出口清单）

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`index.ts`
- 存放路径：`meimaohouse-butler-agent/packages/butler-core/src/index.ts`
- 编译产物：`packages/butler-core/dist/index.js`（package.json 的 `main`/`exports` 指向它——**本包入口**）

### 2、文件存在的核心原因

**因为**别的包（examples、apps、tests）要使用管家（`import { Butler } from '@meimaohouse/butler-core'`），包必须有一个正式入口；**而**本包与 agent-sdk 有一个关键区别——**它刻意不做全量转发，而是白名单点名出口**：`Butler` 主类、说明书函数、记忆组装器、三个策略常量——**该给的一个不少；不该给的（SUMMARY_SYSTEM_PROMPT、extractReplyText、appendMessage 等内部件）一个不给**。**为什么这么选**：管家核心的内部件大多是"调用纪律敏感"的（runExclusive、appendMessage 的非空断言、logEvent 的 payload 约定），暴露出去被乱用会破坏不变量；**所以**入口用"点名导出"把 API 面收得干干净净。

文件头注释：`大管家核心：Butler 主类 + 管家 prompt 模板 + 工作记忆组装（Hermes 纪律）`——一句话把包的三块内容说全。

**如果没有这个文件，程序会出现的问题：** 使用方 import 不到任何东西（包不成立）；或者被迫全量转发（内部敏感件裸奔，被外部乱调）。

### 3、文件的整体定位

这个文件**只负责"点名放行"**：14 行代码 = 1 段头注释 + 3 条具名导出语句。它是 agent-sdk 06 文档讲过的"桶文件"的**姊妹篇**——同样的入口职责，相反的出口策略（全量 vs 白名单），两相对照正好教会"出口策略该怎么选"。

### 4、文件的依赖关系

**它需要调用谁（上游）：** 本包三个功能文件——`butler.js`（Butler 主类）、`prompts.js`（说明书）、`memory.js`（记忆组装器）。

**谁来调用它（下游）：**

- `examples/butler-demo.ts`：`import { Butler } from '@meimaohouse/butler-core'`；
- `apps/butler-web/src/server.ts`：同上；
- `tests/core.test.ts`：同上。

**一句话：包的"安检门"——白名单上的才放行。**

## 模块2：文件内核心条目逐个超详细说明

> 本文件没有函数与运行逻辑，3 条导出语句按核心条目逐个拆解。

### 核心条目 0：文件头注释（包的自我介绍）

1. **名称**：1-4 行 JSDoc 注释：`@meimaohouse/butler-core 大管家核心：Butler 主类 + 管家 prompt 模板 + 工作记忆组装（Hermes 纪律）`。
2. **设计的根本原因**：**因为**包名（butler-core）太抽象，**所以**一句话点名三块内容——主类、说明书、记忆组装；"Hermes 纪律"四个字还预告了记忆方案的设计渊源。
3. **语法写法的原因**：JSDoc 注释——编译忽略、IDE 悬停显示。
4. **内部逻辑分步讲解**：纯文字。
5. **触发条件**：不运行。
6. **最终作用**：30 秒读懂本包。
7. **使用场景**：交接、审阅。
8. **缺陷/注意事项**：包内新增大模块时同步更新（与 agent-sdk 06 同款提醒）。

### 核心条目 1：`export { Butler, type ButlerOptions } from './butler.js'`（主类出口）

1. **名称**：第一条具名导出——只放行 `Butler` 类与它的选项类型 `ButlerOptions`。
2. **设计的根本原因**：**因为**使用方唯一需要的门面就是 Butler 类（new 它 + 调它的三个公开方法），**而**但管类内部还有一堆敏感件（runExclusive、appendMessage、logEvent、SUMMARY_SYSTEM_PROMPT……），**所以**用大括号点名：类和选项类型放行，其余全留在门内。
3. **语法写法的原因**：
   - **因为** TS 的 `export { A, type B } from '...'` 语法可以在转发的同时逐个点名，**所以**用它（对比 agent-sdk 的 `export *`——全量转发的语法根本拦不住敏感件）；
   - **因为** ButerOptions 是纯类型，**所以**加 `type` 前缀标记（type-only export——编译后消失，不占运行体积，且让打包器明确"这只是类型"）；
   - **因为**工程是 NodeNext 模块规范，**所以**路径写 `./butler.js`（编译产物名——语法强制，见 agent-sdk 06 文档模块4第 1 条）。
4. **内部逻辑分步讲解**：加载本文件 → 加载 butler.js → 把点名成员挂到包出口。
5. **触发条件**：任何 `import { Butler } from '@meimaohouse/butler-core'`。
6. **最终作用**：全工程拿到管家类的唯一正规通道。
7. **使用场景**：demo/tests/apps 三处 + 未来所有装配代码。
8. **缺陷/注意事项**：类名是 `Butler`（不是 Buter/管家）——import 时以本条放行的名字为准；类的方法（chat/delegate/listAgents/getBrief/register）通过实例访问，不在本条放行范围。

### 核心条目 2：`export { buildButlerSystemPrompt, type RosterEntry } from './prompts.js'`（说明书出口）

1. **名称**：第二条具名导出——放行说明书函数与花名册条目类型。
2. **设计的根本原因**：**因为**高级用法（自定义管家说明书、外部界面展示花名册）需要这两个符号，**而** prompts.ts 里也没有别的可暴露内容，**所以**全给了——**白名单不等于抠门，该给的全给**。
3. **语法写法的原因**：同条目 1（点名 + type 标记 + .js 后缀）。
4. **内部逻辑分步讲解**：转发两个符号。
5. **触发条件**：外部拼装说明书 / 展示花名册时 import。
6. **最终作用**：说明书能力对外开放。
7. **使用场景**：自定义装配、UI 展示。
8. **缺陷/注意事项**：RosterEntry 与 agent-sdk 的 SubAgentSpec 前四字段对应——外部别混用两个类型（形状兼容但语义有别）。

### 核心条目 3：`export { assembleMemory, loadBrief, WINDOW, COMPRESS_THRESHOLD, BRIEF_MAX_CHARS, type AssembledContext } from './memory.js'`（记忆出口——本文件最长的一条）

1. **名称**：第三条具名导出——放行记忆组装器两个函数、三个策略常量、一个结果类型，共 6 个符号。
2. **设计的根本原因**：**因为**记忆策略是"可调优的"——窗口/阈值/上限三个常量就是给应用方按自家模型档位调整的旋钮，两个函数供外部复用组装逻辑（比如独立的记忆服务），**所以**全部放行；**而** memory.ts 的 fmtMessage / butlerAgentId 两个内部助手不暴露（实现细节）。
3. **语法写法的原因**：具名点名 + type 标记 + .js 后缀——同前；**为什么常量也能 export**：TS/ESM 的导出对象包括值（函数/常量/类）与类型，三个常量是"值"，照常放行。
4. **内部逻辑分步讲解**：转发 6 个符号。
5. **触发条件**：外部调优记忆参数 / 复用组装逻辑。
6. **最终作用**：记忆策略"可调、可复用、可测"。
7. **使用场景**：应用按模型档位定制窗口大小；独立记忆服务复用组装器。
8. **缺陷/注意事项**：**导出了 assembleMemory 不代表可以绕开 Butler 用它**——它要求传入合法的 summarize 回调（模型压缩员），单用要自己备齐模型件。

## 模块3：文件内每一个参数超详细说明

> 本文件没有运行时参数（纯转发文件，机理见 agent-sdk 06 文档模块3）。它放行的**符号清单**即"参数面"，归纳如下：

1. **放行的运行时值**（5 个）：`Butler`（类）、`buildButlerSystemPrompt`（函数）、`assembleMemory`（函数）、`loadBrief`（函数）、`WINDOW / COMPRESS_THRESHOLD / BRIEF_MAX_CHARS`（3 个常量，共 4 个值成员）。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、白名单点名 vs 全量转发（export *）——本文件最重要的设计对比

**因为**两个包的"内部件敏感度"不同：agent-sdk 的五个文件都是"标准件"（校验器/工具/接口/工厂——全部适合公开），**所以** `export *` 全量转发最省心；**而**但管核心的内部件（串行队列、账房私有方法、SDK 兼容层）是"运转细节"，被外部调用会破坏不变量（并发约定、db 非空前提），**所以**必须点名放行。**没有谁对谁错——出口策略跟着"内部件的公开 readiness"走**。**如果**本文件改成 `export *`：敏感件裸奔，被误用的那一刻问题会在远离根源的地方爆发（最典型的就是绕过 runExclusive 直接并发调模型）。

### 2、为什么连三个常量都要单独点名（而不是 export * 后再藏内部件）

**因为** `export *` 没有"排除名单"的常规写法（要靠改内部文件的 export 标记），**而**本文件的诉求恰恰是"源文件内部自由、出口精确"——**所以**宁可出口语句写长一点（第三条 6 个符号逐个点名），也要保持"源文件不为一层出口改自己"。**点名语句的长度就是白名单策略的成本**——14 行换来的 API 面控制，值得。

### 3、`type` 前缀——为什么三个类型都显式标记

**因为** type-only 导出让编译器/打包器明确"这只是类型"（编译后彻底消失）：一方面运行产物更干净，另一方面杜绝"把类型当值 import"的运行期错误（import 一个只存在于类型世界的名字会直接报错——错误在编译期暴露）。**语法强制角度**：工程 `tsconfig` 虽未强制 isolatedModules 下的 type 标记，但这是严格工程的标准姿势。

### 4、三条导出的顺序——为什么是 butler → prompts → memory

**因为**入口文件的阅读体验 = 包的"目录页"：主类（最重要）→ 说明书 → 记忆——与 00 总览的文件地图顺序一致，也与包名描述（"Butler 主类 + prompt 模板 + 工作记忆组装"）逐词对应。纯可读性安排，无功能差异。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 使用方 `import { Butler } from '@meimaohouse/butler-core'` → Node 定位到 dist/index.js；
2. 逐条执行导出语句 → butler.js / prompts.js / memory.js 的编译产物被加载（各自顶层定义生效——注意 butler.js 顶层无副作用，memory.js 顶层只有常量）；
3. 使用方拿到白名单符号 → `new Butler({...})` 开工。
4. **整个加载零副作用、零模型解析**——懒加载链条从入口就开始保持。

### 2、文件在整个工程中不可替代的作用

**它是管家核心的"安检门 + 目录页"**：保证外部只见该见的（门面 + 可调策略），不见不该见的（运转细节）——包的公开 API 契约由它单点定义。

### 3、运行依赖的环境与前置条件

- 依赖本包三个功能文件编译就位（dist 完整）；
- 前置条件：Node 支持 ESM（工程 `"type": "module"`）；
- 自身零第三方依赖。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **"白名单点名出口"模式**：一切"内部件敏感"的包的标准出口（与 export * 的适用边界一起记：标准件全量、敏感件点名）；
- **type 前缀导出**：类型与值分开放行的规范写法。

### ⚠️ 易错点

1. **改了内部文件签名忘了这条没编译**：使用方报"X 不是函数/未导出"——先查本文件点名清单；
2. **往白名单里随手加内部件**：比如把 appendMessage 放出来——破坏调用前提（db 非空断言）的事故就来了；
3. **import 了不存在的符号**：本文件是白名单——**SUMMARY_SYSTEM_PROMPT 等 import 不到是设计不是 bug**。

### 🔍 调试关键点

- **"找不到模块 '@meimaohouse/butler-core'"**：包没构建（dist 缺失）——包目录 `npm run build`；
- **"X is not exported by ..."**：符号没进白名单或名字拼错；
- **新增导出后别的包还报旧错**：重新编译本包 + 使用方清缓存重启。

### 🚫 修改红线（不能改）与可优化点

| 位置 | 能不能动 | 说明 |
|---|---|---|
| 白名单的"不放行"清单 | 🚫 不能随意加名 | 内部件各有调用前提（见各源文件文档模块6） |
| `.js` 后缀 / type 标记 | 🚫 不能改 | NodeNext 语法强制 + 工程规范 |
| 三条导出的成员覆盖 | ✅ 可扩展 | 新公开能力先过"是否自带调用前提"审查再点名 |
| 改成 export * 全量转发 | ✅ 技术可行但强烈不建议 | 会裸奔全部内部件（见模块4第 1 条） |
| 文件头注释 | ✅ 可更新 | 包内容演进时同步 |
