# 02 · memory.ts 源码白话详解（工作记忆组装器）

---

## 模块1：文件整体基础介绍

### 1、文件名称 + 文件存放路径

- 文件名：`memory.ts`
- 存放路径：`meimaohouse-butler-agent/packages/butler-core/src/memory.ts`
- 编译产物：`packages/butler-core/dist/memory.js`

### 2、文件存在的核心原因

**因为** AI 模型的对话记忆有两个天然死穴：① 全都记着 → 上下文越撑越大，迟早爆掉（而且越长的上下文模型越贵、越迟钝）；② 什么都不记 → 程序一重启就"失忆"，昨天的约定今天全忘。**而**管家恰恰是需要长期记性的角色（主人上周说"下周三来客人"）。**所以**必须有一套"既记得住、又撑不爆"的记忆方案——本文件实现的就是工程文档里说的 **Hermes 纪律：上下文恒定有界**：

- **长期纪要（brief）**：历史攒多了就让模型把"该记的"压缩成 ≤600 字摘要（未决事项/偏好/承诺），存数据库；
- **滑动窗口（window）**：每轮只现读最近 20 条消息，进程内**不攒任何历史**；
- **水位（watermark）**：记住"压缩到哪条了"，下次从刻度线之后接着压——纪要和水位都在库里，**重启零失忆**。

文件头注释把这套结构写得很直白：每轮动态组装 = system prompt + 【长期纪要】+ 【近期对话】。

**如果没有这个文件，程序会出现的问题：** 管家要么聊 50 轮就撑爆上下文报错，要么重启后把主人的约定忘得一干二净——"庄园管家"变成"金鱼管家"。

### 3、文件的整体定位

这个文件**专门负责"管家每一轮该带着什么记忆上场"的组装**：3 个常量（窗口/阈值/上限）+ 1 个结果类型 + 2 个导出函数（loadBrief 读纪要、assembleMemory 组装）+ 2 个内部助手（fmtMessage 格式化、butlerAgentId 查管家 ID）。它是"记忆策略"的全部实现——策略调优就调这三个常量。

### 4、文件的依赖关系

**它需要调用谁（上游）：**

- `@meimaohouse/db`：`Db` 类型 + `MemoryRepository`（读写纪要与水位）+ `MessageRepository`（读消息、查最新编号）；
- 还需要调用方传进来一个 `summarize` 函数（用管家模型做压缩——**为什么不由本文件自己建模型**：保持本文件"纯记忆策略"、模型细节留给 butler.ts，职责分离）。

**谁来调用它（下游）：**

- `butler.ts`：chat() 每轮调 `assembleMemory`；getBrief() 调 `loadBrief`；
- `index.ts`：把两个函数 + 3 个常量 + 结果类型导出（外部调优/展示用）。

**一句话：管家的"记忆策略中枢"——每一轮"想起什么、想起多少"由它说了算。**

## 模块2：文件内核心定义与核心函数超详细说明

### 核心定义 1：三个常量 `WINDOW / COMPRESS_THRESHOLD / BRIEF_MAX_CHARS`（记忆策略的三个旋钮）

1. **名称**：`WINDOW = 20`（窗口条数）、`COMPRESS_THRESHOLD = 30`（压缩触发阈值）、`BRIEF_MAX_CHARS = 600`（纪要字数上限）。
2. **设计的根本原因**：**因为**"带多少记忆上场"不能拍脑袋写死在流程深处——它是需要按模型上下文大小、成本、效果反复调的**策略参数**，**所以**抽成具名常量放在文件最顶上，调优只动这三个数；**且导出**（index.ts 也导出了它们），外部应用可以按自己的模型档位定制。
3. **语法写法的原因**：**因为** TypeScript 的 `export const` 声明不可变常量（改了编译期报错），**所以**用 const 而不是 let——策略参数不该被运行中意外篡改。
4. **内部逻辑分步讲解**（三个数的配合关系）：
   - 窗口 20 条：每轮带的"近期对话"体量——够覆盖最近话题，又恒定有界；
   - 阈值 30 条：未压缩消息攒到 30 条才触发一次压缩——**为什么比窗口大**：攒一批再压比每条都压省模型调用（压缩本身要花一次模型推理的钱）；30 条攒起来约压成一两百字的增量，不心疼；
   - 上限 600 字：纪要的体量红线（注释说明约 500 汉字）——保证"长期记忆"这一段永远只占上下文的小头。
5. **触发条件**：不运行；assembleMemory 内部读取它们做判断。
6. **最终作用**：让"记忆带多少、什么时候压、压到多短"三个决策全部可调、有据可查。
7. **使用场景**：assembleMemory 内部；外部应用按需 import 调优。
8. **缺陷/注意事项**：三个数是联动关系（窗口 < 阈值，否则窗口里的内容永远处于"该压未压"的挤压状态）——调一个要想着另两个。

### 核心定义 2：`AssembledContext`（组装结果的三件套）

1. **名称**：`AssembledContext`，接口，3 个字段：`historyText`、`window`、`compressed`。
2. **设计的根本原因**：**因为**组装函数干的事其实有三样：拼历史文本、读出窗口消息、报告"这轮有没有顺手做压缩"——调用方（butler.ts）三样都用得上（historyText 拼进请求、compressed 用来打日志、window 可供调试/展示），**所以**打包成一个结果对象一次交齐。
3. **语法写法的原因**：接口三字段——historyText 是 string（拼好的文本）；window 是 `MessageRow[]`（数据库消息行的类型，从 db 包引入）；compressed 是 boolean。
4. **内部逻辑分步讲解**：historyText = "纪要段 + 窗口段"拼好的成品文本；window = 本轮实际用的最近 20 条（**不含本轮**——本轮消息此刻还没写入）；compressed = 本轮是否触发了压缩。
5. **触发条件**：不运行；assembleMemory 的返回类型。
6. **最终作用**：一次调用、三样产出，调用方不用二次查询。
7. **使用场景**：butler.ts 的 chat()。
8. **缺陷/注意事项**：window 里是"本轮之外"的近期消息——不要误把它当"含本轮"的完整对话（本轮是 chat 里 beginTurn 之后再单独拼的）。

### 核心函数 1：`fmtMessage(m)`（消息格式化助手，文件内部私有）

1. **函数名称**：`fmtMessage`，入参 `m: MessageRow`（一条消息行），返回 `string`。
2. **函数设计的根本原因**：**因为**数据库里的消息是"生数据"（发送方是英文代号、内容可能超长、可能有换行空格乱排），直接塞给模型既费字数又难读，**所以**统一"翻译 + 修剪"：代号转人话、超长截断、空白压扁。三处调用（压缩片段、窗口组装）共用一份格式——**格式只有一种，模型读到的记忆口径才稳定**。
3. **函数语法写法的原因**：**因为**它只被本文件使用，**所以**不 export（模块私有，收窄可见面）。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：翻译发送方——`m.sender_kind === 'human' ? '主人' : m.sender_kind === 'butler' ? '管家' : m.sender_kind`：人和管家翻译成中文称呼（模型读了直接能用）；其他种类（sub/system）原样输出（**为什么不全翻**：子 Agent 代号本来就是有意义的标识，保留原样信息量更大）；
   - 第 2 步：截断——`m.content.length > 200 ? m.content.slice(0, 200) + '…' : m.content`：超过 200 字截断加省略号（**为什么 200**：单条消息在记忆里的价值递减很快，前 200 字通常已含要点；省略号明示"此处有删节"，模型不会误以为话就说到一半；
   - 第 3 步：压空白 + 拼格式——`.replace(/\s+/g, ' ')` 把换行/连续空格压成单个空格，再套上 `[谁] 内容` 的统一格式。
5. **函数的触发条件**：assembleMemory 组装压缩片段和窗口文本时，每条消息调一次。
6. **函数的最终作用**：数据库生数据 → 模型爱读的规整文本。
7. **函数的使用场景**：仅本文件内部（两个调用点）。
8. **函数的缺陷/注意事项**：截断可能切掉关键信息（比如长消息末尾才说的事）——这是"有界记忆"的代价，用 200 这个相对宽松的阈值做了平衡。

### 核心函数 2：`loadBrief(db, userId)`（读当前纪要与水位）

1. **函数名称**：`loadBrief`，入参 `db: Db` 和 `userId: number`，返回 `{ brief: string; watermark: number }`。
2. **函数设计的根本原因**：**因为**组装和展示（butler.ts 的 getBrief）都需要"先读当前纪要和水位"这个动作，**而**读法有一套固定细节（命名空间是 'brief'、水位要转数字、没有就给空串/0），**所以**封装成独立函数——两处共用，读法只写一遍。
3. **函数语法写法的原因**：**因为**纪要的存取用的是 agent-sdk Memory 的键值约定（agent_memories 表、ns='brief'），**所以**读取时带 scope `{ agentId, userId, ns: 'brief' }`（**为什么带 userId**：不同主人的记忆必须分开——A 主人的待办绝不能出现在 B 主人的纪要里）；**因为**水位存的是字符串（Memory 值只收 string，见 agent-sdk 03 文档），**所以**读出来要 `Number(wm)` 转回数字；**因为**"没有纪要"是正常初态，**所以** `?? ''` 兜底空串、水位没有就 0（0 = "从头开始都是未压缩"）。
4. **函数内部完整逻辑分步讲解**：
   - 第 1 步：`new MemoryRepository(db)` 建仓储；
   - 第 2 步：读 `brief` 键 → 空值兜底空串；
   - 第 3 步：读 `watermark` 键 → 有就转数字，没有就 0；
   - 第 4 步：打包返回。
5. **函数的触发条件**：assembleMemory 开头；butler.ts 的 getBrief()（给界面/调试展示纪要）。
6. **函数的最终作用**：提供"当前记忆进度条"——记了什么（brief）、压到哪了（watermark）。
7. **函数的使用场景**：assembleMemory、getBrief。
8. **函数的缺陷/注意事项**：它不做任何写操作——纯读；水位数字类型转换假设存的一定是数字字符串（写入侧由 assembleMemory 保证）。

### 核心函数 3：`butlerAgentId(db)`（查管家在数据库里的 ID，文件内部私有）

1. **函数名称**：`butlerAgentId`，入参 `db: Db`，返回 `number`。
2. **函数设计的根本原因：****因为**记忆是挂在"管家这个身份"名下的（agent_memories 表按 agent_id 归属），**所以**每次读写记忆都要知道管家的数据库 ID；**而**"查 ID"在 loadBrief 和 assembleMemory 两处都要用，**所以**收敛成一个函数。
3. **函数语法写法的原因**：**因为**这里只需要一次极轻量的主键查询，**所以**直接用 `db.prepare("SELECT agent_id FROM agents WHERE agent_key = 'butler'").get()` 裸 SQL（**为什么不走 AgentContext 完整流程**：butler.ts 里已经走过了完整装配，这里是纯读取，轻量直查最合适）；**因为**查不到说明装配顺序错了，**所以**抛带人话指引的错误（"请先 ensureButlerAgent(db)"）。
4. **函数内部完整逻辑分步讲解**：执行查询 → 没有就 throw → 有就返回 agent_id。
5. **函数的触发条件**：loadBrief / assembleMemory 里构造记忆 scope 时。
6. **函数的最终作用**：记忆数据的"归属人 ID"。
7. **函数的使用场景**：仅本文件内部。
8. **函数的缺陷/注意事项**：每次调用都查一次库（不缓存）——频率低、查询轻，可接受；若未来高频调用可加缓存（可优化点）。

### 核心函数 4：`assembleMemory(db, userId, summarize)`（组装主函数——本文件的灵魂）

1. **函数名称**：`assembleMemory`，入参 `db: Db`、`userId: number`、`summarize: (prompt: string) => Promise<string>`（模型压缩回调），返回 `Promise<AssembledContext>`（异步——因为压缩可能触发模型调用）。
2. **函数设计的根本原因**：**因为**"每一轮带什么记忆上场"是一条完整流水线：查水位 → 判断要不要压 → （要压就）生成压缩指令 → 调模型压 → 存新纪要推水位 → 读窗口 → 拼文本——**而**这条流水线必须每轮 chat 前跑一遍，**所以**封装成单一入口。**封装的深层原因**：把"记忆策略"集中在一处，策略调优/排障只看这个函数。
3. **函数语法写法的原因**：
   - **因为**内部可能 await 模型压缩（网络等待），**所以**必须是 async、返回 Promise（语法硬要求）；
   - **因为**本文件不该依赖具体模型，**所以**压缩能力以函数参数注入（`summarize` 回调）——**依赖倒置**：策略层只要求"给 prompt 还我摘要文本"，谁家的模型随便换；
   - **因为**压缩失败不该连累本轮对话，**所以**内部有自己的 try/catch（见模块4第 5 条）。
4. **函数内部完整逻辑分步讲解**（两大步）：
   - **第 ① 大步：压缩检查**（在读取窗口之前做——**顺序讲究**：先把该压的压掉，窗口和纪要才是最新的）：
     - 取纪要和水位（loadBrief）→ 查最新消息编号 `latest = msg.latestIdByUser(userId)`；
     - `pending = latest - watermark`（未压缩消息条数）→ `pending >= 30 && latest > 0` 才触发（**两个条件的意义**：攒够一批才压；库里有消息才压——新用户首轮 pending=latest>0 但通常 < 30 不会压）；
     - 触发则：取水位之后最多 200 条消息（`{ afterId: watermark, limit: 200, order: 'asc' }`——**asc 正序**：按对话时间顺序给模型看才读得懂）→ 逐条 fmtMessage → 拼成 segment；
     - 组装压缩指令 prompt：先交代身份与任务（"你是庄园管家的记忆管理员…"）→ **三类保留**（未决事项/稳定偏好与长期约定/重要承诺与背景事实）→ **硬性清除规则**（已办结/取消/拒绝的删除；带日期且已过期无跟进的删除；无关寒暄细节删除）→ 有旧纪要则附上（"在此基础上修订"）→ 附待压缩记录；
     - `(await summarize(prompt)).trim()` 拿回新纪要 → **容错验收**：`if (next && next.length <= BRIEF_MAX_CHARS * 3)`——空结果不收；超长（超 1800 字）也不收（防模型失控输出污染记忆）；验收通过则截断到 1800 字内、写库（brief + watermark = String(latest)）、`compressed = true`；
     - **整个压缩包在 try/catch 里，catch 是空的**——压崩了就当没发生（见模块4第 5 条）；
   - **第 ② 大步：组装上下文**：
     - `msg.listByUser(userId, { limit: 20, order: 'desc' }).reverse()`——**先倒序取最近 20 条、再反转成时间正序**（**为什么这么绕**：数据库"取最近 N 条"天然按新→旧取，而对话要按旧→新给模型读——先拿够数再拨正顺序）；
     - parts 数组：有纪要推"【长期纪要…】+ 纪要"；有窗口推"【近期对话（最近 N 条）】+ 格式化消息"；
     - `historyText = parts.join('\n\n')`（两段之间空一行，段落清晰）→ 返回三件套。
5. **函数的触发条件**：butler.ts 的 chat() 每一轮开头（在登记本轮 human 消息**之前**——顺序红线见 03 文档模块4第 1 条）。
6. **函数的最终作用**：产出本轮的完整工作记忆（文本形式），并顺手把"该压的"压掉——**上下文恒定有界 + 重启零失忆**两大目标在这一函数里同时达成。
7. **函数的使用场景**：butler.ts chat()；测试可直接调它验证压缩逻辑。
8. **函数的缺陷/注意事项**：压缩是**同步做在本轮请求路径上的**（用户会多等一次模型调用）——换来的是水位始终准确、逻辑简单；`limit: 200` 是单次压缩的段长上限（水位长期不推进时可能压不全，下轮接着压——水位机制天然支持分批）。

## 模块3：文件内每一个参数超详细说明

### 参数 1：`db`（三个导出函数共用的数据库连接）

1. **名称 + 类型**：`db`，`Db`（db 包的连接类型）。
2. **参数设计原因**：**因为**纪要、水位、消息、消息编号全在数据库里，**所以**所有函数都要拿连接。
3. **参数类型选择原因**：db 包的 Db 接口（prepare 等能力）——**只认接口不认具体实现**，测试可换假库。
4. **参数的传入来源**：butler.ts 的 this.db（ButlerOptions.db 注入）。
5. **参数的内部使用逻辑**：建仓储（MemoryRepository/MessageRepository）、裸 SQL 查管家 ID。
6. **参数的取值范围**：已建立且完成装配（agents 表有 butler 行）的连接——没装配会在 butlerAgentId 处抛人话错误。
7. **参数的最终作用**：记忆数据的读写通道。

### 参数 2：`userId`（记忆归属的主人 ID）

1. **名称 + 类型**：`userId`，数字（number）。
2. **参数设计原因**：**因为**不同主人的记忆必须完全隔离（A 的口味不能进 B 的纪要），**所以**所有读写都按 userId 圈定范围。
3. **参数类型选择原因**：**因为**数据库里用户表主键是数字自增 ID，**所以**用 number（不是 username 字符串——字符串要先 resolveUser 换成数字，这件事 butler.ts 已经做了）。
4. **参数的传入来源**：butler.ts 解析（`this.getButlerAgent().resolveUser(this.ownerUsername)`）。
5. **参数的内部使用逻辑**：进 scope（纪要归属）、查最新消息编号、读窗口消息——三处圈定。
6. **参数的取值范围**：数据库中存在的用户 ID；不存在的 ID 会得到空窗口/空纪要（不报错——新用户初态）。
7. **参数的最终作用**：记忆世界的"户主标识"。

### 参数 3：`summarize`（模型压缩回调）

1. **名称 + 类型**：`summarize`，函数类型 `(prompt: string) => Promise<string>`。
2. **参数设计原因**：**因为**压缩要靠模型（本文件没有也不该有模型），**所以**以回调注入——**谁用谁传**：butler.ts 传"用管家模型裸调用一次"的封装（见 03 文档 summarize）。
3. **参数类型选择原因**：**因为**模型调用是异步的（网络等待），**所以**签名必须是"收字符串、还 Promise 字符串"——异步契约写进类型，实现想偷懒同步都不行。
4. **参数的传入来源**：butler.ts 的 `(prompt) => this.summarize(prompt)`。
5. **参数的内部使用逻辑**：唯一调用点——压缩触发时 `await summarize(prompt)` 拿新纪要。
6. **参数的取值范围**：任何符合签名的函数（测试可以传假实现——返回固定文本，全链路不花模型钱）。
7. **参数的最终作用**：记忆策略与模型能力的"焊接点"，且保持了策略层可独立测试。

### 参数 4：`m`（fmtMessage 的入参——一条消息行）

1. **名称 + 类型**：`m`，`MessageRow`（db 包的消息行类型：sender_kind/content 等）。
2. **参数设计原因**：格式化的对象单位是"一条消息"。
3. **参数类型选择原因**：直接用 db 包的行类型——格式化器不需要更多。
4. **参数的传入来源**：压缩片段 / 窗口读取的消息数组。
5. **参数的内部使用逻辑**：读 sender_kind（翻译称呼）和 content（截断压扁）。
6. **参数的取值范围**：数据库合法消息行。
7. **参数的最终作用**：单条消息的"美颜"。

### 参数 5：`prompt`（summarize 的入参——压缩指令）

1. **名称 + 类型**：`prompt`，字符串。
2. **参数设计原因**：模型压缩的"工作说明书 + 原材料"都在这一段文本里。
3. **参数类型选择原因**：模型的输入就是文本。
4. **参数的传入来源**：assembleMemory 内部组装（规则 + 旧纪要 + 待压记录）。
5. **参数的内部使用逻辑**：经回调传给模型 → 模型返回纪要文本。
6. **参数的取值范围**：任意（由组装逻辑保证结构完整）。
7. **参数的最终作用**：压缩质量的直接决定因素。

## 模块4：文件关键逻辑 & 特殊代码说明

### 1、三个常量的配比（20 / 30 / 600）——为什么是这个组合

**因为**记忆方案的三个体量要互相咬合：窗口 20 条是"每轮必带"的固定开销；阈值 30 条 > 窗口，保证触发压缩时"未压缩的"至少能覆盖一整个窗口有余——压完之后未压缩的回落到 10 条左右，不至于频繁触发；600 字上限保证纪要段永远是小头（真正的体量大头是窗口，而窗口恒为 20 条）。**组合起来：上下文总量 ≈ 常数**——这就是"上下文恒定有界"的字面实现。

### 2、压缩指令里的"三类保留 + 硬性清除规则"——为什么写这么细

**因为**"把对话压缩成摘要"如果只说"压缩一下"，模型会保留大量寒暄和细节（它不知道什么重要），纪要越压越肥，几轮就失去意义；**而**把"什么必须留（三类）""什么必须扔（已办结/过期/闲聊）"写成硬规则，模型才知道**取舍标准**——"解决即弃、过期待办过期自灭"（文件头注释原话）正是"记忆不腐烂"的关键。**这是本文件含金量最高的一段文案**，改前必读红线。

### 3、`next.length <= BRIEF_MAX_CHARS * 3` 的容错验收——为什么超长不直接扔而是"收下截断"

**因为**模型偶尔会超长输出（不受控）；**如果**直接扔掉这次压缩：水位不推进，下轮同样的 30+ 条再压一次（浪费一次模型调用，还可能再次超长）；**而**收下并截到 1800 字：记忆更新成功、水位推进、下轮正常——代价是纪要暂时偏肥（仍被 3 倍上限兜住，不会失控）。**"带闸门的宽容"**比"完美主义的一票否决"更稳。

### 4、空 catch（压缩失败静默跳过）——为什么不是 bug 而是设计

**因为**压缩是"锦上添花的维护动作"——本轮对话用的是"旧纪要 + 窗口"，本来就能正常工作；**如果**压缩失败让本轮报错：一次模型抖动就把用户对话打断，记忆维护反而成了可用性杀手；**而**静默跳过（注释原话："压缩失败：本轮照常用旧纪要，下轮重试"）——水位没动，下轮 pending 仍超阈值，自动重试。**注释里明确写了这个意图**，读代码的人不会误以为是忘了处理。

### 5、窗口读取的"desc 取 + reverse"——为什么不能直接 asc 取前 20 条

**因为**"最近的 20 条"必须从最新往回数才知道是哪 20 条——asc（旧→新）取前 20 条拿到的是**最早**的 20 条（完全错）；**所以**先 desc 取够 20 条（新→旧），再 reverse 拨回旧→新——**两步缺一不可**，这是分页查询的常用技巧。

### 6、`historyText` 里两段用 `\n\n` 连接且各有【标题】——为什么要加标题

**因为**给模型的记忆文本若不加标注，模型分不清"这段是旧事的浓缩还是最近的原话"；**而**【长期纪要（之前对话的浓缩…）】【近期对话（最近 N 条）】两个标题让模型对每段信息的**可信度与时效**有正确预期（纪要是浓缩转述、窗口是原话）——标题是"记忆的元信息"，成本两字、收益明确。

## 模块5：文件整体运行总结

### 1、从加载到运行完成的完整步骤流程

1. 程序启动，butler.ts import 本文件（常量与函数就位）；
2. 每轮 chat() 开头：assembleMemory 被调 →

4. 程序重启：纪要与水位都在库里、窗口现读 → 下一轮照常"记得一切"（零失忆）。

## 模块6：可复用模块 / 易错点 / 调试关键点 / 修改注意事项（⚠️ 高亮）

### ✅ 可复用模块

- **"纪要 + 窗口 + 水位"三件套记忆方案**：任何"长对话 + 有界上下文"的 Agent 都能整套搬走（换张表结构即可）；
- **"压缩回调注入"模式**：策略层与模型层解耦，测试可以传假 summarize 零成本跑全链路；
- **fmtMessage 的"翻译 + 截断 + 压空白"**：一切"数据库文本 → 模型输入"的格式化场景通用。

### ⚠️ 易错点

1. **调窗口忘了看阈值**：WINDOW 调大到 30 以上而阈值不动，会出现"刚压完又立即触发"的抖动；
2. **把 window 当"含本轮"的完整对话**：组装发生在本轮消息入库之前——window 永远不含本轮（本轮是调用方拼的）；
3. **给 summarize 传会带工具的 Agent**：压缩要的是纯文本一次调用，带工具的模型可能去查库存而不是压缩——butler.ts 的 summarize 专门用裸 Agent（无工具）；
4. **手动改库里的 watermark**：改小 = 大量重压（浪费），改大 = 一段历史永远进不了纪要（失忆）——它是水位刻度，不是随便的数字。

### 🔍 调试关键点

- **管家忘了之前的约定**：先 getBrief() 看纪要里有没有——没有则查水位与消息数（是否根本没触发过压缩：pending < 30）；
- **压缩从不触发**：查 pending 计算（latest - watermark）与阈值；查 summarize 是否抛错被静默吞了（catch 是空的——可在 catch 里临时加日志）；
- **纪要疯长**：查压缩指令的清除规则是否被改弱 + 模型是否总超长（1800 截断在兜底）；
- **上下文里本轮消息出现两遍**：这不是本文件的锅——chat 里登记顺序被改动了（见 03 文档模块4第 1 条）。
