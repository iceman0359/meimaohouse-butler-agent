# butler-core-白话详解 · 总览与阅读指南（大管家核心包）

> 本文件夹是 `packages/butler-core/src` 目录下全部 4 个源文件的零基础白话详解。
> 与《agent-sdk-白话详解》《agents-白话详解》配套：那边讲了"零件箱"和"两名工人"，这边讲"总管全局的大管家本人"。

---

## 一、先搞懂这个包在工程里扮演什么角色

**因为**整个工程是"人类只见管家"的架构——人类所有话都说给管家，管家决定派活、收结果、做汇报——**所以**必须有一个"管家的大脑与办公室"。`packages/butler-core`（包名 `@meimaohouse/butler-core`）就是这个角色：

```
人类 👤 ──说话──▶ 大管家（本包 Butler 主类）──派活──▶ 厨师/清洁工（agents 包）
                     │
                     ├── 自己的岗位说明书（prompts.ts）
                     ├── 自己的记性（memory.ts：纪要 + 滑动窗口）
                     ├── 名下的工人登记表（subAgents 注册表）
                     └── 自己的账本（可选：db 落库——会话/消息/任务/事件）
```

**它对外只承诺三件事**（文件头注释原话）：

1. `chat(message)`：人类对话入口——管家模型自己决策"这活派给谁"，干完转述（人类拿到的永远是一句人话）；
2. `delegate(task)`：程序化直派——跳过模型决策，按领域直接派任务给某个子 Agent（给测试/定时任务/外部编排用）；
3. `listAgents()`：当前花名册——手下有哪些工人、各自管什么。

## 二、开始前必须懂的核心设计：三条"管家纪律"

### 1、见面隔离（人类与子 Agent 永不见面）

**因为**让人类直接面对多个 AI 工人会失控（该找谁？结果怎么拼？），**所以**管家是唯一入口：一切需求由管家接收、一切结果由管家转述。这条纪律写在 prompts.ts 的工作纪律第 1 条，靠 tools.ts（agent-sdk）的 Agent-as-Tool 机制在技术上落实。

### 2、管家不干活（只调度/记忆/汇报）

**因为**管家如果亲自回答"冰箱里有什么"，它就是在没有真实数据的情况下瞎编（它自己没有工具去查冰箱）；**所以**纪律第 2 条规定管家只做三件事：派活、记事、转述——领域事务全部交专职人员。

### 3、上下文恒定有界（Hermes 纪律：重启零失忆）

**因为** AI 模型的"对话记忆"要么撑爆上下文（全存），要么重启全丢（全弃），**所以** memory.ts 实现了一套双轨记忆：

- **长期纪要**：历史攒多了（超 30 条）就由模型压缩成 ≤600 字的"纪要"，只留未决事项/偏好/承诺；
- **滑动窗口**：每轮只从数据库现读最近 20 条消息，进程内不攒历史；
- **水位（watermark）**：记录"压缩到哪条了"，重启后纪要和水位都在库里 → **零失忆**。

**这是本包最有含金量的设计**，02 文档会把它拆透。

## 四、上下游关系（谁依赖谁、谁在用它们）

```
本包依赖（上游）：
  @meimaohouse/agent-sdk（getModel/createTaskId/TaskRequestSchema/createMemoryTools + 六个类型）
  @meimaohouse/db（AgentContext/四个仓储/Db 类型——可选持久化）
  @strands-agents/sdk（Agent 底座）

谁在用它们（下游）：
  examples/butler-demo.ts   —— CLI 演示：new Butler({ subAgents: [chef, cleaner] })
  apps/butler-web/src/server.ts —— Web 服务端：new Butler({ db, memory, ... }) 全功能装配
  tests/core.test.ts        —— 核心测试：注入假子 Agent 测 chat/delegate
```

**注意 db 的"可选"设计**：`new Butler({...})` 不传 `db` 就是纯内存模式（零数据库依赖也能跑，多轮对话靠进程内上下文）；传了 `db` 就开启"每轮从库组装记忆 + 全链路落库"（重启零失忆）。**同一个类，两种运行形态**——03 文档的 invokeModel 双路径就是这条分界线。

## 五、开始前必须懂的大白话概念（本包新增的部分）

其余概念见前两套总览的词典，这里补管家专属的：

1. **花名册（roster）**：管家手下工人的名单（id/名字/领域/能力描述）——由注册表现算，写进管家提示词，管家模型靠它决定"这活派给谁"。
2. **工作记忆**：管家每轮"带着上场的记忆"，= 长期纪要 + 最近 20 条消息，动态拼出来，用完即弃。
3. **纪要（brief）**：历史对话的浓缩摘要（≤600 字），只留未决事项/偏好/承诺——是"重启不失忆"的载体。
4. **水位（watermark）**：已压缩到哪条消息的编号（刻度线）——下次压缩从这之后接着压，不重复不遗漏。
5. **落库/持久化**：把对话、任务、事件写进 SQLite 数据库——程序重启后数据还在。
6. **串行队列**：管家一次只能"处理一个请求"（底层模型不允许并发调用）——后来的请求排队，前面的做完才开始。
7. **事件流水（event log）**：管家工作的"行车记录仪"——回复了、出错了、任务完成了，都记一条事件，供排查与统计。

## 六、全局修改红线与易错点（改这个包前必看）

> ⚠️ **高亮警告区**：各文件细项在各自文档的模块6，这里提炼全局红线。

1. **`chat()` 里"先组装记忆、再登记本轮消息"的顺序不能颠倒**：颠倒后滑动窗口会把本轮消息也算进"历史"，导致本轮消息在上下文里出现两遍（一遍在窗口、一遍在"主人本轮消息"），模型行为混乱。
2. **`invokeModel` 的双路径不能合并**：无 db 时**必须复用缓存实例**（否则进程内多轮对话历史丢失——纯内存模式唯一的记忆来源就是实例自带上下文）；有 db 时**必须每轮新建**（否则实例自带的历史会与注入的 historyText 叠加重复）。
3. **`runExclusive` 串行队列不能删**：底层 Strands Agent 不允许并发 invoke——删了并发调用直接报错或结果错乱。`.then(task, task)` 的"失败也继续"写法不能改成 `.then(task)`（上一次失败会卡死队列）。
4. **压缩提示词的"三类保留 + 硬性清除规则"不能删改**：那是"解决即弃/过期自灭"纪律的本体——删了纪要会越压越肥，最终塞满上下文。
5. **`extractReplyText` 的兜底分支不能删**：SDK 返回形状会随版本变化，最后一级 `JSON.stringify` 保底"永远有字符串可回"。
6. **delegate 里两个"数据库没有记录"的报错不能删**：它们把"装配顺序错了"（没先 ensureButlerAgent/ensureSubAgent）在第一时间变成人话提示，删了会变成深处的天书错误。
7. **prompts.ts 六条纪律不能删改**：见面隔离/不亲自干活/平级转派/needs_human 转述/汇报不说内部黑话/不臆测——这是工程核心原则在管家层的全部落地。
8. **改任何文件后重新编译本包**（`npm run build`）：应用引用的是 dist 产物。
